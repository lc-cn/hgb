# 需求覆盖与可行性矩阵

日期：2026-11-15。状态：研究结论与待验证判断，供技术选型及架构重审；没有实现、部署或真实游戏／服务实验。

## 结论先行

App管理壳、任务／计划编辑、版本管理、历史、事件规则和通知配置，能采用成熟Android与网络／存储组件实现，当前没有证据表明需要另造平台。**真正决定产品能否达到目标的是本地游戏能力，而非这些管理页面。**

已适配任务自动操作属于有公开能力和同类项目经验支持的条件实现；但还没有本项目在目标手机或模拟器完成真实闭环的证据。跨主题尤其留出主题、新活动自主执行、Root登录态可靠恢复均为高不确定项，不能把UI原型或通用OCR／视觉模型文档当作完成证明。24小时运行与开机行为受到Android生命周期限制，只能验证具体支持条件，不能承诺任何状态下永久运行。

因此当前结论是：**管理容器可采用成熟组件；游戏执行路线需关键PoC；完整核心目标尚未被验证可行。**这不是将高风险需求排除或推迟到某一期。

## 需求来源与判断方式

需求来源依次为当前会话已确认规则、[PRD v2.4](../PRD.md)、[领域用语](../../CONTEXT.md)及当前[交互稿](../design/app-v2-design.md)。本次是已有需求的结构化分析，没有伪称做过额外用户访谈、设备实验或完整现网玩法核验。

最新模型补充：Action为基础能力，Step编排动作，Task是步骤＋配置schema，Plan是任务集合＋时间；只有Executor拥有pause/resume(mode)。continue跳过完成步骤、未完成步骤从入口新观察；restart_current_task仅当前任务step1，其他任务不变，保留本轮规则／版本、消耗和unknown。它们不是任务、计划各自的控制状态机。动作目录与表达格式尚未实现，本矩阵的证据等级不因新增概念而提升。

[旧开源调查](onmyoji-automation-survey.md)、[悬浮源码对照](assttyys-floating-layers.md)与[事件经验](event-rule-rationale.md)只用于识别故障类别或复用候选，不授予产品行为。其早期Windows优先、冲突不排队、暂停线程等描述已经被后续用户规则替代，不能移植上游的自动重试、自动启动、资源整理或阈值。

| 分级 | 含义 | 不表示什么 |
| --- | --- | --- |
| M：可采用成熟组件 | 有标准UI、事务存储、网络或确定性逻辑可承接，主要工作是集成与合同验证 | 本项目已经安装、集成或测试通过 |
| P：需要目标PoC | 路线有依据，但实际游戏、环境、回调、识别或副作用必须先实验 | 估计了工期或保证通过 |
| H：高不确定 | 缺少足以支持关键目标的项目证据，不能用通用能力替代 | 必然不可实现，或可以悄悄删掉该需求 |
| L：受平台限制 | 普通权限或系统生命周期存在明确限制，只能在允许条件下实现 | 用户已接受改平台、提权、绕过限制或缩减范围 |

一项需求可同时含多个级别，表中按子能力区分；“成熟”是技术依赖判断，“本项目已验证”是另一维度。

## 技术路线已有依据到哪一步

本文件为需求与可行性分析，不代替根agent的具体依赖选型表。可以明确采用成熟承接路线，不必把一切标成“以后再选”：

- 管理UI以Kotlin／Compose原生路线承接，结构化数据以Room／SQLite、轻偏好以DataStore类组件承接；这些解决管理与持久化，不能解决游戏识别。
- Executor采用单命令处理入口与coroutines有界异步；计划不是另一个执行器，步骤结果是推进依据。最新接口需对齐后再测试，不能照抄旧PlanRun原型。
- 云任务采用版本化数据／资源和受限步骤运行时；下载／校验／启用分开，先用真实代表流程证明表达力，不预设需要远程JS／DEX或通用插件系统。
- 本地识别以中文bundled OCR及图像／相对锚点建立离线基线。可明确选定首个基线进行比较；没有目标样本前不把候选声明为游戏准确率赢家。
- 模型／HTTP渠道／SMTP使用各自协议适配，复用路由与凭据基础设施；邮件代理与发送结果单独验证，不能把“HTTP客户端支持代理”当全部需求已覆盖。

这些是实现建议而非已经集成的事实；确切库／模型／ABI／构建版本由后续选型记录固定，避免将资料页当前示例当已安装依赖。

## 首先验证什么，失败后怎么走

以下是依赖顺序，不是重新分期，不给时间／人天估计。替代路线均为需报告和评审的选择，不能失败后静默改产品要求。

| 顺序 | PoC目标及最小问题 | 通过后能确定什么 | 失败后的路线与保留限制 |
| --- | --- | --- | --- |
| P0 首先 | 在代表手机和专用Windows模拟器里，独立APK实际取得游戏画面并受控输入；比较截图源／浮层影响，核对撤销及授权失效 | Android独立运行后端、窗口／权限、ABI和最低范围的实证；不是仅能安装 | 可比较MediaProjection与无障碍截图；用户已接受的专用Root环境可作单独受控候选。若仍需常驻PC/ADB或固定环境，先报告改变，不能默认迁移产品 |
| P1 随P0，纯逻辑可先做 | 单Executor pause/resume(mode)，旧输入在途／旧工作器卡住／晚到；continue跳已完成、restart仅当前任务 | 最新控制模型及薄输入桥必要性／实际可撤销范围 | 同进程取消只作为更简单候选；若不可中断代码使其不成立，再比较进程隔离。平台无法证明静默时保持受阻，不用超时冒充可继续 |
| P2 随P0建立观察闭环 | 模型关闭，代表领取及另一类任务在已适配和留出主题、方向／分辨率上完成真实结果核对 | 本地识别基线、跨主题可行范围；先验证用户最主要痛点 | 比较OCR／锚点／小检测器与资源适配；若只有固定主题可用，应明确核心目标未达，不能称“跨主题完成” |
| P3 依赖P1/P2 | 同容器安装两个完整任务版本，完成代表流程；安装／入队／启用／删除与步骤结果关键点中断 | 数据型步骤表达力、单版本锁、引用／离线／持久恢复路线 | 改原语或比较现有pipeline，不以eval填洞；文件／DB不一致就修安装恢复，不能靠删除配置解决。日程缺口先形成可审阅规则 |
| P4 依赖P2/P3 | 日常、领取、商店、御魂等按已明确目标／预算做代表闭环与误结果核对；不要一上来用全部22夹具当验收 | 真实业务完成／未生效／未知证据，资源规则与对象识别能力 | 缺规则先补具体任务定义；识别／结果不可靠就保留受阻，不自动购买、整理、反复刷取或降低保护 |
| P4a 可与观察研究并行 | 专用Root同环境A→B→A，目标停止、快照恢复／中断／错号／回退 | 登录态路线是否可行，及同版本／渠道／设备条件 | 失败时仍可保留助手启动当前已登录账号的路线，但“快照指定账号登录”不能标完成。其他手工登录／游戏内合法切号是待评审替代，不伪称实现快照恢复 |
| P5 依赖真实步骤／观察 | 用户选择服务图片协议／结构化／坐标／取消；再用未写活动专用流程的目标验证规则、行动、完成 | 模型接入范围和新活动实际自主边界 | 接入成功但活动失败，两结论分开；可提议“模型辅助＋人工适配任务包”，须承认低于自主目标并经评审，不能改名为自主理解 |
| P6 管理模块可先搭，真实测试独立 | 六类渠道事件投递，三域HTTP／SOCKS5，认证／DNS／TLS／SMTP、发送中断和unknown | 实际支持协议／渠道与代理组合，事件／通知不干预执行 | 单独替换相应传输适配；如SMTP代理不兼容，如实标缺口，不静默直连或自动改邮件接口 |
| P7 汇总验证 | 代表环境24小时，覆盖任务切换、人工暂停／两种恢复、异常、资源释放、存储和重启授权路径 | 有条件长期运行／自启结论与资源门槛 | 定位到生命周期、识别、native资源、网络背压或日志引用问题；限制条件需评审，不能以进程存活、自动解锁或降SDK补足证明 |

P0/P1是游戏执行的前置阻断；P2是核心“换主题”承诺的前置阻断；P4a只阻断登录态路线；P5只阻断尚无证据的新活动自主能力。这样区分可独立实现的管理能力、条件游戏执行与研究能力，避免把全部工程都说成不可做，也避免管理页完成后误报核心可行性已解决。
