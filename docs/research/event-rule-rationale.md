# 首批事件触发规则依据

日期：2026-11-15。范围：从 OAS、MaaYYs、assttyys 的原始 README、文档和 issue 提炼本项目首批提醒规则。不修改执行器、HTML 或 JavaScript，不运行游戏，不新增自动取消、重试或恢复。

## 证据与限制

- [OAS #1665](https://github.com/runhey/OnmyojiAutoScript/issues/1665)：用户报告登录页下非 Restart 任务重复导航直至超时；报告的页面图因果分析没有在本次通过运行复现确认。可作为“循环但无任务进展”的历史样例，不能证明当前版本仍有该缺陷。
- [OAS #1562](https://github.com/runhey/OnmyojiAutoScript/issues/1562)：用户报告悬赏提前结束、协作未完成导致重复执行，讨论中有退出页面的识别时序分析与局部修复反馈。说明“本方执行完成”“对方未完成”“未识别到列表”应分别表达，不应把空识别直接当完成。
- [OAS #1660](https://github.com/runhey/OnmyojiAutoScript/issues/1660)：用户报告御魂容量满弹窗下连续点击奖励并出现 `GameTooManyClickError`。这支持识别资源／容量阻塞与连续确认失败；不是授权自动整理御魂。抓取页显示已关闭，本次没有验证当前代码和实机。
- [OAS 开发入门文档](https://github.com/runhey/OnmyojiAutoScript-website/blob/master/docs/development/preamble.md)：搜索可见文档以 `GameStuckError` 表示连续截图但无操作超时。本项目不直接移植其错误处置或时间阈值；“无操作”也不等同于“无业务进展”。
- [MaaYYs README](https://github.com/TanyaShue/MaaYYs)：明确说明任务起始界面、分辨率、渠道、皮肤、OCR、游戏 UI 更新可能影响识别，且需要连接 ADB。支持将运行条件与任务结果分开。[MaaYYs #92](https://github.com/TanyaShue/MaaYYs/issues/92) 是长时间运行后电脑卡顿的用户报告，抓取页为关闭且未见维护者回复；不能推断为已确认内存泄漏或具体根因。
- [assttyys README](https://github.com/zzliux/assttyys_autojs)：列有妖气自动排队等任务，说明排队可为正常任务阶段。未找到足以确认截图权限异常处理策略的 README／issue 证据，因此本项目截图权限规则须由平台回执定义，不宣称复刻上游已验证方案。

网页抓取含缓存，上述状态仅是所见资料，不保证实时。这里采用其问题类别与区分方法，不把历史报告当作当前未修缺陷。模型不可用规则来自本项目接入模型的需求，不是上述项目默认规则。

## 八类规则建议

以下是本项目建议契约，**不是上游默认行为或已验证阈值**。每类规则只产生事件；启用状态、时间／次数条件属于规则，发送渠道属于订阅。调整订阅不应改变判定或执行状态。

| 事件类别 | 触发证据与边界 | 可配置条件 | 主要误判风险 |
| --- | --- | --- | --- |
| 任务失败 | 执行器明确报告本次任务以失败结束，并有可定位原因。只有识别超时、命令无回执或模型猜测时不得推定任务失败。 | 无额外延迟；终态每次运行只记一次。 | 将战斗单局失败误当整项任务失败；把资源不足或用户停止算失败。 |
| 结果未知 | 已发起可能改变游戏状态的操作，但不能验证是否生效；同一操作连续确认失败也在此类，保存操作与最后观察。 | 确认失败连续次数，或确认等待时长；确认是观察，不是自动重做该操作。 | 超时后动作实际已生效；若自动重做可能重复领取、购买或消耗。 |
| 排队等待过久 | 已可靠识别排队／等待队友阶段，持续时间达到该规则条件；它仍是等待事件，不是失败。 | 连续等待时长，按任务／阶段计时。 | 排队过程静止属正常，不应同时当卡死；看不见队列不等于排队。 |
| 任务无进展 | 处于主动执行阶段，观察能力正常，但已确认的步骤、进度或业务状态在条件期内没有推进。也覆盖重复走同一路径或重复操作仍无变化。 | 连续无进展时长；必要时补充同一意图的连续确认失败次数。 | 战斗、动画、排队、等待开放、用户暂停均不能仅凭画面不变算无进展。 |
| 运行条件丢失 | 原生／设备接口明确报告截图权限撤销、连接断开、控制通道不可用，或截图连续不可用。分别保存原因，不把黑屏直接标为权限撤销。 | 明确撤销／断连可立即产生；瞬时截图失败可按连续次数确认。 | 黑屏可能是加载、截取对象错误；取不到图像时应停止推导游戏结果，不能虚构任务失败。 |
| 资源或容量受限 | 可靠观察到体力／门票／次数不足、背包容量满，且已影响当前任务；记录资源名和对任务的影响。OCR 低置信度或空值不等于 0。 | 明确提示可立即产生；数字型条件需任务规则明确所需数量。 | 资源读错、等待自然恢复、未达预算和实际资源耗尽是不同原因；不得触发购买、整理或取消。 |
| 模型不可用 | 模型接口明确鉴权、额度、限流或服务异常，或请求超时，影响当前需要模型的步骤。保留服务错误类别，不改写为游戏失败。 | 连续调用失败次数或持续时长；无须依赖自动重试才能累计。 | 网络瞬断、模型有回应但无法理解、视觉证据不足应区分；错误事件不得自动换模型或重复执行游戏动作。 |
| 任务完成 | 执行器按本次目标验收并明确进入成功终态；记录已完成数量或目标证据。消失的按钮、空 OCR、线程结束都不足以单独证明完成。 | 每次运行只记一次终态；由订阅选择是否推送。 | 只完成一个步骤却报全任务完成，或用户停止／进程退出被当成功。 |

## 最小一致性要求

1. **规则 → 事件 → 渠道订阅分离。** 同一事件可被多个渠道订阅，渠道发送失败只改变投递状态，不改任务结果、不补做游戏操作、不触发额外取消／重试／恢复。
2. **阈值标明来源。** 次数和时长若由本项目给出首批值，必须标为本项目初始设计值，后续用真实日志校准；上游日志的一次超时不是普遍适用阈值。
3. **事实优先于症状。** 明确资源不足时保留资源原因；截图不可用时保留运行条件原因。已有事实不得只留下“卡死”泛化描述。尚未确定的业务结果继续标未知。
4. **连续条件按同一运行／步骤／意图累计。** 已确认取得进展、条件恢复或进入其他阶段时结束当前连续区间。只观察确认，不把规则中的计数解释为自动点击次数。
5. **防止每帧重复提醒。** 同一条件在一次持续发生期间产生同一事件身份；查看／已读或投递失败不等于故障已恢复。如何再次提醒属于独立通知产品规则，不在本次扩展。
6. **不互相篡改状态。** 排队过久、资源受限、模型不可用和无进展均是事实事件；是否暂停、结束或继续由已批准的执行契约决定，不由提醒规则顺便实施。

## 后续验证点

正式实现时需以目标设备和执行器接口验证：明确撤销截图权限与短暂取图失败的区别、动作已生效但确认响应丢失、正常长战斗／排队、OCR 读取失败与真实资源不足、一个条件持续多次观测、通知发送失败及模型超时。此次只有原始资料阅读与规则设计，没有这些运行验证。
