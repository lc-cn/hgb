## 一 产品定位与已确认方向

这是一个可长期运行的阴阳师任务管理与执行助手。用户选择要完成的目标、允许使用的资源和执行条件，助手处理日常、周期物资、商店、副本、御魂与活动任务，并让用户看清正在做什么、完成了什么、为什么停下。

已确认方向：

- 优先 Android App，目标同时在安卓手机和 Windows 安卓模拟器内使用；兼容环境仍须验证。
- 产品采用“稳定壳程序＋云端任务获取”。App 是任务管理与运行容器，游戏任务、流程、识别资源和活动适配独立于 APK 交付，不把完整游戏任务目录写死在安装包里。
- 2026-11-16 补充：容器需可扩展到其他游戏或普通 App。目标应用的包名、身份要求、任务分类与识别内容独立描述；任务、配置、计划及记录按目标隔离，无需账号的 App 不伪造游戏账号。首期仍以阴阳师验证；多应用切换、跨应用计划及并发规则尚未确定。实现边界见[多目标应用扩展](development/target-extensibility.md)。
- 任务包有独立版本。启动 App 自动拉取远端最新版，也支持手动拉取；远端版本附带更新说明，用户可指定使用已取得的版本、回退和删除本地历史版本。
- 支持游戏启动／关闭、已登录账号的本地登录态快照及本次指定账号启动；已接受专用Root环境先验证，不承诺普通权限可提取或恢复。
- 提供助手开机自启偏好，默认关闭；开机后先检查授权与身份，不自动解锁、拉起游戏或恢复托管。
- 成功核对新账号且身份实际改变后清空旧未结束执行队列，由新账号重新添加；历史与未决证据保留，失败回退不清空原队列。
- 支持 24 小时常驻，任务由用户按需启用。
- 长期目标覆盖各种任务和活动，不局限于少数固定脚本。
- 云端视觉模型在设置中自行配置，可关闭；关闭后仍有实际可用的任务。
- 换主题后的识别能力属于核心要求，不以仅默认主题可用作为产品完成标准。
- 开启模型后，尽量自主理解新活动，减少逐次人工适配。
- 包含每日／每周物资领取、永久勾玉卡产出、商店兑换、周三／周六商店、御魂强化与整理。
- 包含通知渠道配置，使用户能够获知运行错误和需要处理的问题；已纳入本机通知、钉钉、企业微信、Bark、邮件及自定义Webhook；首批事件规则已确认，真实接入与触发证据仍待验证。
- 通知管理统一收纳渠道、事件规则和事件记录；规则、事件及投递独立，所有首批规则默认关闭。
- 网络设置支持 HTTP／SOCKS5 代理，用户选择视觉模型、任务更新、外部通知的适用范围；默认直连、范围为空。
- 包含游戏运行时的悬浮球 UI，承担状态查看和快捷控制；授权无障碍后默认显示，用户可在设置关闭，关闭不暂停执行。当前球／快捷／常用三层形态与视觉以 UI v5 为基线，真实窗口与设备手势仍需验证。
- 主 App 需要横屏版本，用户从横屏游戏返回助手时可直接阅读和操作，无需为查看助手旋转屏幕。
- 任务与计划都支持立即执行一次；不改变既有计划时间。
- 视觉模型的服务商使用下拉选择，右侧配置按钮按需显示具体配置，并提供新增服务商入口；内置服务保留获取密钥引导。
- 支持将常用任务或计划加入悬浮球，快速执行与暂停关联运行。
- 异常以原因说明和相关配置修正为中心，替换空泛的“查看并处理”。
- 悬浮球中的常用项根据当前游戏界面自动过滤；可执行性判断属于内部职责，普通主界面不展示技术支持矩阵。开发者模式收纳任务制作、App内调试、上传发布及开发诊断，不增加执行权限；上传成功即成为新版本，不另设云端草稿或发布步骤。
- 完整产品形态与范围确认后，由不同子 agent 分别负责系统架构、技术方案、UI 排版，再安排开发。

## 二 完整 App 的使用形态

用户在同一 Android 环境内安装助手和游戏，由助手获取云端任务，按需配置任务与模型，切换到游戏执行，随后可返回助手查看记录、修改计划或处理异常。任务更新和 App 更新是两个独立概念。

需要同时解决“助手页面里的管理操作”和“执行游戏时的暂停、停止、查看当前任务”。后者纳入悬浮球与展开面板设计；显示授权、系统限制及实现方式由技术方案验证。

完整使用闭环：

安装与环境检查 → 配置可选模型与通知渠道 → 选择任务与资源规则 → 配置执行计划 → 检查待执行内容 → 启动并通过悬浮球查看状态 → 收到异常消息或查看结果 → 接管或修改规则 → 继续运行。

产品应同时支持两种使用情境：

| 情境 | 用户预期 | 产品需要表达 |
| --- | --- | --- |
| 临时处理 | 现在领取物资、兑换商品、整理御魂或执行某项任务 | 本次范围、预期消耗、执行结果 |
| 长期托管 | 按已启用任务及计划持续处理游戏事项 | 当前任务、下次执行、周期完成情况、等待与中断原因 |

两种情境复用同一套任务设置和资源规则，临时执行不隐含开启长期计划，保存计划也不隐含额外消费授权。

## 三 页面结构建议

完整 App 采用五个主入口。当前视觉以用户认可的[UI v5](design/ui-v5/index.html)为基线；HTML 为设计模拟，原生 Android 实现仍需按相同交互验收。

横屏优先利用可用高度，按内容职责分组为一或两列，列宽可不等分。短字段并排，长内容与多选组合理换行；工作台、任务中心、计划及配置页减少不必要纵向堆叠。主要操作保持可达，切方向不丢草稿、选择与运行。

主 App 同时提供竖屏与横屏布局。横屏保留五个入口和同一套任务／状态，依据实际可用宽度与高度选择导航与内容重排方式；不能只将竖屏画面拉宽，也不因横屏就固定采用桌面侧栏。切回助手、进入详情和编辑规则时保留当前上下文，避免强制竖屏或无故返回首页。游戏内横屏悬浮球与主 App 横屏是两项独立交付。

| 主入口 | 用户在这里做什么 | 页面与内容 |
| --- | --- | --- |
| 工作台 | 管理游戏状态和执行队列 | 标题同行展示账号大区／昵称及游戏图标控制；内容区展示当前执行、队列、结果和按需异常 |
| 任务中心 | 决定做什么以及怎么做 | 六类业务任务、规则、行内常用星标和执行；不展示开发者可执行性矩阵 |
| 托管计划 | 决定何时做、顺序与目标 | 每日／指定星期计划、任务编排、时间、目标和资源限制 |
| 历史记录 | 查看通知和执行结果 | 仅“通知”“运行”两个视图；保留投递状态、实际结果与资源消耗及关联证据；异常处理由工作台和详情进入 |
| 设置 | 配置公共能力与使用方式 | 必要授权、账号资料与开机自启、云端模型、通知管理、网络设置、悬浮球、运行规则及数据设置；开发诊断独立收纳 |

业务任务、执行计划、结果消息与公共设置分工明确。任务规则在任务详情配置，计划引用任务规则，工作台和悬浮球提供同一运行状态的快捷视图，避免同一规则在多处各存一份。

任务中心建议采用以下六类。每日、每周、周三／周六、定时、模型依赖是筛选标签，不再与业务类别混排；同一任务不因多个标签而重复创建。

任务中心右上角显示当前启用的版本号，点击进入任务更新；与已知远端最新版不同时附一个小红点，启用最新版后红点消失。无当前版本显示“未启用”，无可靠最新版信息时不伪造更新状态。

六类是管理目录，具体任务条目、参数表单及执行定义从云任务包读取。原型中的 22 项任务是缓存目录的示例夹具，不是未来 APK 的固定完整清单。任务中心提供“任务更新”入口，设置引用同一个页面，不新增第六个主入口或另建插件市场。

| 业务分类 | 内容与专门页面 | 归属原则 |
| --- | --- | --- |
| 日常与领取 | 签到、日常任务、花合战、悬赏、宠物、每日／每周物资、永久勾玉卡产出 | 区分完成任务与领取奖励；原有具体玩法清单仍待核对 |
| 商店兑换 | 商店列表、商品规则、数量与预算、周三／周六商店 | 所有商店兑换集中配置，周期由标签与计划表达 |
| 副本与挑战 | 御魂、觉醒、探索、御灵及待确认的周期挑战 | 获取资源或挑战关卡；单人／组队为具体任务条件 |
| 御魂管理 | 强化、整理、筛选与保留规则、对象和素材检查 | 管理已有御魂，和“刷御魂副本”明确分开 |
| 结界与阴阳寮 | 结界收取／挂卡、个人／寮突破及寮相关任务 | 同一玩法只保留一个任务定义，可关联领取结果 |
| 限时活动 | 已适配活动、新活动理解、活动目标与阶段 | 活动内奖励与兑换可从活动详情关联访问，复用公共规则与记录 |

例如，周三／周六商店归入“商店兑换”，并标注相应周期；御魂副本归入“副本与挑战”，强化整理归入“御魂管理”。跨页面快捷入口指向同一项任务，不重复调度和计数。

### 3.1 工作台

工作台是独立的运行管理入口：统一暂停／恢复状态机，展示与管理队列，查看当前执行状态和结果摘要。任务中心负责具体做什么及操作规则，计划负责哪些任务在何时执行；详细历史仍在历史记录。页面切换不重建、停止或另建状态机。每日与每周进度必须基于任务结果，不能把识别失败显示为“已清完”。

工作台展示当前执行项和待执行队列，列出名称、简短状态与等待时长。等待项与被抢占项按调度顺序展示；横屏利用主副列，队列单独滚动，避免挤压当前控制。 当前任务／计划名作为主文本，执行阶段与优先级作为次信息；标题栏不再重复提供运行更多菜单，记录与暂停／停止从当前执行区到达。当前原型删除以全历史完成计数冒充“今日与本周”进度的区块，保留按当前账号读取的实际最近结果；周期汇总必须另有真实周期依据。

队列行支持右滑移除，包含正在执行或卡住的当前项。移除当前项后继续调度剩余项，不隐含暂停整个队列；这是与手动暂停／长按停止不同的操作。移除须撤销旧执行器的输入权限，独立确认旧输入已静默后交接，不能等待卡住的任务自行返回，也不能只删一行而仍在后台操作。移除中有真实状态反馈，重复操作不重复取消或重做。

手动暂停或长按停止当前项则暂停整个队列，便于用户自己操作游戏，直到用户继续。移除普通等待项不解除已存在的人工暂停；结果未知仍保留核对证据，不因移除伪装成已失败或已完成。

### 3.2 任务目录与详情

普通任务界面显示用户需要设置和理解的作用、目标、资源、停止条件及最近结果。页面识别、主题兼容矩阵、技能适配状态和内部可执行性判定不放在普通主界面。需要用户补齐密钥、授权或任务规则时，按实际原因给出明确入口，不要求用户理解技术支持分类。

常规界面保持简洁：常用使用列表行星标，不附带过滤原理；不在每页重复解释保存、单次执行、周期启用和运行状态之间的关系。帮助性说明集中在使用帮助，技术信息放开发诊断。页面保留实际目标与资源影响、单位和输入约束、必要费用提示，以及发生问题时的具体原因和操作入口。

用户应能发现后续待交付能力，但未交付条目不能出现可执行假象；是否在发布版显示未来功能，由分期与 UI 方案决定。

任务执行步骤使用默认收起的只读details，用户按需展开，不改变实际步骤定义。点击任务直接进入该任务的配置，摘要、目标与资源规则在同一页完成，常用星标留在列表；不再经过只有介绍和“配置规则”的中转页。详情采用顶部返回；不保留只有“返回列表”的固定底栏，也不在详情重复五个主导航。规则复杂时按内容分组，不能把每个字段都拆成新页面。

普通业务参数单选使用单选按钮组，多选使用可切换的多选按钮组；云端视觉模型的服务商按用户指定使用原生下拉，工作台未启动时的账号资料可下拉展开选择启动账号，其余常规字段不采用下拉或checkbox列表。按钮组竖屏纵向排列，横屏横向排列且超出换行；方向切换保留选值和草稿。

输入控件随场景选择。有明确合理范围的数值可用滑块，并提供同步的精确值输入；次数、数量与大额预算使用适合其单位和精度的数字输入或步进控件，不为套用滑块编造上限。时刻使用时间选择器，日期及日期范围使用对应选择器，不让用户手写格式。任务包参数描述提供字段语义、单位、范围与步长，由容器渲染；缺少必要控件能力时明确不兼容，不随意降级或猜测新值。切方向和返回编辑时保留输入草稿。该要求不额外新增日期触发、计划周期或资源规则。

任务和已保存计划的列表行右侧均提供“加入队列”运行按钮，不单独建设执行目录或额外执行流程。执行使用其已保存规则、资源限制与资格检查，仅发起本轮运行，不隐含打开周期计划、改变执行时刻或扩大次数与预算。计划手动执行后，后续周期执行如何核对本周期已完成项目，沿用同一资格和实际结果，不能盲目重复领取或消费。

任务和计划在各自列表行右侧提供一个可切换的常用星标：点按选中或取消，详情不再重复放常用开关。选中后自动出现在悬浮常用候选，取消后移除。常用是任务／计划本身的属性，不另设收藏、快捷管理或添加页面。悬浮入口引用原任务或计划，不复制规则、不改变计划日程。立即执行与定时到点均提交执行项进入同一队列，由优先级统一调度，不创建并行游戏输入。

任务和计划列表按同一执行状态显示操作：未入队时运行按钮加入队列；等待或被抢占挂起时显示“队列中”标识，运行按钮禁用；当前执行项显示运行状态，按钮改为暂停，暂停后可继续。工作台、列表和悬浮球的暂停／继续及长按停止均作用于同一关联运行。长按后不再触发短按，取消或离开控件不停止其他运行。手动暂停保留本轮进度并暂停整个队列；停止结束本轮执行项并暂停整个队列，其他排队项保留。新请求可以入队，只有用户继续后才恢复调度。悬浮面板已提供当前运行控制时，常用区不重复放同一个运行的暂停按钮。

计划列表竖屏单列，横屏可两列展示，常用与执行操作保持在各自行右。 计划编辑只在已选行展示引用任务，提供移除图标与顺序调整；候选区只列未选任务，不再把已选内容重复铺在全量选择区。移除只取消该计划引用，不删除原任务。计划结束条件使用明确选项，默认本轮任务完成即结束；可选最长运行时长，用小时／分钟设置，不输入自由规则。无时长限制保存为空值；限定时长需正值、整数且分钟为0–59。任务本身的次数和资源限制继续在原任务设置，不重复创建一套计划预算。

计划周期只保留“每日”和“指定星期”，指定星期只选周一即可表达每周一执行。移除重复的“每周”和周期总启用开关；有效计划保存后按所选时间生效，不立即插入一次运行。时间、引用任务及指定星期为空时提示补齐，不能静默设置默认时间或星期。

### 3.3 物资与商店页面

物资页按来源和周期展示领取资格、可领取、已领取和异常；永久勾玉卡产出作为明确条目。

商店页展示商店与商品、支付资源、数量、限购及开放条件。周三／周六商店是已要求的业务场景，正式名称与刷新规则待核对。领取权益产出与购买权益分开配置。

### 3.4 御魂页面

强化与整理为两个明确操作入口，复用御魂筛选与保留规则。用户可检查目标御魂、强化阶段、素材、预算及整理命中条件。

整理操作需拆分为具体能力，如筛选、锁定／解锁、标记及消耗性处置。哪些操作纳入、是否预览确认、何种规则可无人值守执行均待确认；不能由一个开关默认包含所有处置。

### 3.5 活动页面

展示已适配活动与需要模型理解的活动，分别说明能力条件。用户能查看活动目标、助手理解的规则、资源要求、当前阶段、执行结果及无法判断的事项。

活动不另建一套与常规任务冲突的调度与预算规则。模型自主执行的范围与是否首次确认计划，作为显式产品决策。

### 3.6 历史记录

记录主入口名称为“历史记录”，只保留“通知”“运行”两个标签，不另设“待处理”标签。通知记录展示投递尝试及渠道反馈，运行记录保存任务／计划的实际结果、资源影响和证据。横屏使用左侧标签、右侧可独立滚动的内容区；切换方向和标签保留对应上下文。

移除“待处理”标签不移除异常能力。工作台和悬浮球保留简短异常入口，问题详情说明原因与实际影响，并定位到模型、任务、授权或通知渠道等相关配置。未知兑换／强化结果先核对商品、限购、余额与已知证据，不能仅通过保存配置、成功投递通知或更新任务包来确认此前操作结果。

事件记录位于“通知管理”，用于查看规则触发事实、来源及关联投递；它与历史记录的通知投递列表职责不同。事件可以没有订阅渠道，仍保留事件记录。渠道已接收、用户已读、问题已处理和任务已恢复分别表达，打开记录不自动解决异常。

### 3.7 设置分组

设置及通知管理入口列表在横屏用两列，竖屏保持自然单列，不增加中转页。

| 分组 | 配置内容 |
| --- | --- |
| 运行环境 | Android 授权、游戏环境、兼容检查及运行条件 |
| 账号资料与开机自启 | 已保存本地账号快照的资料、改名／删除及助手开机自启偏好；不重复游戏启停或启动账号选择 |
| 任务来源与更新 | 云任务目录、获取与更新状态、已缓存版本、待启用或需要升级助手的说明；来源与更新策略仍待细化 |
| 云端视觉模型 | 服务商下拉、右侧按需配置、新增服务商、获取密钥引导、密钥与开关、能力验证 |
| 通知管理 | 唯一通知设置入口，内含通知渠道、事件规则、事件记录；等待阈值归入对应事件规则 |
| 网络设置 | HTTP／SOCKS5、代理地址与端口、可选账号密码，以及视觉模型／任务更新／外部通知适用范围 |
| 悬浮球 | 显示开关（授权无障碍后默认显示）、尺寸与透明度等外观选项、位置与展开方式；其余具体选项待 UI 方案确认 |
| 开发者模式 | App内制作步骤／任务／配置schema、调试、生成JSON并上传发布，以及页面识别／环境／常用过滤诊断；不作为普通用户必经配置 |
| 运行与数据 | 已确认的恢复规则、日志与截图留存、必要的导出和清理方式 |

任务的商品数量和御魂筛选规则属于业务页面，不塞入公共设置；通知渠道的密钥也不分散到各任务详情。

模型页的常规路径为“服务商下拉选择 → 点击右侧配置 → 填写密钥 → 保存”。服务商选择使用原生下拉，是普通单选按钮组的明确例外；未点配置时不铺开连接表单。另提供新增具名服务商，保存后进入下拉；新增或切换不自动启用云端模型，取消新增不登记服务。每个服务商独立保留草稿、已保存连接及凭据，选择变化不隐式保存或验证。“获取密钥”直接链接该服务的官方创建入口，步骤说明放在旁边的帮助，不增加一个必须经过的引导页。每个预设包含明确的服务区域、协议、地址、视觉模型与能力要求，用户无需手动拼地址或填写模型标识。引导说明必要的开通或额度前提，不承诺无注册、免费或所有地区通用。保存和主动测试分开，保存配置不隐含付费调用、发送截图或能力已验证；测试按钮需说明测试内容，本轮原型仅模拟反馈。

新增或自定义服务的名称、服务地址、模型标识与兼容协议按需配置；内置服务的其他参数可查看，不是普通配置的必填表单。预设参数需经官方契约核验和后续兼容测试，不能假定任何同名模型支持图片输入。预设变更、备用模型和跨服务切换不自动生效，更不能因一次失败把截图发送给另一服务。

### 3.8 悬浮球与展开面板

悬浮球用于游戏中的轻量控制，展开面板提供当前运行信息。它与主 App 显示同一运行状态，不单独维护一套任务开关或队列。

本轮原型统一为一套逐级展开的三层结构：收起小球 → 快捷层 → 常用列表。快捷层提供当前运行的小图标控制、常用入口、简短异常入口和返回助手；点常用才展示按当前画面过滤的任务／计划。第三层保留同一份当前运行行，可返回快捷层，也可直接收起到小球。主 App 不再提供 A/B/C 悬浮结构选择器，旧三种方案仅作历史对照。此处收敛信息层级，具体视觉和真机兼容仍需评审验证。

| 形态 | 信息与操作建议 | 设计要求 |
| --- | --- | --- |
| 收起的球体 | 运行／等待／暂停／异常状态，必要的提示标记 | 状态不能仅靠颜色区别；避免持续遮挡游戏关键区域 |
| 展开面板 | 当前任务、进度或等待原因、暂停／继续、停止、返回助手、查看待处理问题 | 高频操作可快速到达，危险的相邻操作需防误触；不承载复杂任务编辑 |
| 异常详情 | 问题摘要、已知游戏状态、处理入口与可执行的接管操作 | 与消息中心关联；何时自动展开、是否打断游戏待确认 |

UI 设计需覆盖拖动与点击的区分、边缘和屏幕边界、横竖屏与不同尺寸、展开收起、临时隐藏及再次唤出、授权失效，以及真机触控和模拟器鼠标操作。吸边、自动收起和手势映射目前是待评审选项，不预设触发阈值或默认值。

技术与 UI 需共同验证悬浮层是否干扰游戏截图识别和操作区域，不能因球体遮挡或截获输入导致执行错误。隐藏球体不等于停止任务，暂停也不等于停止；这些结果必须明确反馈。应用尚未确认暂停或停止生效时，面板不能提前显示成功。

后续 UI 子 agent 应单独交付悬浮球的状态样式、展开面板布局、手势与命中区域说明，覆盖正常、等待、暂停、异常、停止中和权限不可用等状态。

悬浮展开后支持访问用户选定的常用任务和计划。快捷项只显示名称和必要的关联运行状态，技术可执行条件由内部判断，可立即执行；已运行的关联项目提供暂停／继续。暂停作用于实际运行，不能把暂停当前运行误显示为已停用周期计划，也不能对尚未执行的收藏项伪造暂停状态。

展开面板中，当前任务与其他任务采用同一行结构：左侧名称与简短状态，右侧为与启动按钮同等尺寸的小图标，分别暂停／继续和停止。不使用宽大的暂停按钮或独立大块控制区；图标含可读标签，等待确认期间反映真实状态。当前任务控制独立保留，常用区不重复一份。

用户在任务或计划列表行点按常用星标，悬浮球自动显示当前常用项，不另做快捷项添加、移除或排序流程。任务或计划删除、规则变化、权限缺失、模型不可用时，快捷入口反映当前状态；不使用收藏时复制的旧规则。游戏内不编辑复杂任务或密钥；常用星标直接放在原任务／计划列表行，不要求先运行一次。

### 3.9 按当前画面过滤常用项

悬浮列表由“已开启常用的任务／计划”与“当前界面可开始执行的项目”共同决定，不要求用户手动维护支持页面或过滤规则。过滤只改变当前可见列表，不关闭常用开关、不删除项目、不修改计划，也不自动开始执行。

开发者在任务定义中描述可开始的场景、必要能力以及已具备的导航路径。判断的是能否从当前画面开始执行；入口不在当前页但可通过正常导航进入的任务，不应仅按同名页面匹配而被排除。计划使用其实际执行入口和所需条件判断，不因一个任务碰巧匹配就宣称整轮可执行。具体游戏场景和任务对应关系须通过后续实现验证，本稿不预设某副本内能否跳到某商店。

内部区分“可以开始”“当前不可开始”“画面或条件未知”。识别尚未完成不能当作确定不支持；普通悬浮界面用简短状态如“正在识别当前画面”，确认无可执行常用项时才显示“当前暂无可执行的常用任务”。切换画面、主题、配置或能力后重新判断，不能继续使用旧画面的结果。执行时还需核对当前状态，列表可见不等于永久获得执行许可。

当前运行的暂停／继续／停止控制独立于候选常用列表。即使当前画面不适合启动新任务，或当前运行项因此不在候选列表中，用户仍能控制已启动的运行，不能因自动过滤而丢失停止入口。

### 3.10 开发者模式

在设置中单独收纳开发者模式，包含任务制作、App内调试、上传发布及原有开发诊断，不在普通首页或任务列表展示技术支持状态。开发者可以使用App动作编排步骤与任务、编辑配置schema，生成一套任务JSON并上传。上传成功即发布为云端可拉取的新版本，不另设云端草稿／发布步骤；普通用户仍自行选择启用。

开发者模式仅对项目负责人及其指定开发者开放。采用GitHub授权登录，并核对指定任务仓库的有效权限；以GitHub仓库／组织团队权限管理指定人员，不另建开发者白名单或共享授权码。登录GitHub本身不代表有权进入或发布，也不能以任意自有仓库权限解锁。任务发布就是向指定仓库创建Release并上传任务JSON／资源附件，实际发布权限由GitHub校验。普通用户使用任务不要求写权限；仓库可见性与只读访问策略待配置。

任务制作应保持简单。推荐选动作、填参数、编排步骤与配置字段的表单流程，JSON由App生成；支持复制已有任务修改作为简化建议，不要求先手写整份JSON或建立复杂节点图。App内可试跑调试任务，查看当前步骤、动作输入输出、识别结果和错误位置，调试走同一个执行器。具体编辑与调试命令以[任务制作设计](design/developer-task-authoring.md)评审，不据此冻结JSON协议。

本地草稿保存、调试和上传发布分开，保存或试跑不自动上传；调试不自动启用或替换正式任务版本。当前HTML原型只提供原有开发开关／诊断，新增制作、调试和真实上传尚未实现。

诊断内容建议包括当前页面识别结果及时间、场景与环境信息、候选任务及过滤原因、任务前置条件、识别依据、主题兼容与必要日志。开发者可以解释为什么某个常用项消失，普通用户不必逐项处理“支持／不支持”。

开发者模式不改变任务权限、资源规则或执行安全条件，也不开放未经定义的强制执行。入口改为授权访问，不能仅靠本地开关开放；GitHub令牌不进入任务JSON，发布由GitHub实际鉴权。截图和日志仍遵循数据设置，不因进入开发模式而自动上传。Android授权实现及单次上传内部步骤属于技术提案，不增加人工发布审批；旧原型的开放诊断开关尚未对齐，不能作为已实现保护的证据。

### 3.11 工作台游戏状态与账号

游戏状态管理位于工作台标题同行，不另设必须进入的游戏操作页。账号资料区紧凑展示大区与昵称：未启动时可点开下拉选择本次启动账号，旁边图标启动；游戏启动后禁用账号切换。运行中当前账号尚未保存时，在资料旁显示保存登录态图标，另有停止游戏图标。游戏启停与执行队列暂停／停止明确分开命名和无障碍提示，不复用含义不明的“停止”。

设置保留账号资料管理与助手开机自启，不重复放启停或启动账号选择。账号列表／详情（`#accounts`／`#account/id`）用于资料、验证状态、改名和删除本地快照；删除不删除游戏账号、不登出游戏，操作依赖中的快照不可删除。旧独立游戏操作页不作为正式操作入口。

失败、身份待核对或权限不足时，在工作台内容顶部按需显示简短原因和可用处理入口，不常驻状态表格与解释段落。未核对时不把预期账号显示为已验证的当前账号；仍保留独立静默与身份门槛。

产品目标是保存已登录游戏的登录态快照供之后指定账号启动。工作台未保存账号的保存图标是采集入口，账号管理不重复提供采集或游戏启动按钮。点击图标先短确认说明将暂停托管并停止游戏；确认后再走既有一致性流程，不是运行中无影响保存；保存完成仍为未验证。真实停止、提取和恢复方式尚待受控设备验证，不能把返回桌面或截图权限当作强停／跨App私有数据访问。

默认庭院账号A仅为元数据夹具，非实际读取。恢复后须新的UID／区服／渠道观察核对，演示通过只标`verified-demo`；错误身份保留失败和回退元数据，回退后也需核对原身份。设备、渠道或游戏版本不兼容不能直接恢复。

### 3.12 外观与当前 UI 基线

默认跟随系统，用户可手动选择浅色或深色。切换按钮直接放在设置标题右侧，使用“系统／浅色／深色”三项，不另建外观页面或列表入口。

主体使用黑白灰；图标允许丰富配色并混入透明度。状态保留其语义色：运行／信息蓝、成功绿、警告／结果未知琥珀、失败红、更新圆点红；同时保留文字或图形依据。按钮使用用户要求的液态玻璃视觉，内容与长表单保持可读；降低透明度或不支持模糊时提供实色回退，减少动态时取消非必要动效。

UI v5 的颜色、透明度和材质参数是当前视觉参考，原生实现需依据实际合成背景验证可读性，不机械照搬 CSS。横竖屏、工作台、任务中心、计划、历史、设置及三层悬浮沿用已确认交互。截图可验收布局和外观，不能证明游戏能力或真实状态机已实现。主稿、完整流程和开发者预览各自的 fixture 也不能直接移植成多套执行器。

## 五 本地能力与模型增强的统一体验

模型是能力增强配置，用户始终使用同一套页面、任务、计划与记录。

| 能力 | 关闭云端模型 | 开启云端模型 |
| --- | --- | --- |
| 已适配常规任务 | 在本地已验证范围内执行 | 保留同样的任务与目标，模型参与方式由技术方案验证 |
| 物资、商店、御魂规则 | 建议提供本地可执行路径 | 可辅助理解界面，不自行改写商品、预算或保留规则 |
| 主题变化 | 在本地已验证范围内处理，未知状态可见 | 评估对陌生主题的理解能力，不宣称任意主题必定支持 |
| 新活动 | 已适配活动可执行；未适配内容说明限制 | 目标是理解规则并执行未写专用流程的场景，须独立验证 |
| 云端服务异常 | 无此依赖 | 区分配置、网络、限流与响应问题，按确认规则处理受影响任务 |

模型关闭、临时不可用和任务本身不支持是不同状态。运行中开启或关闭模型如何影响当前任务，需要明确生效规则。

### 5.1 稳定容器与云任务

App提供基础动作能力和唯一任务执行器，并承载统一状态、计划、用户配置、模型与通知接入、主界面和悬浮控制。开发者使用App动作编排步骤与任务，提供任务配置schema，封装为一套JSON及相关资源发布到云端。用户拉取任务版本、填写配置后，可直接提交任务执行，或自行组合为定时计划；具体执行仍统一入队。

业务能力的App更新用于新增／调整支持的动作；任务流程与配置schema等更新通过云端任务JSON交付，已有动作足够时不要求更新App。JSON格式方向已确认，具体字段、动作合同、解释与校验方式由技术方案提出并验证；采用JSON任务不等于已经批准下载任意程序执行。

在现有容器能力足够时，修复识别、支持新主题、调整任务流程或新增活动可以只更新任务包。若任务依赖容器没有的新系统能力或不兼容的运行契约，则清楚提示需要升级助手，不能承诺所有更新永远无需更新 App。

云端获取、完整性与兼容核验、缓存、启用是不同阶段。失败时不能将残包当作可用任务；首次无缓存和已有可用缓存的离线情境分别表达。已取得的任务应能在其本地依赖具备时使用，不能因为任务目录服务暂时不可达就无依据禁用全部本地任务；本身依赖云视觉或网络的步骤仍受实际条件限制。

一次运行绑定明确的任务及依赖版本，更新不替换在途步骤。用户的常用、计划引用和规则关联稳定任务身份；更新不能静默重置、复制或丢弃这些设置。参数变化若不能无损兼容，保留原设置与原因，不能猜测新的消费规则。结果未知仍按原运行核对，不通过降级、更新或重新下载来消除。

启动 App 自动获取远端最新版及其更新说明，完成可用内容的拉取和校验；用户也可手动拉取最新版。启动指一次 App 启动，不是每次切页面、切方向或从游戏返回。拉取在界面可用时进行，有可用本地版本时不阻塞其管理和使用；失败如实提示并保留现有内容。

任务版本页采用平面列表，只展示本地已取得的任务版本和更新时间，右侧为“启用”“删除”。已启用行显示禁用的“已启用”，删除置灰；其他占用导致的不可删除状态也置灰，具体规则收在帮助。点击版本行正文展开更新说明，再次点击收起；操作按钮不触发展开。删除后对应本地行移除。手动拉取最新版放在顶栏，不另放版本标签、独立说明按钮、状态表格或大段原理说明。远端获取失败不等于版本已下架，版本比较使用远端明确的最新版标识，不依赖版本字符串排序猜测。

拉取最新版不覆盖用户指定的使用版本。用户可选择完整、可信、兼容的本地版本用于后续新运行，包括回退到旧版本；切换不回滚游戏里已经发生的操作、不重做未决消费，也不修改常用、计划启用或用户规则。当前运行继续绑定原版本，本轮原型在运行结束后由用户再选择切换，不自动停止任务。

本地历史版本支持删除；当前使用、运行／暂停中或未决结果恢复所依赖的版本需保留，并显示不能删除的具体占用原因。删除只清理该版本的本地内容，不删除云端版本、任务设置、常用、计划或运行记录；共享资源仍有其他引用时不能一并误删。已删除的远端版本仍可按其可获得性重新拉取。

启动拉取和手动拉取已确认。持续后台轮询、自动切换使用版本、自动回退、来源管理和发布审核机制仍需另行细化，不由本次启动拉取推导。版本兼容的技术细节进入开发诊断，普通页面保留更新说明、使用选择、删除原因和必要的升级要求。

## 六 统一的状态和资源边界

无论入口是物资、商店、御魂还是活动，都必须区分完成、等待、未满足条件、执行失败、结果未知和需要接管。具体展示词汇可由 UI 设计优化，但不能合并不同含义。

完成依据来自游戏实际状态。已点击不等于完成，页面识别失败不等于没有物资，兑换结果未知不等于失败。对可能产生消耗的操作，恢复或重试前先确认实际结果。

用户规则需要覆盖商品与数量、货币和门票、强化对象与素材、御魂保留条件等。未确认的规则不由模型自行猜测。任务间共享资源或操作对象时，不能出现一个任务仍在判断、另一个任务已经消耗的情况。

内容层次为动作→步骤→任务→计划。动作是可复用基础能力，步骤组织动作为业务阶段；任务由多个步骤和一组配置schema组成，用户填写值后形成已保存任务配置；计划由有序任务集合及执行时间管理组成。任务是配置与交付的基石，步骤／动作不增加普通用户配置页面。动作目录和步骤表达格式由技术方案提出并验证。

队列排序单位为一次独立任务提交或一份计划提交集合，计划内部按所选顺序处理；这不增加计划执行控制状态机。

计划优先级为本轮全部任务优先级之和，提交时锁定，子任务完成或失败后不递减。例如计划内任务10和20，整体优先级30；执行其中10时，独立任务25仍等待。严格更高优先级可在旧输入安全静默后抢占，平级按入队顺序；高优结束后从所有等待／可恢复项中统一选取。

暂停由唯一任务执行器处理，暂停整个自动执行过程。恢复执行器时选择“继续”或“重新开始”两种恢复动作，而不是给任务、计划各建一套暂停／恢复状态机。计划只是有序任务集合与定时提交规则；排队与运行标识从任务和执行器派生。原有整计划合计优先级只负责本次提交的排序，不产生第二层执行控制。

任务恢复以步骤为粒度：已完成步骤跳过，未完成步骤从入口重新观察并执行，不保存动作中途的运行细节。选择“重新开始”时，该任务从第一个步骤开始，其他任务不变。原尝试的结果、实际消耗和未知证据仍保留。领取／兑换等可能已生效但结果不明确时先核对，不能通过继续或重新开始盲目重复消费。人工暂停仍挂起整个队列，直到用户继续。

人工暂停／停止将全局自动操作挂起，直到用户继续。继续时重新观察游戏并核对进度，再按统一优先级选择执行项。确认失败记录原因后继续后续任务：计划子任务失败后继续其余子任务，整轮结果区分部分失败与全部失败。未知结果不等于确认失败，不直接重试或跳过；完成和失败事件不能解除人工暂停。

每份执行项锁定任务包、配置、计划、优先级及账号归属快照；排队与挂起期间更新配置不改变已提交的一轮。同一任务或同一计划尚未结束时不得重复入队，独立点击与定时触发共用此约束；结束或移除后可重新添加。同一到点事件和同一命令重复交付仍返回原结果，不重复入队。现场条件暂不满足可等待，不能把暂时识别未知误报成配置不存在。执行器、队列与通知职责独立。完整转换及安全交接见[执行调度设计](design/execution-scheduler.md)。

优先级生产取值和默认值、跨周期重叠、错过补做、时长到限策略、游戏重启后的真实恢复、重新登录条件和自动重试仍需分别验证或确认；原型数值与模拟事件不构成生产默认。

### 6.1 通知管理、事件规则与投递

设置中只提供一个“通知管理”入口，替代旧“排队等待通知”入口；内部为通知渠道、事件规则、事件记录。等待提醒是事件规则之一，不再由渠道表单或执行器各维护一份独立阈值。当前页面关系为 `notification-management → channels / event-rules / event-log`。

用户已确认六类渠道：本机通知、钉钉、企业微信、Bark、邮件、自定义 Webhook。本机通知只需要相关权限、启用和订阅，不显示外部地址或密钥；钉钉／企微填写机器人目标，Bark填写服务器与设备密钥，邮件填写发件服务、账号及收件人，Webhook按其目标展示必要认证。渠道列表的添加、编辑页的测试／保存均在顶栏右侧，不重复放底栏。切换类型与目标不能串用凭据。

事件规则决定“何时产生事实事件”；已启用渠道的订阅决定“向哪里投递”。完整路径为 **规则 → 事件 → 已启用渠道订阅 → 投递记录**。满足已启用规则的事件即使没有订阅也保留，未匹配渠道不等于触发失败。渠道测试使用当前草稿，仅产生测试投递记录，不产生业务事件、不隐式保存。投递失败、查看记录或已读均不改变执行结果、队列或异常处理状态。

首批11项规则如下，**全部默认关闭**。推荐次数／时长仅在规则编辑时预填；保存并启用后才作为该规则条件，不是上游默认、实测可靠性阈值或已启用策略。

| 稳定标识 | 规则 | 触发含义与可配置项 | 编辑建议预填 |
| --- | --- | --- | --- |
| `task-started` | 任务开始 | 任务首次真正开始；普通恢复不重复开始事件 | 无阈值 |
| `task-succeeded` | 任务成功 | 按目标验收并进入成功结果 | 无阈值 |
| `plan-started` | 计划开始 | 一轮计划首次开始，恢复不重复触发 | 无阈值 |
| `plan-completed` | 计划结束 | 按用户勾选的完成／部分失败／失败／取消结果筛选 | 结果由用户选择 |
| `execution-failed` | 连续执行失败 | 同一任务／计划的确认失败次数；未知不计作失败 | 1次 |
| `unknown-result` | 结果待核对 | 操作可能生效但无法确认；保留原因及关联证据 | 无阈值 |
| `queue-wait` | 排队等待过久 | 首次执行前的有效排队等待达到时长；人工暂停与恢复核对不累计 | 10分钟 |
| `no-progress` | 执行无进展 | 主动执行时已确认进度长期不推进；正常战斗、已识别等待和人工暂停不直接算无进展 | 5分钟 |
| `condition-lost` | 运行条件中断 | 有执行或排队事项时，可靠观察到截图／操作能力中断 | 无阈值 |
| `resource-shortage` | 资源或容量受限 | 已确认资源不足或容量限制持续达到时长 | 10分钟 |
| `vision-unavailable` | 视觉服务异常 | 正在使用的视觉服务异常持续达到时长 | 2分钟 |

同一持续条件不因每帧观察重复产生新事件；再次提醒、合并、静默及恢复通知策略仍待细化。开启规则不补发此前已发生的离散开始／成功／结束事件。关闭提醒不关闭执行器对未知结果、输入所有权等安全约束。规则只产生提醒事件，不自动取消、提权、购买资源、重试或恢复任务，也不自动切换模型。

首批规则参考开源历史问题类别及本项目需求，依据见[事件规则研究](research/event-rule-rationale.md)，职责及模拟契约见[事件通知架构](design/event-notification-architecture.md)。历史 issue、推荐值和原型模拟不代表上游当前缺陷、通用默认或真机验证结果。

事件内容应关联时间、来源、原因、执行状态、必要资源影响与处理入口；不得泄露模型、通知或代理凭据。真实渠道协议、截图外发、留存、投递重试与外部存活监测仍需单独验证和决策。助手进程已停止时，不能保证由该进程发出告警。

### 6.2 网络设置

网络设置提供直接连接／使用代理，支持HTTP与SOCKS5、地址、端口和认证选择；可选用户名／密码。默认直连、范围为空。使用代理时须明确选择类型、地址、1–65535整数端口及适用范围，不猜测配置。用户多选视觉模型、任务更新、外部通知；内部scope为`model`、`task-source`、`notifications`，不预先勾选。

请求按已保存的配置与范围决定路由，未保存草稿不改变路由。保存只提交配置，不自动测试、访问网络、重试或扩大代理范围；显式原型测试同样为内存模拟。本功能是助手相关服务的请求路由，不创建系统 VPN，也不接管游戏或其他 App 的网络。

代理凭据私有，改变目标不能串用旧凭据；不能进入公开快照、URL或导出。正式Android 传输实现、HTTP／SOCKS5 兼容及手机／模拟器环境需要后续验证；不把设置页面存在当作真实代理已生效。

### 6.3 游戏生命周期、账号归属与开机

游戏启动、强停或登录态提取前，宿主先暂停执行队列，等待独立输入通道确认旧输入静默，再推进生命周期操作。游戏会话模块拥有游戏／身份阶段，不拥有调度器；它不能直接恢复队列或取得输入所有权。身份核对待完成或失败时，宿主拒绝继续托管。

已接受专用Root环境的受控快照验证路线。正式提取须先验证游戏停止与数据静默；恢复前保留可回退状态，并核对同设备、渠道和游戏版本。保存成功不等于可恢复，恢复本地状态不等于已进入预期账号；启动后必须新观察核对UID、区服和渠道。错误匹配不放行，回退也需要核对原身份。存在未决消费结果时拒绝跨账号启动，不通过换号清除证据；沿用当前账号启动可帮助核对旧结果，但本身不解决unknown。

用户已确认：**只在新身份核对成功且账号实际改变后，清空全部旧未结束执行项；新账号重新添加任务。** 历史与unknown记录保留，不能将移除写成完成或已确认失败。恢复失败、错误身份或回退不清原队列。整个过程保持人工暂停，成功后也由用户继续，不隐式恢复旧项。清理的是执行队列，不是删除本地任务／计划定义。

每个新执行项只锁定`accountBinding`中的opaque key与显示名，供宿主核对归属；不接收登录态字节、token或快照句柄。身份归属不能因换页面或修改选择而改写在途快照。

定时计划按账号隔离：创建／保存时锁定所属账号，编辑已有计划不自动改绑；计划列表和工作台“下次计划”只展示当前账号计划。换号保留旧账号计划配置，新账号需重新创建自己的计划。旧计划到点提交仍锁原`accountBinding`，等待匹配账号，不借当前新号执行，不自动切号或补做；原型只演示到点事件，不运行真实定时器。

删除本地登录态快照不删除该账号的计划或历史。任务结果、最近结果和完成摘要按当前账号读取，不能把A账号完成显示成B账号完成；历史记录保持全局并明确标注账号来源，供跨账号追溯。

助手开机自启偏好默认false。开机恢复只初始化助手并等待授权与账号核对，不自动解锁、拉起游戏、切账号或恢复托管；既有人工暂停仍由宿主维护。系统授权或执行桥需要重新检查，不能沿用上次进程的验证结果当作当前证据。

本轮只有内存占位状态机及元数据；Root能力、已登录A／B、新身份核对和boot事件均由设备框外评审工具模拟，不是正式产品绕过权限的入口。本机虽已发现可执行 ADB，本项目尚未连接 Android 目标环境，也没有实际提取、写入或恢复登录态；不承诺免登录、跨设备迁移或已通过真实Root验证。官方边界及待执行实验见[游戏生命周期与账号边界](design/game-lifecycle-account-boundaries.md)。

## 七 完整产品验收框架

后续每期按实际交付能力验收，并累积到同一份能力与环境矩阵：

1. 功能覆盖：逐项核对实际游戏结果、支持条件、周期和资源影响。
2. 模型开关：独立验证无模型可用范围和模型增强范围，包含运行中失效。
3. 跨主题：同一任务测试多套实际不同的主题，并单独评估未专项适配主题。
4. 自主活动：使用未预写专用流程的活动场景，记录专用修改、人工介入和真实结果。
5. 长期运行：在支持的安卓真机与 Windows 安卓模拟器代表环境分别实测至少 24 小时，覆盖等待、切换和中断。
6. 资源与御魂：核对限额、素材、保留规则和结果未知时的处理，包含强化整理联动。
7. 可控性：检查游戏执行期间与助手页面内的暂停、停止及接管行为。
8. 环境生命周期：验证授权拒绝／撤销、系统中断、游戏退出及恢复条件。
9. 通知：验证唯一管理入口、11项默认关闭规则、触发事实与渠道订阅分离、无订阅事件留存；测试渠道不保存也不生成业务事件，投递失败不影响执行或清除异常。推荐阈值需与生产验证区分。
10. 悬浮球：验证各状态、拖动点击、展开收起、暂停停止和异常入口，覆盖屏幕方向、真机及模拟器输入；确认不干扰识别与游戏操作。
11. 主 App 横屏：覆盖工作台、任务中心、托管计划、消息记录、设置及关键详情／表单；从横屏游戏切回、布局切换和导航后无需旋转屏幕，内容和控制可读可达，任务状态、草稿和当前页面上下文不丢失。
12. 立即执行：任务与计划均可从主 App 和收藏快捷入口发起本轮运行，不修改既有日程；有其他运行时进入队列，同命令重复提交保持幂等，未配置及资格不足反馈实际原因，不创建并发游戏操作。
13. 模型预设：普通路径只需选择服务和填写密钥，有真实官方获取指引；区域、鉴权、图片能力或额度不满足分别反馈；高级自定义可达且不混入普通必填项。
14. 悬浮常用项：任务与计划通过列表行常用星标控制悬浮显示，不另设管理页，入口引用最新有效规则；执行、暂停和继续只作用于正确的关联运行，不串任务、不改变计划日程。
15. 异常配置：按问题定位相关配置，修正后不无依据宣布已修复或重试消费；无配置解法的异常如实说明，不提供无效“处理”按钮。
16. 场景过滤：常用开关不变时，切换游戏画面可更新悬浮候选；区分确定不可开始与识别未知，切换期间不沿用旧判断；正常导航可达的任务按其前置条件判断；当前运行控制始终可达。
17. 用户与开发诊断分层：普通主界面不展示支持矩阵和过滤原因；需要用户操作的授权／密钥／规则问题仍有明确入口；开发者模式诊断不扩大执行权限或自动外发数据。
    开发者可在App内用动作编排步骤／任务及配置schema，生成JSON、调试并定位错误；明确上传后直接形成可拉取新版本，不增加云草稿／发布按钮，不替消费者启用。验证制作复杂度及调试与托管的输入隔离；旧原型测试不覆盖新增能力。
18. 简洁性：点任务直达同页配置、详情无多余返回底栏；工作台与悬浮当前运行行直接暂停／继续；暂停后不放行新的并行运行；未知消耗优先核对；悬浮当前控制不重复；获取密钥直达官方；通知按类型展示字段。
19. 云任务容器：任务目录和定义可独立获取与更新，稳定 ID 保留常用、计划引用和规则；区分首次无缓存、缓存可用、获取失败、待启用与容器不兼容；当前运行使用绑定版本且不被更新替换。验证任务更新不需要每次升级 APK，同时明确需要新容器能力时的升级路径。
20. 适合场景的输入：有界滑块和精确数值同步，次数／预算可精确录入，时间与日期使用对应选择器；范围、步长、单位及时间语义明确，校验失败不静默截断或改值，横竖切换保留草稿。日期控件支持不等于新增日期调度行为。
21. 版本管理：启动只触发本次最新版拉取，导航和旋转不重复触发；手动可获取版本及对应 changelog，已有版本不重复安装；拉取不覆盖指定使用版本。选择旧版本后新运行绑定该版本；删除历史不丢用户数据，占用版本显示原因，失败／中断／不兼容不替换完整可用版本。

22. 调度状态：验证整计划求和、严格高优抢占与步骤级恢复、平级顺序、快照锁定、到点与命令幂等、手动暂停／停止全队挂起、继续跳过完成步骤、重新开始仅重做当前任务且保留计划已完成成员、继续前重新核对、确认失败继续及部分失败结果、未知结果不被误清。
23. 队列移除与等待通知：工作台横竖屏均可查看与右滑移除，当前卡死项可经独立输入撤销后继续后续项，迟到事件不复活；等待通知遵循设置阈值与渠道订阅，投递失败不影响调度，不因提醒自动取消或重试。

24. 设置与历史：模型原生服务商下拉、按需配置及具名新增，各服务草稿／凭据隔离；历史仅通知／运行两标签，横屏左标签右内容，异常详情仍可达。

25. 网络设置：验证HTTP／SOCKS5、可选认证、空范围直连及已保存范围路由；保存不测试、不发网、不自动重试，不产生系统VPN。

26. 游戏与账号：分清能力未知、普通启动与Root受控强停／提取；静默前不推进，保存为未验证，恢复须新身份核对，错误匹配与回退不放行；操作依赖快照不可删除。

27. 账号与队列／开机：仅成功核对身份实际改变后清空旧未结束执行项，保留历史与unknown，失败／回退保留原队列且始终hold；run只含账号归属元数据。自启偏好不隐含游戏启动、解锁或托管恢复。

28. 账号隔离：已有计划编辑不改绑，列表／下次计划及任务结果摘要按当前账号；旧计划到点锁原账号并等待匹配，不自动切号或补做。删除快照保留计划／历史，全局历史标账号来源。

具体样本、性能和成功率门槛由方案及目标环境验证后确定。截图测试、模拟测试、真机／模拟器实测分别报告；功能菜单存在不能代替交付证据。

## 八 确认顺序与分期方法

五个主入口、六类业务与完整功能方向作为本轮基线。此次评审聚焦原生布局、简洁操作、云任务容器及输入控件；真实通知协议及重复／静默策略、资源操作与自主活动细则仍需分别细化；当前悬浮形态和视觉以 UI v5 为基线，未声明的手势不自行补充。

用户已认可整体方向并授权启动三个独立子 agent。三者以同一版蓝图为输入：架构负责职责和状态所有权，技术方案验证实现条件，UI 将信息架构细化为完整页面与交互。主 agent 汇总冲突和验证风险。

[旧低保真交接说明](prototype/README.md)保留 30 个页面／状态及导航关系作为范围资料；其排版与悬浮球视觉未通过评审。本轮已参考真实 App 结构重新覆盖完整页面，旧稿不直接作为最终布局基线。独立方案为[系统架构](design/system-architecture.md)、[技术方案](design/technical-plan.md)及[App v2 交互交接](design/app-v2-design.md)，此前[旧 UI 设计](design/ui-design.md)仅作历史对照。视觉调整不自动批准新的执行行为。

当前设计见[UI v5](design/ui-v5/index.html)及[交付索引](design/README.md)，[App v2 原型](prototype/app-v2.html)保留作历史交互资料，需求覆盖见[复核矩阵](design/reissue-requirements.md)，参考见[原生交互研究](design/native-interaction-research.md)及[assttyys 源码对照](research/assttyys-floating-layers.md)。当前悬浮结构已收敛为“小球 → 快捷层 → 常用列表”，不再并列三套方案。此前[局部原生草案](design/native-ui-preview.html)、旧三方案和低保真只作历史对照。

随后制定分期清单，顺序建议为：关键可行性验证 → 可实际使用的任务闭环 → 任务覆盖扩展 → 自主活动能力逐步增强。Android 截图与操作、跨主题和新活动能力应提前验证，不能到最后一期才发现核心方向不可行。

该顺序只是交付组织建议，当前不把任何已提出功能自动分配到某一期。每期需写明交付任务、前置依赖、用户可用闭环、验收和未覆盖范围，再由用户确认。

## 九 尚未纳入的扩展与待决事项

本地游戏账号登录态快照管理与指定账号启动已纳入。多设备协同、远程控制、云端账号体系、云端快照备份／迁移、付费订阅、任务社区和插件市场均未获确认，完整形态不因“完整”而自动扩展到这些功能。通知渠道配置与异常告知已纳入；通过通知渠道远程下发游戏操作不在本次新增范围内。

需要继续细化的产品决策包括：完整逐项任务行为规格、商店和领取周期、御魂规则与操作、自主活动范围、日程时区／错过／重叠及停机期间定时触发策略、真实通知协议及重复／静默策略、云端预算和记录留存。任务模型、唯一执行器、两种恢复方式、队列优先级、三层悬浮和 UI v5 已有明确约定，不将其整体重新列为未定。优先确认功能与流程，具体数值和默认值在对应方案可评估时补齐。

当前进行产品原型与方案设计，不编写生产应用、操作真实账号或发布部署。[设置收敛与验证](design/settings-convergence.md)记录原型实现及核对；网络设置的已确认交互与实际验证状态以该交付记录为准。原首期 PRD 的具体任务描述与验收条目作为需求资料保留；与本稿冲突时，以本稿为准。


### 2026-11-16：App 重新打开后的执行恢复

用户已明确选择：App 被系统杀掉后重新打开，自动恢复可确认安全的任务；结果未知时仍暂停核对。既有人工暂停不因重新打开而解除。恢复沿用原轮次、任务版本、配置与完成步骤；未完成步骤从入口重新观察，停机期间的定时补做策略仍单独确定；桥连接恢复或超时不能作为旧输入静默／业务成功的证据。实现仍需实际输入与账号核对证据；本条确认产品行为，不代表已通过进程恢复实测。
