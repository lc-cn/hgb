# 开发模式：手机采样调试 + 电脑编辑发布

日期：2026-11-20。状态：总体方案和下列三项已由用户确认（草稿存服务端；第一期就做步骤与动作的可视化编辑；开发者资格为任务仓库写权限），页面待画设计稿确认，未实现。取代 `developer-task-authoring.md` 和 `ui-v3/developer-design-notes.md` 中“全部在手机上编辑”的部分；GitHub 授权、上传即发布、调试与托管不并发这些既定原则不变。

## 为什么要融合

做寄养任务时，开发者大部分时间花在下面几件事上：

| 环节 | 实际在做什么 | 在哪做更好 |
| --- | --- | --- |
| 采样 | 在游戏里走到某一页，留下原图和识别结果 | 手机：就在游戏里，原分辨率，不用切走 |
| 标注 | 框出文字区域、裁模板、量偏移 | 电脑：大屏、鼠标 |
| 定义页面状态 | 几个状态要互斥，否则谁都确认不了 | 电脑，并且需要工具当场判定 |
| 编排步骤 | 动作的顺序、分支、循环；任务里步骤的顺序 | 电脑 |
| 试跑 | 在真游戏上跑草稿，看每一步 | 手机执行，两边都能看 |
| 查失败 | 截图 + 每个状态差在哪一条 | 电脑看详情；手机能当场重新探测 |
| 发布 | 校验、版本号、更新说明 | 电脑（手机也可以） |

所以不在两条路里选一条，而是让**同一份草稿在两端流转**：手机负责“看得准、跑得真”，电脑负责“改得快、看得全”。

## 总体结构

```text
           ┌──────────── 服务端（草稿、样本、试跑记录）────────────┐
           │                                                        │
 网页工作台（电脑）                                         App 开发模式（手机）
  编辑任务/步骤/配置项                                       悬浮球「采样」「探测」
  在样本上框区域、裁模板、判定状态互斥                        草稿列表、试跑、单步、暂停
  发起试跑/探测 → 选一台在线手机 ───── 现有云端通道 ─────→   同一个执行器执行草稿快照
  看时间线：每步结果 + 截图 + 失败原因 ←── 实时回传 ──────   失败自动附截图和本机原因
  校验 → 版本号/更新说明 → 发布到任务仓库 Release
```

- **草稿存在服务端**，和账号绑定（与“游戏账号、计划、记录存服务端，窗口只执行”的定稿架构一致）。手机和网页打开的是同一份，按节点合并编辑；离线时手机能用最后同步的快照试跑，但不改草稿。
- **执行只有一个**：试跑走现有执行器和云端通道，和托管作业互斥；作者发起试跑前，若手机正在跑托管作业，网页提示等待或停止，不抢输入。
- **发布只有一个出口**：校验通过才能发布；发布前检查草稿用到的动作，标出需要的最低 App 版本（例如 `screen.dragRegion`、`task.result`），避免旧 App 整包拒收。

## 手机端做什么

1. **悬浮球采样**：在游戏里点悬浮球「采样」，当前画面连同整屏识别结果存进当前草稿的样本库（上传服务端）。不离开游戏、不切 App。可连续采多张，给每张起名（如“寄养-好友列表”）。
2. **悬浮球探测**：对当前画面跑草稿里某个“页面状态”或整步的判定，悬浮球上直接显示“成立 / 差在哪一条”。这是今晚调试最缺的东西。
3. **试跑与单步**：开发模式里打开草稿，可以运行整个任务、某一步，或“走一步停一下”；暂停、继续、重新开始沿用执行器现有命令。运行时悬浮球显示当前步骤。
4. **本机记录**：试跑的每步记录、失败截图、带识别文字的本机原因都在手机上可看；上传到服务端的只有不含他人文字的部分（与本次 `why` 的处理一致）。

手机上**不做**大段编辑。可以改配置项的测试值、改某个数值（如等待时长）后立刻再试，这类小改直接写回草稿。

## 网页端做什么

1. **任务与配置项**：任务名称、分类、配置项（单选、多选、数字、开关……带“推荐值”），旁边实时预览用户看到的设置页。
2. **任务编辑与步骤编辑**：沿用“动作形成步骤，步骤组合成任务”（`action-step-task-model.md`）。任务编辑页只排步骤：每个步骤写明从哪个画面开始、到哪个画面结束、怎样算完成、读哪些配置项、运行条件；可新建步骤或从**步骤库**（同一游戏的公共步骤，如进庭院、回庭院、关奖励弹窗）引用。步骤编辑页排动作：左侧常驻 App 的动作目录，中间是带编号的动作编排，分支、循环是步骤里的编排写法，用带竖线的槽位表示嵌套，每条路径末尾标出是否核对过画面；右侧是选中动作的属性，每个输入三选一（前面动作的产出、配置项、写死），失效的产出变灰并说明原因。“找字并点击”这类常用写法一次插入两个普通动作，不另造概念。规则见设计稿“⓪ 规范”。
3. **样本标注**：打开手机传上来的样本，图上叠加识别到的文字框；拖框生成区域（自动换算到 2400×1080 参考尺寸）、框选生成模板、点两个元素量偏移。
4. **状态判定台**：一个“页面状态”写好后，立刻在所有样本上算一遍：哪些样本成立、哪些样本同时满足多个状态（不互斥会标红）、差在哪一条。今晚的“确认框带问号”“两个状态同时成立”在这里写的时候就能发现。
5. **试跑时间线**：选在线手机发起试跑，网页上按步骤显示每个动作的结果、用时、截图和原因；失败那一步可以一键“在这张截图上重算状态”。
6. **发布**：校验（引用、互斥、资源、最低 App 版本）→ 版本号、更新说明 → 发布。

## 数据与接口（概要）

| 对象 | 说明 |
| --- | --- |
| 草稿 | 任务集工作区：从当前发布版本复制而来，含全部任务、片段库、资源；编辑按节点 id 打补丁合并 |
| 样本 | 图片 + 整屏识别结果 + 采集时间/设备/名称；只属于作者，不随任务发布 |
| 资源 | 模板图（从样本裁出）、识别模型引用；发布时打进任务包 |
| 试跑 | 一次试跑 = 草稿某修订的快照 + 目标手机 + 范围（任务/步骤）；记录每步结果，回传截图有数量上限 |
| 云端命令 | 新增“探测”“试跑草稿”两类，复用现有作业通道、租约和互斥；只有对任务仓库有写权限的 GitHub 账号能发 |
