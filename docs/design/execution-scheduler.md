# 任务步骤 计划执行与队列调度

版本：0.2<br>
日期：2026-11-15<br>
状态：本轮状态机与可运行模拟的设计契约，不是已部署的 Android 调度器。

最新恢复口径：用户已确认按步骤恢复，不实现动作中途续跑；已完成步骤跳过，未完成步骤重入。支持显式重新开始当前任务，计划内已完成成员保留。原动作结果、消耗与unknown须保留核对；具体简化架构见[系统架构1.0](system-architecture.md)。下文检查点只用于表示已完成步骤与恢复核对依据，不扩大为通用中途快照机制。原型尚未提供重新开始命令。

控制归属补充：暂停属于唯一任务执行器；继续／重新开始当前任务只是执行器恢复时的两个动作。下文较早的 PlanRun／执行项状态描述不能据此引入任务或计划各自的暂停／恢复状态机；计划提交批次仅保留排序、去重、成员顺序与事实汇总，状态由关联任务和执行器派生。具体简化模型以系统架构1.0为准，全队人工暂停和已确认的整计划合计优先级仍保留。

本稿落实用户最新纠正：任务是具体操作步骤集合，计划是任务集合及何时执行；支持完整队列、定时到点入队和高优先级安全抢占。以本稿替代旧设计中“忙时仅提示冲突、是否排队待定”的部分。来源、任务包、资源与结果契约继续沿用[系统架构](system-architecture.md)。

## 一 已确认语义

1. Task 包含完成一个具体业务操作的步骤，例如领取、悬赏、放卡。步骤的观察、输入、结果核对和检查点属于任务。
2. Plan 包含有序 Task 成员及执行时间。计划内保持用户编排顺序，不因子任务优先级重新排序。
3. 全局执行项为一个独立 TaskRun 或一整份 PlanRun。入队、优先比较、抢占、恢复和取消都以执行项为单位。
4. PlanRun 的 priority 为其锁定成员 task priority 之和，整个本轮保持不变。正在执行哪个成员、完成了几个成员不改变该总值。
5. 新候选只有 priority **严格大于**当前整项才可触发抢占；平级按稳定入队次序执行。
6. 自动抢占在可恢复安全检查点、旧输入已静默后交接，之后恢复原执行项的任务、步骤与进度。
7. 用户手动暂停或停止都暂停整个队列，等用户继续。期间可入队，但不能发出任何新的游戏输入。
8. 手动停止额外取消当前执行项，保留其他排队／自动挂起项；停止计划只是取消这一轮，不删除未来日程。
9. `manual_hold` 与 `preempted` 不同：前者只有用户继续才解除，后者是调度器可自动选择的恢复候选。
10. 已确认失败记录后自动继续后续任务，不自动重试。PlanRun 的成员失败不阻止按原顺序处理后续成员；整轮结果如实汇总，不能显示全成功。
11. 工作台展示实际执行队列，支持右滑移除等待、挂起或当前执行项；当前项移除后，在输入静默和结果安全条件具备时继续其余队列。
12. 排队过久未执行需要通知，等待阈值由设置决定；告警本身不取消、提权、重试任务或阻塞调度。

数字只用于演示：A 包含 task10 与 task20，总 priority 为 30；即使 A 当前正在做 priority10 的成员，B25 也必须等待。数值生产范围、缺省值、上限和优先级编辑来源仍待确认，不将示例冻结为默认值。

## 二 单一事实源与数据契约

队列调度器是运行、排队和抢占的唯一所有者。页面与悬浮球读取同一快照，不能再保留一个可独立修改的 `state.run` 或在 UI 中另写队列规则。

| 对象 | 最少语义字段 |
| --- | --- |
| TaskDefinition | taskId、步骤定义与稳定 stepId、priority 字段语义与约束、前后条件、可恢复检查点、所需能力和资源影响 |
| PlanDefinition | planId、有序成员 taskId、每日／指定星期与时间规则、配置版本；不另存可与成员总和冲突的计划 priority |
| Occurrence | scheduleId、稳定 occurrenceId、应到时刻与时区依据、生成时的计划配置版本、入队结果 |
| ExecutionItem | runId、kind=task/plan、实体引用、来源 commandId/occurrenceId、稳定 admissionSeq、锁定 priority、workerGeneration、取消原因、生命周期、资源与结果状态 |
| ExecutionLock | Task／Plan 及全部成员配置、成员 priority、原任务编排、参数 schema、包及资源依赖的不可变版本集合 |
| TaskCursor | 本执行项中的成员位置、taskId、stepId、步骤阶段、最近检查点、实际结果与未决动作引用 |
| Checkpoint | 逻辑业务阶段、观察依据、对象身份、资源账、已完成步骤／动作、恢复前提、工作流和规则版本；不是截图坐标缓存 |
| SchedulerSnapshot | queueMode、调度阶段、activeRunId、待交接／移除原因、当前或待撤销输入所有者及代际、所有未终结执行项、待验证／阻塞原因 |
| QueueWaitObservation | runId、入队时刻、首次开始／挂起等事实、观察时刻、等待阶段与设置版本；不以 UI 挂载时间计时 |

同一顶层 ref(kind,id) 尚有未结束执行项时不得重复入队，包括等待、手动暂停和自动挂起；独立点击、不同 commandId 与定时 occurrence 均不能绕过此约束。相同 commandId 或 occurrenceId 的重投还须按幂等合同返回原处理结果。顶层独立任务引用与计划内成员实例分开：同一 taskId 可被不同计划引用，不用成员 taskId 的全局唯一键误吞整份计划。结束或移除后，新的独立提交可再次入队。

有效任务 priority 由同一份已保存任务配置解析，提交时冻结到执行锁；不同时维护另一个可与用户配置冲突的可变分值。TaskDefinition 声明字段语义，具体生产范围／缺省仍待确认。计划只是对所引用有效值求和。

已知定义但包资源或能力暂缺的到点执行项仍可保存入队事实与明确版本引用，标记受阻而不发输入；缺少 priority 或配置不能用 0／当前 latest 兜底执行。如何补齐缺失配置保留为明确操作和条件变化，不等于自动重试已经失败的游戏步骤。

## 三 三组状态必须分开

### 3.1 队列模式与调度阶段

`queueMode`：

- `running`：允许调度器在条件满足时分配唯一输入权。
- `manual_hold`：用户主动接管游戏，禁止任何新游戏输入；排队、时钟记账及状态展示仍可进行。

调度阶段独立为 `idle / selecting / executing / quiescing / validating_resume / blocked`。例如队列可处于 `manual_hold + quiescing`：禁止新输入已经生效，但旧平台手势是否结束仍待确认。错误导致的 blocked 不冒充用户手动暂停。

### 3.2 执行项状态

| 状态 | 意义与后续 |
| --- | --- |
| queued | 已接收入队，尚未获得本轮输入权 |
| running | 当前执行项拥有输入权，在已锁定步骤中执行 |
| suspending | 已提出自动抢占，正在取得检查点并等待旧输入静默 |
| preempted | 因自动抢占挂起，检查点已保存，可参加后续恢复排序 |
| manual_paused | 用户暂停的原执行项保留检查点；manual_hold 解除前不能自动恢复 |
| resuming | 已选为候选，正在新观察、对象和结果核对，还不能发游戏输入 |
| cancelling | 用户停止当前项，已禁止新输入，正在确认在途动作与取消结果 |
| blocked | 缺少能力、条件、核对结果或所需策略；原因单独记录 |
| completed | 本执行项全部目标按实际证据完成 |
| partial_failed / failed | 整份计划有成功与确认失败混合时为 partial_failed，全部失败或计划本体准备失败时为 failed；独立 TaskRun 有确定失败依据时 failed。不代表未知结果或自动重试许可 |
| cancelled | 本轮意图取消，保留已经发生的消耗和未知结果；不取消未来 schedule |

状态可以有恢复来源字段，但不复制同一项到多个可变队列中。queued、preempted 与可恢复的 manual_paused 是同一执行项集合中的不同状态，不额外建立互相失配的“恢复栈”。

### 3.3 步骤与业务结果

步骤阶段至少区分 `not_started / observing / intent_recorded / input_in_flight / verifying / checkpointed / completed / blocked / failed / cancelled`。阶段与 `verified_applied / verified_not_applied / unknown` 结果分开。

执行项被停止或抢占不能把已经发出的兑换改成“未执行”。已取消执行项也可以留有 unknown 动作，后者继续占有必要资源保留与包引用，不能因不再调度该项就删除。

### 3.4 核心状态转换

| 事件与当前条件 | 状态转换与输入约束 |
| --- | --- |
| 新项／到点事件入队，manual_hold 中 | 新项 queued 或明确 blocked；hold 不变，无输入 |
| 新项入队，空闲且队列 running | selecting → 新观察与条件核对 → running；未核对前无输入 |
| 候选 priority 小于或等于当前整项 | 当前继续，候选保留 queued；平级保持 admissionSeq |
| 严格更高候选出现 | 当前 running → suspending；旧项仍持权，候选无输入 |
| 安全检查点与旧输入静默均成立 | 原项 preempted，撤销旧代际；重选并核对候选后授予输入权 |
| 自动恢复 preempted 项 | resuming → 新观察／检查点核对 → running，不回放旧坐标 |
| 任意非终结阶段手动暂停 | 立即 manual_hold，当前转 manual_paused 或保留在途核对；禁止后续游戏输入 |
| 任意阶段手动停止 | 立即 manual_hold，匹配的当前项 cancelling → cancelled；其他项与日程保留 |
| 移除非当前等待／挂起项 | 指定项取消，其他 owner、hold 与未来日程不变，不等待无关 worker |
| 移除当前项 | 撤销旧 worker 代次；无输入／unknown 风险时取消并继续，否则等待独立输入通道静默或结果核对；不新设或解除 hold |
| ContinueQueue | 解除 hold，validating_resume；核对后统一排序选择，不立即发输入 |
| 当前任务步骤确定完成 | 保存证据并推进相应步骤；任务结束后按成员顺序或全局队列继续，仍受 hold 约束 |
| 成员确定失败 | 保存失败，结束该成员剩余步骤，计划按原序继续；不能自动重试或改变整项 priority |
| 独立项／计划本体确定失败 | 记录 failed 后选择后续就绪项；若 hold 则只记录，不调度输入 |
| 任意副作用结果 unknown | 保留动作与资源，阻塞依赖核对路径；不进入确定失败后重做分支 |
| 交接／完成／模型回调晚到且已 hold／取消 | 只接收仍匹配身份的事实，不能重新授予输入权或解除 hold |

## 四 入队 优先级与定时

### 4.1 入队与版本锁

人工立即执行与计划到点都先创建 ExecutionItem，不绕过队列直接调用手势。接收时锁定已保存配置、包版本、计划成员顺序与全部成员 priority；后续普通编辑和任务包下载不改变既有项的排序或步骤含义。

计划优先级为全部锁定成员 priority 的和，不随剩余任务减少。同一独立任务或同一计划同一时刻最多有一个未结束执行项，以kind + id识别；完成、失败或移除后的新运行有独立锁，不能回写过去项。

入队使用唯一 admissionSeq；读取、刷新页面、挂起或恢复不重新编号。可排序项按 `priority 降序 → admissionSeq 升序`。不增加 aging、随等待时长加分、超时丢弃、默认重试或随机顺序。

### 4.2 定时 occurrence

保存有效的每日／指定星期、时间和成员任务后，计划按该配置产生应到事件。保存本身不立即插入一次人工执行；手动“立即执行”是另一个有 commandId 的请求。

Occurrence 所有者为每一个应到事件生成稳定身份；幂等键为 `scheduleId + occurrenceId`。重投、时钟重复检查或进程恢复返回原入队结果，不能多插一轮。配置版本保存在 occurrence 与 ExecutionLock 中，但不能仅因重读到新配置版本就将同一个已生成事件当作新的发生。

manual_hold 期间到点照样记录和入队，不能通过到点事件解除 hold 或发输入。一个计划前一轮尚未结束时，下一轮事件仍有独立发生事实，但不得重复创建同一计划的队列项；入队返回已有项冲突。是否延后提交或如何处理错过的发生事实仍待确认，不能擅自实现补做或静默当作执行成功。

游戏时区、系统时钟变化、重启期间错过时间及修改日程后当期事件映射需使用明确规则；当前不新增补做、跳过或期限默认值。

## 五 自动抢占与嵌套恢复

### 5.1 抢占判定

有就绪候选且其整项 priority 严格大于当前整项时，登记抢占请求。平级不抢占，低级不抢占；不能拿当前 PlanRun 的子任务 priority 比较。

候选“就绪”必须满足能力、版本、资源和可达前提；priority 很高不使未知消费、无截图或未授权动作变成可执行。被阻塞项保留其真实 priority 和原因，不假装低优先级。

### 5.2 安全交接

1. 原执行项保持唯一输入所有权，不给候选发出并行点击。
2. 按任务预定义的可恢复单元取得检查点，核对已提交动作并等待输入静默。不能为了交接执行未定义的额外消费或跨入无关任务。
3. 持久化 TaskCursor、检查点、资源账和 ExecutionLock，使原项进入 preempted。
4. 撤销旧输入代际与所有权，再从当前仍就绪的候选中重新选最高整项，验证后授予新所有权。

等待交接期间候选可能取消或出现更高项，交接完成时按最新就绪集合选择，不能执行过时的目标请求。若出现 unknown 副作用，原项保留核对阻塞及资源引用，不把它当作失败重放；其他项仍须独立满足资源与游戏状态前提，不能借确认失败后的继续策略绕过未知核对。

如果当前任务没有已定义的安全恢复点，就无法声称可以任意时刻抢占。应等待它的可恢复点或如实说明受限，不用强制杀步骤伪造“恢复原步骤”。具体哪些步骤可恢复由任务工作流定义并验证。

### 5.3 恢复排序

新 queued 与 preempted 项统一按 priority 降序、原 admissionSeq 升序选择，不在高项完成后无条件弹回某个恢复栈顶。这样嵌套抢占也保持统一规则，未终结原项不会丢失。

示例：L30 被 H50 抢占，H50 又被 X80 抢占；X 完成后若无更高就绪项，先恢复 H50，随后恢复 L30。若此时有 N60 就绪，则先 N60，再 H50，再 L30。数字只作排序夹具。

恢复保留原 runId、计划成员位置和 stepId。若原步骤尚未发动作，则新观察验证后继续该步骤；若交接前已核实完成步骤，则从其后置检查点继续下一步骤。不得从任务开头重跑，也不能为坚持同一 stepId 而重复已核实的消费。

## 六 手动暂停 停止与继续

### 6.1 manual_pause

接收用户暂停命令时，先在同一串行命令处理中将 queueMode 置为 manual_hold，并关闭全局发输入门，再处理当前执行项检查点。不能先自动启动别的项，或用“返回庭院”之类游戏输入完成暂停收尾。

当前项进入 manual_paused；在途输入及未知结果继续单独核对。平台已经接受的手势无法由本地标志撤销，需明确展示尚未静默；在此期间不会提交新的输入。未获得静默确认不能声称整个游戏已安全可接管。

没有当前项时也可将队列置为 manual_hold。新用户请求或定时事件可以入队；队列不因新项、模型回复、资源恢复或任务包更新自动继续。

### 6.2 manual_stop

停止同样先置全局 manual_hold。然后取消命令所指的当前执行项，保留所有其他 queued／preempted 项与未来日程；PlanRun 被停止时取消本轮剩余成员，不把这些成员自动拆成独立执行项。

停止命令携带预期 activeRunId。若实际当前项已变，仍先兑现用户要求的全局 hold，但不能误取消另一个 run；返回目标冲突供 UI 展示。未决动作与资源记录保留，取消不代表消费回退。

### 6.3 ContinueQueue

只有明确用户继续命令解除 manual_hold。恢复先取得新观察并核对检查点、目标对象、剩余资源和版本；验证前输入门不放行，不能拿旧坐标直接点击。

按照通用优先级规则的设计解释：继续不是给旧项额外的恢复优先权，而是恢复队列调度；从已就绪的新项和可恢复挂起项统一按最高整项 priority 选择。hold 期间到达的较高项可先执行，旧项仍保留检查点，之后按规则恢复。不要求用户再选一次执行项。

这属于对已确认通用排序的明确解释，不是声称用户逐字指定了新的默认值。手动挂起项参加自动选择必须发生在此次 ContinueQueue 授权之后；manual_hold 仍在时绝不自动恢复。

### 6.4 右滑移除队列项

工作台的队列来自调度器快照，右滑提交 `RemoveQueueItem(commandId, runId)`，不由 UI 直接 splice 可见数组。命令幂等：重投返回同一取消结果，不能重新取消别的项；已经移除的 occurrence 和 commandId 保留原记录，不因删行而重新入队。

等待、受阻或自动挂起的非当前项移除不影响另一个当前 inputOwner。当前项也可移除，但需走下述独立撤销与静默流程。取消针对这一轮 ExecutionItem：从后续可选择集合排除，保留取消原因、版本锁、已发生消耗和必要证据。其他项的 priority／admissionSeq、未来日程与已有 manual_hold 均保持。已终结项重复移除返回原状态；引用缺失与已取消分别呈现。

移除与手动 stop 是不同命令：移除不新设 manual_hold，而手动停止保持“取消当前本轮＋全局 manual_hold”。移除也不解除已有 hold；如果用户此前暂停了整个队列，删行后仍须用户 ContinueQueue，不能顺便恢复游戏输入。

为处理卡住的旧任务执行器，dispatcher／Android 输入 Adapter 必须独立于业务 worker。当前移除按以下顺序处理：

1. 幂等登记取消并撤销该 runId 的 workerGeneration／后续输入租约资格；原 worker 不再能提交输入或推进步骤。
2. 从可调度当前项移除业务意图，独立记录是否仍有旧 inputId 在途及其撤销票据。撤销发输入资格不等于平台输入已静默，不能直接清空旧 owner 证据就放行下一项。
3. 无在途输入且没有相关 unknown 安全问题时，结束该项并按既有队列规则自动选择后项；不等待旧 worker 的完成、失败或检查点回调。
4. 有在途输入时，由独立 Adapter／dispatcher 接受匹配撤销票据、inputId 和代次的静默确认，再允许后项输入；不得依赖卡死 worker 自己报告完成，也不得以超时经过替代静默事实。
5. 旧 worker 的 complete／checkpoint／fail、旧模型响应及重复释放租约事件因代次失效被拒绝，不能复活取消项、清除其他 owner 或解除 manual_hold。平台层迟到回执如需保存，仅作为原动作事实，不推进旧任务或重新授予执行权。

如果平台层仍无法确认静默，显示取消待静默／需处理，而不是谎报已安全释放；这不再等待旧业务 worker。真实 Android 停止与静默机制仍须验证，本轮模拟不能证明平台已取消物理手势。

未知消费结果、对象锁和资源保留不随可见队列行消失。若仍有依赖核对的事实，应保留独立问题与证据；不能将它改成失败、重新执行、自动释放预算或解除相应输入阻塞。右滑可以移除调度意图，不能撤销游戏内已发生的动作。

### 6.5 排队等待通知

调度器根据执行项的等待事实产生过久等待事件，由独立通知模块投递。等待阈值取自用户设置及其明确单位／版本，不写入生产默认秒数；阈值尚未设置时如实展示配置状态，不由模拟夹具数字补齐。

需要保留入队、首次执行、挂起、恢复及移除时刻，避免工作台刷新、切屏或排序使等待计时归零。首次尚未执行的排队等待与抢占后的恢复等待分开记录；挂起和 manual_hold 时间是否计入同一提醒、重复提醒及阈值修改对已有项的作用需明确，不因一个阈值字段自动扩展告警范围。

告警事件携带 runId、等待原因、已等待时长及所用阈值设置版本，并与投递状态分开。重复检查同一等待事实应能识别同一事件，不能每帧刷新都发送；再次提醒策略仍由已确认通知规则决定。

通知发送失败、无渠道或渠道结果未知只影响投递状态，不阻塞队列选择、抢占和检查点流转，也不能把任务标为失败。等待超阈值不自动移除、取消、提权或重试任务；用户可查看队列并按已授权手势处理。

## 七 最少命令与事件接口

以下是给模拟器与 UI 共用的语义，不冻结最终函数名或生产语言实现。

| 输入 | 核心效果 |
| --- | --- |
| EnqueueTask / EnqueuePlan(commandId, entityRef) | 创建或返回同一人工执行项；锁定定义、顺序、规则及 priority；不绕过 hold |
| MaterializeDue(scheduleId, occurrenceId, dueAt) | 幂等记录到点并入队；不由 UI 定时器直接点击游戏 |
| ManualPause(commandId) | 立即关全局输入门并进入 manual_hold，保留当前项 |
| ManualStop(commandId, expectedActiveRunId) | 全局 hold，加取消指定当前执行项；其他队列和未来日程保留 |
| ContinueQueue(commandId) | 解除 hold 并开始新观察／恢复验证；统一排序，不立即发旧坐标 |
| RemoveQueueItem(commandId, runId) | 幂等取消等待／挂起／当前本轮；当前项撤销 worker 代次与后续输入资格，不新设或解除 hold，静默安全后可继续其余项 |
| ConfirmRevokedInputQuiescent(revocationId, inputId, generation) | 独立 Adapter／dispatcher 核实旧输入静默；不能由旧 worker 的完成事件替代，也不能释放不匹配 owner |
| ObserveQueueWait(now, settingsRevision) | 按明确用户阈值形成等待告警事实，不进行游戏输入，不等待通知发送完成 |
| ObservationReady / CheckpointReady | 仅接受匹配 runId、stepId、包／配置锁与输入代际的结果 |
| InputQuiescent | 确认旧输入静默，满足检查点条件后才能自动交接 |
| StepOutcome / ItemCompleted / ItemFailed | 记录事实和资源影响，不把 unknown 当作确定失败 |
| Snapshot / Events | UI 只读当前运行、队列、挂起原因、用户 hold、交接与未决结果 |

所有命令串行归约，commandId 重复返回原结果。平台手势完成、云模型响应、通知发送与 UI 点击都不能自行授予输入所有权；只有调度协调器能更换 owner，并在动作发出前再次检查 queueMode、owner 与代际。

本轮模拟接口可将上述语义映射到单引擎 `enqueue / snapshot / manualPause / stop / resume / confirmResume / checkpoint`。`resume` 创建带 reconcileId 的待核对状态，`confirmResume` 只接受匹配 reconcileId 和新 observationId 的确认；由引擎按统一排序选择，不要求 UI 传入偏好的恢复项。UI 的 run、command、queue 只能从该引擎快照只读派生。

## 八 失败 取消与恢复的界限

确定失败、结果未知、条件等待、用户暂停和自动抢占是不同原因。用户已选择“记录失败，自动执行后续任务”：独立 TaskRun 确认失败后结束该项并选择后续就绪项；PlanRun 中某个成员确认失败后记录其实际结果，结束该成员的剩余步骤，按用户原编排继续后续成员。每次继续前仍须具备新观察、资源与输入静默条件，不能因自动继续绕过动作检查。

PlanRun 有成功与确认失败混合时最终为 partial_failed，全部成员失败时为 failed；计划本体在准备阶段确认失败、尚未进入成员时，该执行项可直接 failed 并转向后续队列。整轮 priority 始终是提交时所有成员的锁定总和，不因某成员完成或失败而扣减。已确认失败不自动重试或重新放回队列，也不把后续任务成功覆盖成整轮全成功。

上述自动继续始终服从 queueMode：如果用户已手动 hold，迟到的完成或失败回调只记录结果，不能解除 hold 或启动下一任务。继续任务不等于删除失败证据或未知资源记录。

unknown 时保留动作意图、资源保留、检查点与包引用，不能套用“确认失败后继续”的分支。新高项如依赖同一未决资源或无法确认当前游戏状态，不能绕过核对；其他项只有其独立前置条件实际具备时才属于就绪候选，不能把高 priority 当作越过核对的理由。

恢复中断时重建队列事实、原 admissionSeq、occurrence 幂等记录、ExecutionLock 与资源账。用户明确产生的 manual_hold 要保留，不能进程重启就自动清除；是否自动重新拉起 Android 执行宿主仍受平台与产品策略限制，不能由本稿新增开机运行。

暂停、抢占和等待时间是否计入已有 maxDuration、时长约束达到后如何处理仍需明确。该字段可保留在配置锁中，但本轮不凭架构新增超时丢弃、自动终止或重试规则。

## 九 本轮模拟与后续验收

| 场景 | 应观察结果 |
| --- | --- |
| A=[10,20]，B=25 到达 | A 整项30继续，当前成员10不使 B 抢占 |
| 更高项在安全点前到达 | 先登记交接，未静默前无候选输入；检查点与旧结果核对完成后才交接 |
| 平级到达及多层抢占 | 平级稳定等待；统一候选排序恢复，不重置 runId 或步骤 |
| 人工暂停后高项／定时事件入队 | 队列保留新项，输入数不增加，不自动继续 |
| 人工停止 PlanRun | 本轮取消且全局 hold；其他项及计划未来日程保留 |
| Continue 时有较高候选 | 新观察／检查点验证后按整项排序，旧项不丢也无额外优待 |
| 暂停／停止与交接回调竞态 | 手动 hold 优先约束输入，晚到回调不恢复旧输入权 |
| occurrence 重投／重启 | 返回相同执行项，不重复入队；不同合法发生事件有不同身份 |
| 配置、包或 priority 改动 | 已入队项保留锁；新请求读取之后生效的版本 |
| 消费步骤结果未知 | 不重做、不标为失败；取消或抢占不释放必要证据与资源保留 |
| 成员确认失败与整项准备失败 | 成员失败按原序继续后续成员，整计划汇总 partial_failed／failed；整项失败可转向下项，但 manual_hold 不被回调解除 |
| 右滑等待／挂起项及重投 | 只取消指定本轮，其他 owner 与队列顺序不变；重复命令／occurrence 不把它重新加入 |
| 当前 worker 卡死后右滑移除 | 撤销旧代次；无输入／未知问题时继续后项，有在途输入则独立静默确认后继续，不等旧 worker 回调 |
| 旧执行器或未知动作仍有回调 | 已取消项不恢复输入；静默未知和消费 unknown 保留，不以删行清除问题 |
| 等待阈值与投递失败 | 按用户设置形成可识别事件；通知失败不堵队列，不自动取消、提权或重试 |

本轮可以用可运行内存状态机展示上述事件、队列和输入门约束，但真实时钟唤醒、Android 截图／手势、任务工作流、24 小时运行和真实游戏恢复尚未实施。模拟定时器和“安全检查点”按钮不能证明真实任务具有可恢复点。

待决项：等待告警的计时口径与重复提醒、跨周期重叠与错过补做、日程修改的 occurrence 映射、priority 的生产范围／默认值、时长约束计时及到限行为、真实任务安全检查点、独立静默机制与资源隔离验证。它们不阻止表达已确认的队列及 hold／移除语义，但不能用未审默认值填平。
