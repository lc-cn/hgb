# 护肝宝云端控制方案（2026-11-19 定稿）

产品改名：整体不再叫“阴阳师助手”，改叫**护肝宝**（保护游戏玩家的肝），阴阳师是其中一个游戏。代码和仓库名暂未改。

状态：2026-11-19 定稿。核心概念是**游戏账号管内容，应用只执行**：任务设置、计划和运行记录都属于游戏账号，保存在服务端；计划由服务端计时，到点下发到合适的应用。本文取代同日早些时候的“以云端为准、App 只做执行器”和“设置计划以设备为准”两版方案。第一期实现见[开发说明](../development/cloud-console.md)。本文仍取代 PRD 中“登录态快照只留在本机”的规则。

## 1. 概念

```text
护肝宝账号
├─ 游戏账号（按游戏分组，如阴阳师主号、小号）……… 内容：跑什么、怎么跑、何时跑
│    ├─ 任务设置
│    ├─ 计划（服务端计时）
│    └─ 运行记录
├─ 每个游戏的当前任务版本
└─ 设备（手机、Windows）……………………………… 只管绑定、在线
     └─ 应用 = 执行器（属于某个游戏）………… 只有状态：在哪跑、跑到哪
          手机：阴阳师、阴阳师（分身）、王者荣耀
          Windows：阴阳师 1、阴阳师 2、阴阳师 3
          当前登录的账号、默认账号（可不设）、正在运行的任务、队列
```

- **游戏**：阴阳师、王者荣耀这样的种类。任务版本、游戏账号、步骤库都按游戏分。设备上只出现护肝宝支持并且已安装的游戏。
- **游戏账号**：任务设置、计划、运行记录都挂在游戏账号下，跟着账号走，与在哪台设备、哪个应用运行无关。
- **应用**：某台设备上能独立运行的一个游戏实例，就是一个执行器。手机上一个游戏通常是 1 个应用，系统分身或双开再多一个；Windows 多开几个窗口就有几个应用。每个应用一次只运行一个任务，不同应用可以同时运行。应用可以改名（如把“阴阳师 2”改成“小号专用”），名字只用来显示，调度仍按账号。
- **设备**：一台手机或电脑，用于绑定、在线状态和保活，不直接承载任务。每台设备有一个**同时运行上限**：手机是 1（前台只有一个），Windows 是多开数量。同一台手机上的多个应用共用一条运行队列。
- **叫法约定**：“应用”只指游戏实例；护肝宝自己的 App 在界面上一律叫“护肝宝”，不叫“应用”。文档里提到“窗口”，只指 Windows 系统里的游戏窗口这一实现细节。
- **任务版本**：每个游戏一个当前版本，开发者在 App 里制作、调试后上传，网页任务库选定，设备自动下载（第 5 节）。

## 2. 职责划分

| 能力 | 服务端（含网页） | App |
| --- | --- | --- |
| 护肝宝账号、登录方式、设备绑定 | 负责 | 登录后自动绑定 |
| 游戏账号 | **以服务端为准**：名称、UID、区服、渠道、账号材料、账号锁 | 识别当前账号、保存账号、切号（第 6 节） |
| 任务设置 | **以服务端为准**，网页和 App 都请求服务端修改 | 缓存会用到的账号的设置；断网时只能看、不能改 |
| 计划和调度 | **以服务端为准**，服务端计时，到点分配应用并下发 | 网页和 App 都请求服务端修改；设备只执行下发的任务 |
| 运行 | 下发计划任务和网页的立即运行；转发暂停、停止 | 每个应用一个执行器；本机和悬浮球的运行直接在设备上排队 |
| 运行记录 | 长期保存，网页按步骤展开 | 运行中实时上报，断网时联网后补报；本机只留最近几十条 |
| 任务版本 | 接收上传，存为草稿；每个游戏选定当前版本 | 下载并校验摘要；开发者做步骤、拼任务、调试、上传 |

**为什么这样分**：设置和计划只有一份，在服务端，不用合并修改；计划只由服务端触发，不会有多台设备各跑一遍。代价是断网的设备收不到计划，服务端停机时所有计划都不执行；本机手动运行和悬浮球断网照常可用。

## 3. 连接与通信

```text
网页 ──SSE（服务端推送）──┐
网页 ──HTTP（修改、命令）──┤
App  ──HTTP（修改、查询）──┤
                         服务端 ──WebSocket（双向）── App（设备）
```

- **App ↔ 服务端：WebSocket。** App 登录后建立连接，前台服务保活，断线自动重连（退避重试）。连上后先上报快照：设备信息、已安装的游戏、每个应用的当前账号和运行状态、任务版本。之后有变化就上报增量。服务端靠心跳判断在线。服务端经这条连接下发任务、转发暂停和停止、推送设置变更。
- **服务端 → 网页：SSE。** 只推当前护肝宝账号的数据：设备和应用状态、运行进度、设置和计划变更。先推全量快照，之后推增量。每条事件带递增编号，断线重连时能补发就补发，补不了就重推全量。服务端每 15 秒发一条心跳注释，反向代理要关掉这条路径的响应缓冲。
- **网页、App → 服务端：普通 HTTP 请求。** 修改设置、计划、游戏账号，以及发起立即运行，都是请求服务端。改动后通过 SSE 推给网页，通过 WebSocket 推给相关设备。
- **鉴权**：网页用同域 Cookie（浏览器自带的 SSE 不能加请求头），App 用平台签发的令牌。
- **部署**：第一版只跑一个服务端实例。以后多实例时，需要加消息转发（如 Redis 发布订阅）。

## 4. 调度

### 4.1 计划

- 计划属于一个游戏账号，包含这个账号的任务列表和时间规则，由服务端计时。
- **可运行设备**：默认是所有装了这个游戏的设备，可以限定到某几台。
- **最晚开始时间**：默认到点后 30 分钟，每个计划可以改。超过时间还没开始，这次不执行，记录原因（如“没有可用应用，未执行”）。

### 4.2 分配应用

计划到点或网页“立即运行”（自动分配）时，服务端按顺序找应用：

1. **先找已登录这个账号的应用。** 有在线应用正登录着这个账号，不管它空闲还是忙，都直接推进这个应用的队列，由设备排队执行。
2. 否则找一个**空闲、没设默认账号、游戏支持切号**的在线应用，切到这个账号再运行。当前登录的账号还没保存为游戏账号的应用也可以这样用。
3. 都没有就在服务端等，有应用空出来再下发，直到最晚开始时间。

- **“空闲”的含义**：应用没有在运行，并且它所在设备没到同时运行上限。手机上任何一个应用在运行，这台手机的其他应用都不算空闲。
- **排队任务带账号**：推进队列的每个任务都带着自己的游戏账号。轮到它时，执行器发现应用当前登录的不是这个账号（比如前面有切号任务），就先切号再运行。第 1 步只决定排在哪个应用后面。

- 网页立即运行（自动分配）走到第 3 步时，如果有空闲但设了默认账号的应用，就用它切号运行，结束后切回它的默认账号。计划不会这样做。
- **指定应用**：网页立即运行可以指定设备和应用。应用忙就排在它后面；账号和应用当前登录的不一致时先切号，应用设了默认账号就在结束后切回。
- **账号锁**：同一个游戏账号同时只能在一个应用上运行，跨设备也一样。账号正在别的应用运行时，排到那个应用后面（第 1 步）；指定了其他应用的，等它结束再开始。
- 推进设备队列的任务同样受最晚开始时间约束，超时还没轮到就跳过并记录。设备排队期间断开连接，排给它的任务留在它名下，联网后照常执行；在最晚开始时间之前，服务端不会把它改派到别的应用，所以不会重复执行。
- **实现方式**（第 2 期第②步）：应用的队列记在服务端，服务端每次只把下一个作业推给设备，设备开始一个才推下一个。所以设备断网期间不会开始排给它的新作业，联网后才继续；已经在设备上开始的作业不受断网影响。

### 4.3 下发

- 下发沿用作业租约：带任务、游戏账号、任务版本摘要和该账号设置的快照。设备领取后才开始；超时没领就收回改派。
- 设备那边刚好开始了本机任务、接不了时，拒绝这次下发，服务端改派。
- 设备核对租约里的护肝宝账号与当前登录的一致，不一致直接拒绝。

### 4.4 本机运行

App 和悬浮球里的“运行”直接进这个应用的队列，不经过服务端调度，断网也能用，使用本机缓存的账号设置。运行记录联网后补报。

- **账号锁**：联网时，本机运行开始前也要向服务端拿这个游戏账号的锁，拿不到就提示“主号正在 某设备 上运行”，不开始。断网时不拿锁，照常运行；这时和别的设备撞上的可能性很小，接受这个风险，联网后在运行记录里标出冲突。
- **实现方式**（第 2 期第③步）：联网时“运行”就是让服务端给本机这个应用建一个作业，所以拿锁、排队、运行记录都和网页下发的一样；账号正在别的设备运行时服务端直接拒绝。服务端分配时也守账号锁：别的设备拿着这个账号的作业时，排给本设备的这个账号的作业先等着。断网时直接进本机队列，用服务端上次推来的设置；断网运行的补报还没做。被动触发的任务（看到画面就做的那类）和断网运行都不经服务端，服务端的账号锁管不到它们，接受这一点。同一账号排在别的设备上更早的作业先走，刚跑完的设备不能一直占着这个账号；同一次计划的几个任务尽量分到同一台设备，保证顺序。
- **App 拿到的数据**：服务端经 WebSocket 把这个用户的游戏账号、本设备各应用当前的账号、计划、各账号的任务设置、计划最近一次的运行整份推给 App，连上时推一次，之后每次变化再推。App 存一份，断网时设置和计划只能看。

### 4.5 命令

服务端发给设备的只有预先定义的动作，不能下发任意点击或 shell 命令：

| 命令 | 说明 |
| --- | --- |
| 下发任务 | 计划或网页立即运行，带租约 |
| 暂停 / 继续 / 停止 | 作用于某个应用当前的运行 |
| 设置变更 | 推送某个账号的新设置，设备更新缓存 |

- 每条命令带编号，设备按编号去重。暂停、停止这类命令设备离线或 30 秒内没回执就失败，不排队。
- 设备上报的事件：上线 / 离线、快照、应用账号变化、运行进度、运行结束、命令结果、任务版本同步状态。运行进度限频，每台设备每秒最多一条。

## 5. 任务版本与开发链

**谁能看到“开发”**：App 的“开发”菜单只对开发者显示，没有本机开关。

- 护肝宝账号必须绑定 GitHub（App 用设备码登录，网页用授权登录）。
- 服务端用 GitHub 用户的数字 ID，查他是否是任务仓库 `lc-cn/hgb` 有写权限的协作者。查询用服务端自己的 GitHub App 凭证，不保存、也不使用用户的 GitHub 令牌。
- 通过就给护肝宝账号加“开发者”身份，App 收到后显示“开发”菜单。每次登录和每 24 小时重新核对一次；权限被撤销后身份失效，菜单隐藏，上传接口也拒绝。
- 上传任务版本的接口同样要求开发者身份，不能只靠 App 隐藏菜单。

**开发链**：

1. **做步骤**：在 App 里截取当前游戏画面，框选区域，选“等画面、找图、找字、点击”。“试一下”只识别，不点击游戏。
2. **拼任务**：从步骤库引用步骤，公共步骤（进入庭院、返回庭院、识别当前账号、切换到账号）可复用；设条件和分支；定义设置项。
3. **调试**：在本机直接运行草稿，悬浮面板显示当前步骤、识别区域和最接近的候选，可以重试、单步，或用当前画面回去改步骤。
4. **上传**：只能上传调试通过的任务。服务端校验任务包结构和摘要，存为草稿版本，不会自动启用。
5. **启用**：网页任务库为每个游戏选定当前版本，设备自动下载、校验摘要后启用。开发者可以在自己手机上临时改用草稿调试。

任务版本、步骤库和开发草稿都属于某个游戏，公共步骤只在同一个游戏里复用。版本升级后，服务端按新版本的设置项重新校验每个账号的设置。

## 6. 游戏账号与切号

### 6.1 游戏账号管理

- **字段**：游戏、名称（如“主号”“小号”）、UID、区服、渠道、能否切换、最近一次在哪台设备哪个应用上使用。
- **添加**：在设备上手动登录游戏，App 识别 UID、区服、渠道后，点“保存为游戏账号”。护肝宝不收集游戏密码。
- **当前账号未保存**：应用识别出的账号还不是游戏账号时，提示先保存。这个应用不会命中 4.2 第 1 步，但可以被第 2 步拿去切号使用。
- **网页**：“游戏账号”页按游戏列出账号；点进某个账号，管理它的任务设置、计划，查看运行记录，也可以从这里立即运行。

### 6.2 默认账号和切号后恢复

- 每个应用**可以设一个默认账号**，也可以不设。默认账号表示“这个应用平时就该登录这个号”。
- 设了默认账号的应用不会被计划拿去切号（4.2 第 2 步只用没设默认账号的应用）。
- 设了默认账号时，切到别的账号运行的任务，结束后**自动切回默认账号**。无论任务是完成、失败还是被停止，都要恢复。没设时不切回，停在最后用的账号上。
- 队列里紧接着的任务用的是同一个账号时，先不切回，等这一串任务都跑完再恢复。
- 恢复失败（找不到账号、碰到验证、不认识的页面）就停下，不继续点，应用标为“账号未恢复”，并通知用户。
- 运行记录里写明：用的是哪个账号、在哪个应用、是否切换过、是否已恢复。

### 6.3 游戏账号适配

不同游戏添加和切换账号的方法不同，通用流程只调用统一接口，每个游戏在自己的任务版本里声明用哪种实现。

| 动作 | 输入 | 输出 |
| --- | --- | --- |
| 识别当前账号 | 无 | UID、区服、渠道、显示名 |
| 保存账号 | 无 | 一份账号材料，加密后存服务端，服务端不理解其内容 |
| 切换到某账号 | 账号材料 | 成功或失败；之后必须再识别一次核对 UID |
| 运行后收尾 | 无 | 可能更新的账号材料；需要时清除设备上的登录态 |

实现方式：

1. **界面操作（第一期只做这种）**：在游戏里退出，从游戏自己记住的账号列表里选目标。材料只是列表里的标识，不需要 Root，不保存密码。“识别当前账号”和“切换到账号”是任务包里的两段公共步骤，用现有步骤引擎执行，可以在开发链里制作和调试。
2. **登录态文件（以后）**：提取和写入游戏数据文件，材料就是登录态，需要 Root。读写逻辑在 App 代码里，任务包只声明文件清单。先完成第 9 节验证再做。
3. **不支持切换**：只能用应用当前登录的账号，分配时跳过 4.2 第 2 步。适合 QQ、微信授权登录这类本地拿不到也切不了的游戏。

规则：任何方式都不让用户输入或保存游戏密码；界面切换只能从游戏自己记住的账号里选；遇到验证码、二次验证或不认识的页面就停下，不做绕过。

**实现方式**（第 2 期第④步，2026-11-20 真机验证）：

- **任务包声明**：游戏在任务包的目标里声明 `accounts: { identify, switchTo }`，指向两个任务。“识别当前账号”没有设置项；“切换账号”只有一个必填文本设置项 `nickname`。这两个任务不出现在任务列表、常用和计划里，只由 App 在作业前后自己运行。声明了它们的应用就是“可切号”，随状态上报。以后换更好的切号手段，只需替换“切换账号”这个任务。
- **识别**：动作 `account.report` 把画面上读到的编号和昵称交给 App。App 随设备状态上报 `observed`，服务端按编号找到这个用户的游戏账号，自动更新应用的“当前登录”。识别到的账号还没保存时，网页设备卡片和 App 云端页可以一键“保存为游戏账号”。
- **账号字段**：目前只有名称、编号（UID，同一用户同一游戏内不能重复）和游戏昵称。切号用游戏昵称在“已有角色”里找目标，核对只比编号。区服、渠道以后再加。
- **作业前后**：租约带 `account`（要用的账号）和 `restore`（应用的默认账号，与本次账号不同、且队列里下一个作业不是同一账号时才带）。设备开始作业前先识别：编号一致就直接运行；不一致就按昵称切号，再识别核对编号，对不上就把作业记为失败，不运行。任务跑完后，有 `restore` 就先切回去，再上报作业结果，这样服务端下发下一个作业时设备已经空出来了。切回失败的原因附在作业结果后面。服务端下发前还会再核对一次：应用登录着别的账号、又切不到这个账号（应用不能切号，或账号缺编号、昵称），作业直接记为失败，不会跑在当前登录的账号上。App 中途重启时，识别和切号重新做一遍，不沿用重启前的结果。
- **还没做的**：识别结果只存在 App 内存里，也不会过期，用户在游戏里手动换号后要再点一次“识别”；它按游戏记，同一游戏装了多个渠道包时还分不开。作业准备阶段（识别、切号）收到暂停，要等任务本身开始后才生效。恢复失败时把应用标为“账号未恢复”并通知用户（通知第 11 节还没做）；运行记录里单独列出“是否切换过、是否已恢复”，目前只能从作业明细里看。

### 6.4 多开和分身

- Windows 上每个游戏窗口是一个应用。Windows 端要给每个游戏窗口稳定编号，识别、截图、点击、切号都只针对这一个窗口。怎么编号需要先验证（第 9 节）。
- 手机上的系统分身或双开也是单独的应用。手机的同时运行上限是 1，多个应用共用一条运行队列，轮流运行。
- **网页导航**：手机和 Windows 用同一个“应用详情”页，内容是运行状态、队列、默认账号、运行记录，以及当前登录账号的设置和计划入口（内容仍属于账号）。区别只在进入方式：Windows 设备先列出应用，选一个进入；手机直接进入它的**默认应用**，页面上方可以切到同一台手机的其他应用（分身、其他游戏）。
- **手机的默认应用**：最近一次运行过的应用；从没运行过就是第一个。和“默认账号”无关，默认账号仍按应用设置。

### 6.5 登录态加密（以后实现）

登录态按**用户**加密，不绑定某台设备。同一个用户登录到新设备后，就能继续操作自己的游戏账号。服务端只保存密文，服务器和数据库都不能解密。

```text
用户密钥（每个用户一把）
└─ 加密每份登录态的数据密钥
     └─ 加密登录态内容

用户密钥的保存方式：
├─ 用恢复密钥加密一份，存在服务端
└─ 用每台可信设备的硬件公钥各加密一份，存在服务端
```

1. 用户第一次保存登录态时，设备生成用户密钥，并生成一份恢复密钥交给用户保管。
2. 每台设备在 Android Keystore 生成不可导出的密钥对，公钥上传服务端。
3. 每份登录态使用独立的随机数据密钥加密，数据密钥再用用户密钥加密。
4. 设备成为可信设备后，能解开用户密钥，也就能解开这个用户的所有登录态。定时任务不需要用户在场。

**切换到新设备**：新设备登录后，在新设备上输入恢复密钥，或在一台已可信的设备上确认，成为可信设备，只需做一次。只在网页点击不能授权，这样邮箱或 GitHub 被盗时，攻击者也拿不到登录态。

**吊销设备**：删除它那份用户密钥密文，并轮换用户密钥，重新加密所有数据密钥。

**用登录态文件切号的流程**：申领账号（加账号锁，拿到登录态密文）→ 停止游戏，解密写入，启动 → 核对 UID、区服、渠道，不一致立即停止 → 运行，期间续锁 → 停止游戏，重新提取登录态加密上传 → 清除设备上的登录态，释放账号锁。

## 7. 用户与登录

Web 和 App 使用同一个护肝宝账号，所有服务端数据都归属某个用户。

**App 的登录要求**：第一次下载任务版本需要登录。之后不登录或断网，也能在本机运行已有的任务（用缓存的设置）；计划、远程控制、上传任务都需要在线并登录。

**登录方式**

| 方式 | Web | App | 说明 |
| --- | --- | --- | --- |
| 邮箱 + 密码 | 支持 | 支持 | 注册时必须验证邮箱 |
| 邮箱验证码 | 支持 | 支持 | 可免密码登录，验证码短期有效且只能用一次 |
| GitHub | 网页授权 | 设备码登录 | 第一个第三方登录，也用于开发者验证 |

- **用户标识**：平台生成自己的用户 ID，邮箱和 GitHub 都只是绑定到这个 ID 的登录方式。GitHub 使用数字用户 ID 绑定，不用可修改的用户名。
- **绑定规则**：不同登录方式不自动合并。邮箱相同也要先登录原账号，再主动绑定，防止他人借第三方账号接管。解绑时至少保留一种登录方式。
- **密码安全**：只保存 Argon2id 哈希；登录和发送验证码都限制频率；登录失败时不提示邮箱是否已注册。重置密码后，其他设备全部下线。
- **第三方令牌**：GitHub 授权码只在服务端换取身份，Client Secret 只放在服务端，不保存 GitHub 令牌，也不用它访问用户仓库。
- **平台会话**：登录后由服务端签发自己的短期凭证。刷新凭证保存在 Android Keystore，续期只依赖平台。网页可以随时踢下线。
- **访问保障**：GitHub 在国内可能访问不稳定，失败时提示改用邮箱登录；已登录的设备不受影响。

**三层防串号**

| 层级 | 防什么 | 做法 |
| --- | --- | --- |
| 服务端接口 | 用户 A 读到用户 B 的数据 | 每个接口和每条 SSE 推送都按当前用户过滤，设备、游戏账号、运行记录必须属于同一用户 |
| App 接收下发 | 任务发到别人的设备 | 租约和命令带用户编号，App 核对与当前登录用户一致，不一致直接拒绝 |
| 游戏内核对 | 切到的账号和目标不符 | 切号后核对 UID、区服、渠道，不一致立即停止，不运行任务 |

**退出和换用户**

- App 退出登录时，先停止运行，断开连接，清除缓存的设置、登录态和设备密钥。
- 重新登录或换用户按新设备处理，旧授权作废。
- 同一个游戏 UID 只能绑定一个护肝宝账号，重复绑定时拒绝并提示。

**登录和加密分开**：任何登录方式都只用于证明身份，不能解密登录态，重置密码也不例外。丢失恢复密钥且没有可信设备时，已保存的登录态无法恢复，只能重新登录游戏并保存。

## 8. 必须遵守的规则

- **登录即绑定**：App 登录成功后自动注册为该用户的设备；成为可信设备后才能申领登录态。
- **固定命令**：只能发 4.5 定义的命令，不能发任意点击或 shell 命令。
- **一个应用一个任务**：每个应用同一时间只运行一个任务。
- **只由服务端触发计划**：设备不自己计时运行计划。
- **账号锁**：同一游戏账号同时只能在一个应用上运行，跨设备也一样；持有记录带递增编号，旧编号的上报一律拒绝。
- **断网只读**：断网时 App 里的设置只能看、不能改。
- **异常清理**：App 启动时、账号锁失效时、解绑时都要清除残留登录态。
- **身份核对**：切号后必须核对 UID、区服和渠道，核对失败不运行任务。
- **消耗上限**：调高消耗上限的修改需要二次确认。
- **审计**：下发、命令、解密、上传、吊销都记录，不记录登录态内容。

**第 3 期的拆分**（2026-11-20 确认）：① 服务端事件规则和事件记录：任务开始、任务成功、计划开始、计划结束、连续执行失败、结果待核对、排队等待过久，加上只有服务端能判断的设备掉线、计划没执行、账号没切回；网页“通知”页配置规则、查看事件记录。② 外部渠道：Webhook、钉钉、企业微信、Bark、邮件；密钥加密存服务端，渠道订阅、测试发送、投递记录。③ 设备上报的事件（执行无进展、运行条件中断、资源或容量受限）和本机通知渠道：设备在线时服务端推给 App 弹出，断网时 App 自己弹出、联网后补报。视觉服务异常随第 5 期 AI 识图一起做。

**第 2 期的拆分**（2026-11-19 确认）：① 服务端游戏账号、按账号的设置和计划，网页游戏账号页；② 服务端计时调度、WebSocket 下发、网页立即运行、暂停、停止；③ App 设置页和计划页改读写服务端，本机运行拿账号锁；④ 识别当前账号和界面切号（真机采样，用户提供第二个账号并自己登录）。④ 之前，应用当前登录的是哪个账号由用户在网页或 App 里手动指定，所有游戏暂按“不支持切换”处理。计划按护肝宝账号的时区计时，默认 Asia/Shanghai，可在网页修改。任务设置在“任务版本按游戏选定”（第 4 期）之前，按这个用户最近上传、含该任务的任务包校验。

## 11. 通知、AI 识图与网络代理（2026-11-19 确认）

PRD 第 6.1、6.2 节和“云端视觉模型”的设计保留，下面只说明它们在新架构里放在哪。

### 11.1 通知

- **归属**：通知渠道、事件规则、事件记录、投递记录都属于护肝宝账号，存服务端，在网页“通知”页配置和查看。路径仍是“规则 → 事件 → 已启用渠道订阅 → 投递记录”，规则默认全部关闭。
- **渠道**：本机通知、钉钉、企业微信、Bark、邮件、自定义 Webhook。除本机通知外都由服务端发送，所以设备掉线或进程被杀也能收到。
- **本机通知**：设备在线时，服务端把订阅了本机通知的事件推给设备，由设备弹出；断网时，设备自己检测到的事件直接在本机弹出，联网后补报事件。
- **事件从哪来**：
  - 服务端根据运行记录和调度判断：任务开始、任务成功、计划开始、计划结束、连续执行失败、结果待核对、排队等待过久。
  - 只有设备看得见的，由设备作为事件上报：执行无进展、运行条件中断、资源或容量受限、视觉服务异常。
  - 新增三条只有服务端能判断的规则：**设备掉线**（连接断开达到时长）、**计划没执行**（超过最晚开始时间仍没有可用应用）、**账号没切回**（6.2 恢复失败）。
- **密钥**：渠道密钥加密存服务端。服务端发送时必须能解开，这一点和游戏登录态不同（6.5 服务端解不开）。网页只显示是否已填写，不回显密钥。
- **历史记录**：运行记录在网页运行记录里；通知投递记录在网页“通知”页里；App 只留最近几十条。
- **实现方式**（第 3 期第①步）：
  - **作业状态变化**：数据库触发器把每次作业状态变化写进 `job_changes`，所以改作业状态的代码不用逐处通知规则。事件模块（`Notices`）在每次作业推送和每个调度节拍读这张表，按规则生成事件，读完就删。
  - **持续的情况**：排队过久、设备掉线在每个节拍按当前状态判断。掉线时长从设备最后一次上报算起，但不早于服务端启动的时间。
  - **去重**：每条事件有一个唯一键，代表“同一件事”：同一个作业、同一次计划、同一段掉线。同一件事只记一条。
  - **规则开关**：只有打开规则才开始记“开始、成功、结束”这类一次性事件，打开前发生的不补发。改阈值不算重新打开。
  - **计划的结果**：一次计划的所有任务都结束才算结束。全部完成算“全部完成”，全部取消算“已取消”，一个都没完成算“失败”，其余算“部分失败”。全部被跳过的那次，记为“计划没执行”。
  - **连续执行失败**：单独运行的任务，按“账号 + 任务”数连续失败的次数；计划按它的历次运行数。结果未知和取消既不计入，也不打断连续。
  - **账号没切回**：设备在作业结果里带上 `restoreIssue`，服务端据此产生“账号没切回”事件。
  - **保留数量**：每个用户保留最近 500 条事件。
- **实现方式**（第 3 期第②步）：
  - **渠道**：钉钉（可选加签）、企业微信、Bark（可自建服务器）、邮件、Webhook（可带一个认证头），每个用户最多 20 个，各自订阅若干条规则。
  - **密钥**：机器人地址、加签密钥、设备密钥、Webhook 地址和认证头都算密钥，用服务端密钥派生的 AES-GCM 密钥加密入库。接口只返回哪些已填写，编辑时留空就沿用原值；换了渠道类型、改了地址（Webhook 地址、Bark 服务器）都不沿用其他密钥，免得旧密钥被发到新地址。可选的密钥（加签、认证头）可以单独清除。
  - **投递**：规则记下事件时，在同一个事务里给每个订阅了这条规则、开着的渠道建一条投递。另有一个循环每 2 秒把到期的投递发出去，不占用请求和调度节拍。失败后隔 1、5、15 分钟重试，第 4 次仍失败就记为失败，网页可以重发；渠道被删除或停用的不再重试。每一轮每个用户最多发 3 条，一个用户的慢渠道拖不住别人；一条读不出来的投递（比如服务端密钥换了）直接记为失败，不会卡住队列。投递是“至少一次”：服务端恰好在发出后、记下结果前停掉，重启后会再发一次，所以 Webhook 的内容里带 `deliveryId` 方便对方去重。钉钉、企业微信、Bark 回 200 也要看回复里的代码是否表示接受。
  - **测试发送**：用表单里的草稿立即发一条测试消息，只留一条测试投递（每个用户保留最近 20 条），不产生事件，也不保存渠道。每个用户 10 分钟内最多测 10 次。
  - **地址限制**：服务端只往 http 或 https 地址发，不跟随跳转，整次请求最多 15 秒，回复最多读 4 KB。地址只解析一次，连接只连这次检查过的地址（防止 DNS 重绑定）；解析出的地址在内网、本机、链路本地、运营商 NAT、基准测试、NAT64 等保留范围的一律拒绝，防止被借去访问内部服务。失败原因里不转述对方的回复内容，只有官方的钉钉、企业微信给的错误说明会显示。钉钉、企业微信的地址必须是官方前缀。本地开发要发到本机时，设环境变量 `YYS_CHANNELS_PRIVATE=allow`。
  - **邮件**：只发到账号已验证的邮箱，由服务端的发信服务发送（C36），每个用户只能有一个邮件渠道，避免被拿去给任意地址发信或重复发信。
- **实现方式**（第 3 期第③步）：
  - **设备判断的规则**：“执行无进展”和“运行条件中断”只有设备看得见，规则里标为由设备判断。服务端把开着的这类规则（含阈值）随设备数据下发给设备，设备每 5 秒判断一次：
    - 执行无进展：正在运行、没暂停，并且同一步停留达到阈值分钟数。暂停之后重新计时。
    - 运行条件中断：有任务在运行或排队，执行器却因为无障碍断开、屏幕不可用、游戏不在前台等原因开始不了下一步，持续一分钟以上，避免一闪而过的情况误报。
    - 同一次情况只报一次，事件编号由“运行 + 步骤”或“运行 + 原因”组成，App 重启后再判断出同一件事，服务端也只记一条。开始不了下一步时只算“运行条件中断”，不再同时算“执行无进展”。
  - **上报**：设备发现的事件存在本机，联网时发到服务端（`/api/device/notices`），断网时攒着，联网后补报，最多保留 50 条。服务端按“设备 + 事件编号”去重，只记规则开着、而且开启之后发生的事；设备不能上报服务端自己判断的那些规则。
  - **本机通知渠道**：渠道类型“本机通知”，指定一台设备。设备在线时，服务端经长连接推给护肝宝 App，用系统通知弹出；设备离线就和其他渠道一样，按 1、5、15 分钟重试。设备自己发现的事件，如果有指向它的本机通知渠道订阅了这条规则，会当场弹出，断网也一样；上报时标明“已弹出”（只有真的弹出来了才标；开关关着或系统不允许通知时不标），服务端就不再推回这台设备。经长连接推送时，只要消息交给了连接就记为已送达。推送至少送达一次，App 按事件编号只弹一次。
  - **App**：“云端控制”页有“在这台手机上弹出通知”开关，关掉后这台手机不再弹出，渠道本身不变；系统的通知权限仍然决定能不能弹出。
  - **还没做的**：资源或容量受限（引擎里还没有判断资源的依据，等有任务能识别资源不足再加）；视觉服务异常（随第 5 期 AI 识图）；App 里显示最近几十条通知（随 App 统一页面结构一起做，C38）。

### 11.2 AI 识图（云端视觉模型）

- **配置在网页**：服务商、密钥、开关属于护肝宝账号，所有设备共用一份；每台设备可以单独关闭。
- **密钥加密存服务端，下发到设备，由设备直连服务商**。截图不经过护肝宝服务端，省带宽也更保护隐私。
- 设备只把密钥放在内存或 Android Keystore 里，退出登录时清除；运行记录和事件里不出现密钥。
- 不采用服务端代理转发：那样所有截图都要经过护肝宝服务器。

### 11.3 网络代理

- 网络代理是 App 的本机设置，每台设备各自配置，不存服务端。
- 走代理的范围在 PRD 的视觉模型、任务更新、外部通知之外，加一项“护肝宝服务端”（WebSocket 和 HTTP）。
- 外部通知改由服务端发送后，App 里的“外部通知”范围只影响设备直接发出的请求。
