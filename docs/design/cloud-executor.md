# 云端控制与 App 执行器化方案（2026-11-18）

状态：用户、设备和作业下发已在 `cloud-executor` 分支实现，见[开发说明](../development/cloud-console.md)；登录态托管和云端计划尚未实现。本文取代 PRD 中“登录态快照只留在本机”的规则。

## 1. 目标

- 用户只用 Web 控制台管理账号、任务、计划和设备。
- App 只负责执行：自动注册到云端，领取作业，运行，上报结果。
- 账号登录态加密保存在云端，执行时才下发到设备，执行后从设备清除。

## 2. 职责划分

| 能力 | 云端 | App |
| --- | --- | --- |
| 账号与登录态密文 | 保管 | 执行期间临时持有 |
| 任务配置、计划、调度 | 负责 | 不再负责 |
| 任务版本 | 指定版本 | 下载并校验 |
| 执行、识别、输入 | 不参与 | 负责，继续用唯一执行器 |
| 中断恢复 | 判断租约是否有效 | 本地日志保证不重复输入 |
| 运行记录 | 长期保存 | 上报后只保留近期 |
| 本机界面 | 无 | 只保留绑定状态、当前运行、暂停和解绑 |

## 3. 总体流程

```text
控制台 / 定时计划
      │ 创建作业
      ▼
云端调度 ── 账号加锁，选择在线设备
      │ 下发租约（作业、任务版本、配置、登录态密文）
      ▼
App 执行器
  1. 校验租约，暂停队列，停止游戏
  2. 解密并写入登录态，启动游戏
  3. 核对 UID、区服、渠道，不一致立即停止
  4. 运行任务，持续续租并上报结果
  5. 停止游戏，重新提取最新登录态，加密上传
  6. 清除设备上的登录态，释放租约
```

## 4. 登录态加密

登录态按**用户**加密，不绑定某台设备。同一个用户登录到新设备后，就能继续操作自己的游戏账号。云端只保存密文，服务器和数据库都不能解密。

```text
用户密钥（每个用户一把）
└─ 加密每份登录态的数据密钥
     └─ 加密登录态内容

用户密钥的保存方式：
├─ 用恢复密钥加密一份，存在云端
└─ 用每台可信设备的硬件公钥各加密一份，存在云端
```

1. 用户第一次保存登录态时，设备生成用户密钥，并生成一份恢复密钥交给用户保管。
2. 每台设备在 Android Keystore 生成不可导出的密钥对，公钥上传云端。
3. 每份登录态使用独立的随机数据密钥加密，数据密钥再用用户密钥加密。
4. 设备成为可信设备后，能解开用户密钥，也就能解开这个用户的所有登录态。定时任务不需要用户在场。

**切换到新设备**

新设备登录后，用下面任一方式成为可信设备，只需做一次：

- 在新设备上输入恢复密钥。
- 在一台已可信的设备上确认，由它把用户密钥加密给新设备。

只在网页控制台点击不能授权，这样邮箱或 GitHub 被盗时，攻击者也拿不到登录态。

**吊销设备**：删除它那份用户密钥密文，并轮换用户密钥，重新加密所有数据密钥。

## 5. 用户与登录

Web 和 App 使用同一个用户账号，都必须登录。所有数据都归属某个用户。

```text
用户
├─ 设备（手机、Windows）
├─ 游戏账号（UID、区服、渠道、登录态密文）
│    └─ 任务配置、计划、运行记录
└─ 用户密钥（加密该用户的所有登录态）
```

**登录方式**

一个用户可以绑定多种登录方式，登录后都是同一个人。

| 方式 | Web | App | 说明 |
| --- | --- | --- | --- |
| 邮箱 + 密码 | 支持 | 支持 | 注册时必须验证邮箱 |
| 邮箱验证码 | 支持 | 支持 | 可免密码登录，验证码短期有效且只能用一次 |
| GitHub | 网页授权 | 设备码登录 | 第一个第三方登录，之后可扩展其他平台 |

- **用户标识**：平台生成自己的用户 ID，邮箱和 GitHub 都只是绑定到这个 ID 的登录方式。GitHub 使用数字用户 ID 绑定，不用可修改的用户名。
- **绑定规则**：不同登录方式不自动合并。邮箱相同也要先登录原账号，再主动绑定，防止他人借第三方账号接管。解绑时至少保留一种登录方式。
- **密码安全**：只保存 Argon2id 哈希；登录和发送验证码都限制频率；登录失败时不提示邮箱是否已注册。重置密码后，其他设备全部下线。
- **第三方令牌**：GitHub 授权码只在服务端换取身份，Client Secret 只放在服务端，不保存 GitHub 令牌，也不用它访问用户仓库。
- **平台会话**：登录后由云端签发自己的短期凭证。刷新凭证保存在 Android Keystore，续期只依赖平台，不依赖 GitHub 或邮箱服务。控制台可以随时踢下线。
- **新设备确认**：App 登录后就能领取普通作业。要领取登录态，还需用恢复密钥或已可信设备授权（见第 4 节）。
- **访问保障**：GitHub 在国内可能访问不稳定，失败时提示改用邮箱登录；已登录的设备不受影响。

**三层防串号**

| 层级 | 防什么 | 做法 |
| --- | --- | --- |
| 云端接口 | 用户 A 读到用户 B 的数据 | 每个接口都按当前用户过滤，设备、账号、作业必须属于同一用户 |
| App 领取作业 | 作业发到别人的设备 | 租约带用户编号，App 核对与当前登录用户一致，不一致直接拒绝 |
| 游戏内核对 | 登录态和目标账号不符 | 启动后核对 UID、区服、渠道，不一致立即停止，不运行任务 |

**退出和换用户**

- App 退出登录或换用户时，先停止运行、释放租约，再清除登录态、配置缓存和设备密钥。
- 重新登录按新设备处理，需要重新确认，旧授权作废。
- 同一个游戏 UID 只能绑定一个用户，重复绑定时拒绝并提示。

**登录和加密分开**

任何登录方式都只用于证明身份，不能解密登录态，重置密码也不例外。用户密钥由用户单独保管的恢复密钥保护。邮箱或 GitHub 被盗时，攻击者也解不开已有登录态。丢失恢复密钥且没有可信设备时，已保存的登录态无法恢复，只能重新登录游戏并保存。

## 6. 必须遵守的规则

- **登录即注册**：App 登录成功后自动注册为该用户的设备，未登录时不能领取作业；成为可信设备后才能领取登录态。
- **账号互斥**：同一账号同时只能有一个有效租约，每次租约带递增编号，旧编号的上报一律拒绝。
- **登录态版本**：上传时比较版本，防止旧登录态覆盖新登录态。
- **异常清理**：App 启动时、租约失效时、解绑时都要清除残留登录态。
- **身份核对**：启动后必须核对 UID、区服和渠道，核对失败不运行任务。
- **固定命令**：云端只能下发已定义的作业，不能下发任意点击或 shell 命令。
- **消耗上限**：设备按租约里的上限执行，调高上限需要控制台二次确认。
- **审计**：下发、解密、上传、吊销都记录，不记录登录态内容。

## 7. 需要先验证

| 问题 | 为什么重要 |
| --- | --- |
| 登录态文件在哪，Root 下能否完整提取和恢复 | 整个方案的前提，目前没有真实证据 |
| 登录态是否绑定设备 | 决定账号能否在多台设备之间调度 |
| 每次运行后登录态是否变化 | 决定回传和版本控制的细节 |
| 频繁切换是否触发安全验证 | 决定调度频率，触发后停止并通知用户，不做绕过 |
| Windows 桌面端的登录态机制 | 决定 Windows 能否走同一流程 |

## 8. 分期

1. **验证期**：在专用 Root 设备和测试账号上完成第 7 节，不接云端。
2. **用户与设备**：用户登录、App 扫码绑定、在线状态、作业下发、结果上报，先不下发登录态。
3. **云端调度**：计划和配置迁到云端，App 执行器化。
4. **登录态托管**：加密存储、下发、回传和清除。
5. **多设备**：账号调度、Windows 多开。

现有代码的衔接点：`ExecutionRequest` 可对应作业，`commandId` 用于防重复提交，`execution_facts` 按编号追加，可直接用于增量上报。
