# 阴阳师助手 Android UI 设计方案

版本：0.2<br>
日期：2026-11-15<br>
状态：旧 UI 方案与视觉稿已被用户否定，保留作过程资料，不作为后续视觉基线。最新完整原型见 [App v2](../prototype/app-v2.html)和[本轮交付索引](README.md)，尚待用户评审。下文原有结构与规则仅作需求追踪，与最新稿冲突时以完整 PRD 和 v2 为准，不代表旧布局获认可。<br>
产品依据：[完整产品蓝图](../PRD.md)，运行契约对齐[系统架构](system-architecture.md)，平台约束对齐[技术方案](technical-plan.md)。本方案定义 UI 结构与表现，不新增游戏行为、消费规则或自动化默认值。

## 一 设计目标与边界

用户最常做的三件事是看托管是否正常、配置游戏任务、在异常时接管。主界面优先回答“是否在运行、正在做什么、是否需要我处理”，其次才是统计。

完整 App 保持一套任务、计划和记录。云端模型是可选能力配置，不产生第二套“AI 版”导航。悬浮球是运行界面的快捷入口，不另建任务列表或一组独立状态。

主 agent 提供的低保真原型作为页面结构基线。后续视觉设计可以调整字体、留白、组件质感与表现，但不得自行增加主入口、改变业务归属、隐去支持条件或将待确认规则填为默认值。确有结构问题时，提出原型修改建议并说明理由。

## 二 导航与信息归属

五个主入口保持稳定：工作台、任务中心、托管计划、消息与记录、设置。顶层采用 Android 可适配的五项导航；窄屏底部入口和宽屏导航形态由最终尺寸验证决定，不额外引入产品入口。

用户已明确要求主 App 支持横屏，避免从游戏切回助手时旋转屏幕。横屏适配覆盖五个主入口及关键详情／表单，不仅是游戏悬浮球。横竖屏共享页面身份、规则、草稿和运行状态，切换方向不重启任务或丢弃编辑。

| 主入口 | 第一屏优先内容 | 二级页面 |
| --- | --- | --- |
| 工作台 | 当前运行状态、待处理异常、当前任务和下一项任务 | 当前运行详情、周期进度、环境问题 |
| 任务中心 | 六类业务入口与支持条件 | 分类列表、任务详情、单次执行范围 |
| 托管计划 | 已配置计划、下一次执行及生效状态 | 计划详情、任务编排、目标和资源限制 |
| 消息与记录 | 待处理事项 | 问题详情、通知投递、运行历史与结果证据 |
| 设置 | 公共能力及其当前可用状态 | 运行环境、模型、通知渠道、悬浮球、兼容、数据 |

任务中心的六类分别为日常与领取、商店兑换、副本与挑战、御魂管理、结界与阴阳寮、限时活动。每日、每周、指定时段、模型依赖是标签和筛选条件。御魂副本与御魂整理不可混在同一配置页；活动页中的兑换入口应指向同一兑换规则。

工作台的“下次执行”跳到计划，任务名称跳到任务详情，异常摘要跳到待处理问题。快捷入口必须可追溯到原始任务或事件，避免复制配置。

## 三 主页面布局与交互

### 3.1 工作台

视觉草案采用的竖屏顺序为：环境或授权阻塞 → 当前运行状态与任务控制 → 待处理异常 → 下次执行 → 今日／本周结果。与低保真中周期指标靠前的排列相比，这里提升异常优先级，保持全部入口与状态不变。

横屏按当前任务与控制、异常及周期信息、下一项执行三个区域重排；当前任务和异常优先可见，不将竖屏画面简单旋转后缩小。

运行区显示一个明确状态词、一句原因和对应操作。进行中显示目标及已验证进度；等待显示等待原因；需要接管显示问题入口。进度不确定时不绘制虚假的百分比。

当前任务区只放运行控制。计划编辑、筛选规则和通知密钥不放进工作台。开始按钮附近应能检查本次选中的任务和资源规则；具体是否额外确认由产品规则确定。

### 3.2 任务中心与详情

分类页呈现六类业务及明确名称。任务详情按以下顺序组织：

1. 任务名称、支持状态、模型与环境条件。
2. 任务目标及是否加入托管计划。
3. 具体对象与规则。
4. 可能消耗的资源及停止条件。
5. 最近结果，以及单次执行入口。

单次执行与加入计划使用不同文案，不以同一个“启动”按钮同时承担两种含义。暂未支持的任务显示限制或待适配说明，不能用可点击开关制造已交付假象。

编辑状态区分未保存、已保存待生效、已生效和保存失败。配置运行中如何生效尚待产品决策；UI 不能先表现为“立即生效”。敏感规则变化应给出差异摘要，具体确认条件待产品决定。

### 3.3 日常与物资领取

以物资来源为行，显示周期、领取资格及状态。永久勾玉卡明确命名为“产出领取”，不与购买卡片共用入口。

至少区分未拥有、尚不可领取、可领取、已领取、结果未知和识别异常。已领取时间或周期只有得到实际结果时才显示；没有证据时用“未确认”，避免用空值代替正常。

### 3.4 商店兑换

商店列表显示开放条件与已配置商品。详情页依次为商店条件、商品选择、支付资源、数量／周期限额、余额或预算规则、执行结果。

周三／周六商店按用户术语标注，正式名称未核对前不绘制看似真实的商品价格、限额或重置时刻。原型中的示例数量和商品均不能直接成为产品默认值。

未开放、缺货、余额不足、已达限额和无法识别使用不同原因说明。结果未知时进入核对结果流程，不能直接提供无条件“重新兑换”。

### 3.5 御魂管理

入口分为强化和整理，两者可复用筛选与保留规则，但保持目标与操作可见。

强化页顺序：目标对象 → 强化目标或阶段 → 素材与预算 → 持续／停止规则 → 预计影响与执行结果。评分、属性阈值和淘汰规则未确定时不填推荐数值。

整理页顺序：筛选条件 → 保留条件 → 具体操作 → 命中对象 → 影响确认与结果。锁定、解锁、标记、奉纳、弃置和作为素材不是同一开关。尚未确认的处置能力应作为待决项，而非默认开启的批量操作。

处理对象列表需要能查看命中与保留的原因。执行中更新对象状态，不能让已被强化或其他任务变更的对象继续以旧信息呈现可处理。

### 3.6 活动

活动列表区分已适配流程与需要模型理解的内容。活动详情展示规则来源、目标、资源条件、当前阶段及限制；“理解完成”和“游戏活动完成”不得共用完成标记。

模型未配置时保留已适配活动入口，依赖模型的新活动能力说明原因。模型可用不等于该活动已验证支持，也不自动允许扩大资源预算。

新活动计划是否由用户首次确认属于产品待决项。无论最终策略如何，UI 需有空间展示助手对规则和资源影响的理解，并显示无法判断的条件。

### 3.7 托管计划

列表按计划呈现启用状态、周期、任务数量与下一次执行依据。详情按目标、执行条件、任务顺序、资源规则、停止条件和配置生效状态组织。

周期表达优先使用可读文案，同时明确游戏时区或周期来源；未核对规则时不能展示确定时间。跨周期补做、抢占与优先级还未决定，界面保留相应待决说明，不制造默认行为。

计划引用任务规则，进入任务编辑后返回原计划上下文。列表排序不等于执行优先级，拖拽顺序也不能被技术实现静默解释为抢占。

### 3.8 消息与记录

视图分为待处理、通知记录、运行历史。默认视图选择是 UI 建议，不代表任务状态自动变化。

问题详情呈现发生时间、任务、问题摘要、实际状态、已知资源影响、最近证据和允许的操作。查看即已读；“已处理”及“已恢复”必须由各自状态支持。对未知结果，操作应引导核对，而非假定失败后重试。

通知记录显示渠道、尝试时间和投递反馈。发送成功只能表述为渠道契约可证明的结果，不能显示“用户已收到”。模拟器中的本机通知不等于真机用户收到了提醒，应在渠道说明中表达接收环境。运行历史保持游戏结果独立，不因通知失败把任务染成失败。

### 3.9 设置

设置按公共能力分组，首层呈现是否已配置及当前可用性；详细密钥留在二级页，不出现在列表摘要。

模型页需要开关、服务地址、模型与认证、能力测试、调用状态及预算规则。未启用、配置不完整、鉴权错误、网络问题、限流和响应不可用分开展示。测试连接通过不等于视觉理解通过。

通知渠道页包含实例列表和编辑页。编辑页包含名称、类型、接收目标、认证、事件订阅、发送规则及测试发送。具体渠道字段随确认后的契约变化；原型应展示通用结构，不伪造第三方已兼容能力。

通知测试明确告知会向所配置目标发送测试消息，且需要用户主动触发。通知编辑、保存和打开开关均不应暗中发送测试消息。

运行环境页将截图会话、操作输入、悬浮显示和通知能力分开显示，分别说明用途、当前状态、用户操作入口与失败后影响，不能用一个“已授权”覆盖所有能力。授权未就绪应能返回查看其余配置，不通过循环弹窗强迫用户立即授予。

如果采用 MediaProjection，UI 需要“截图会话已结束，需重新授权”状态与前往系统授权的明确动作。该授权是会话级能力，不能画成一次开启后永久有效的开关；Android 15 QPR1 及以上锁屏会终止投屏，恢复不能承诺后台一键完成。[Android Media projection](https://developer.android.com/media/grow/media-projection)

本机通知权限关闭应显示“本机提醒不可用”，不能一概显示为游戏执行能力未就绪。Android 13 以上通知权限与前台服务启动前提并不相同，必要的系统运行通知和用户配置的业务提醒也需分开表达。[Android 通知权限](https://developer.android.com/develop/ui/compose/notifications/notification-permission)

兼容页按实际验证显示设备环境、主题及受限任务。不能用一个全局“识别正常”覆盖某任务在某主题不可用的事实。

## 四 运行状态表现契约

UI 需要接收真实状态与原因，不能通过按钮点击自行推定执行器已经暂停或停止。运行阶段、任务结果、能力状态和待处理问题是独立维度；下表是可观察表现的集合，不是一组互斥枚举。例如“本次已停止”可以同时显示“上一步兑换结果未知”，不能为显示已停止而抹掉未知结果。

| 状态 | 用户可读表现 | 典型操作与限制 |
| --- | --- | --- |
| 未开始 | 尚未启动；显示准备情况 | 检查任务范围、开始 |
| 运行中 | 当前任务及已验证进度 | 发起暂停或停止、查看详情 |
| 等待 | 明确等待时间、条件或外部结果 | 依确认规则显示可用操作 |
| 暂停中 | 暂停请求已提交，等待执行器确认 | 不提前显示已暂停，不重复创建控制请求 |
| 已暂停 | 当前执行已暂停，说明保留进度 | 继续、停止 |
| 停止中 | 停止请求处理中，说明正在结束什么 | 不提前显示结束，不允许误触继续 |
| 已停止 | 本次运行结束，保留实际完成与未完成结果 | 查看记录、重新配置；再次执行不是自动重试 |
| 需要接管 | 明确问题与受影响范围 | 查看证据、按允许操作接管 |
| 结果未知 | 无法确认上一步实际结果 | 核对当前状态，不无条件重做 |
| 能力不可用 | 授权、环境或必要服务不满足 | 前往对应设置；区分任务和全局影响 |

已达到资源／次数目标与执行失败使用不同的停止原因。任务失败不一定意味着所有计划终止，实际动作由已确认策略决定，UI 只显示执行器结果。

对齐架构的只读运行快照，主页面和悬浮球共同呈现会话阶段、当前任务、结果、可用能力、待处理命令、当前与待生效配置、问题及状态更新时间。快照过期或连接中断不能继续把旧画面标成实时正常。

停止请求已限制新动作，但无法确认平台在途手势是否结束时，显示“已停止提交新操作，在途输入状态未知”。此时不能以一个“已停止”成功提示覆盖风险，也不能因云端模型未返回而让停止控制一直等待。

## 五 悬浮球与游戏内面板

### 5.1 收起球体

收起状态保留简短图形与可辨认状态，不仅靠颜色。状态建议包括运行、等待、暂停、异常和停止处理中；在尺寸受限时，通过图形加短标记，并让展开面板提供完整文字。

球体位置可调整，交互区应考虑真机手指和模拟器鼠标。点击与拖动的判定阈值需实测，不在本方案随意指定。吸边、自动收起、隐藏与再次唤出的规则均是待评审方案，不默认为启用。

### 5.2 展开面板

信息顺序为：当前状态 → 当前任务与进度／等待原因 → 主要控制 → 次要入口。面板只保留暂停／继续、停止、查看异常、返回助手及收起；复杂任务和预算编辑回主 App。

暂停和停止不相邻堆叠为两个同样强调的高频按钮。建议主操作随状态变化，停止作为明确可达的独立操作，最终视觉由原型空间验证。

异常展开显示问题摘要与“查看并处理”，不因颜色变化自动重试任务。异常是否主动展开面板尚未确定，不能擅自增加打断行为。

### 5.3 横屏与边界

游戏横屏时，面板避免跨越整个战斗区域，依据可用空间选择左右侧或紧凑布局。旋转、窗口尺寸变化或模拟器缩放后，交互入口仍须在可见范围内。

展开方向随边缘位置调整属于布局建议，须与技术方案验证。若悬浮层影响截图或截获游戏点击，应明确处理方案，不能靠用户手工避开全部关键界面。

### 5.4 权限与隐藏

授权缺失时，主 App 显示球体不可用及受影响能力；不能伪造一个已可操作的系统悬浮层。球体隐藏后如何再次唤出必须有明确入口，隐藏与停止运行保持不同语义。不得用覆盖整个游戏的透明可点击层实现球体周边空白；触摸区域与可见面板边界需由技术方案核验。

授权撤销或宿主能力消失后，应按架构状态显示限制；不得显示“持续保护中”等无证据的可靠性文案。系统无法由 App 控制的确认页与授权页，应与应用内页面分开标注。

## 六 视觉与组件建议

低保真阶段固定信息层级和控制关系，不固定品牌色、装饰、插画或最终图标。后续视觉稿以清晰、紧凑、适合长时间查看的 Android 工具界面为方向，避免用游戏皮肤装饰挤占状态和操作空间。

建议采用统一的间距、字体层级、表单、列表、分段视图、状态标签与底部操作区。数值、单位、周期和资源名称保持相邻；长错误信息可展开，但摘要必须说明实际影响。

状态组件至少提供正常、等待、警告、错误、未知和不可用的文字及形状差异。错误颜色不用于普通“尚未开始”；禁用态仍保持必要文字可读。

表单应有稳定标签、当前值、用途与校验原因。密码和认证默认遮盖，明文查看需明确动作。预算和阈值未确认时使用“未设置”或草稿标记，不填看似产品默认的示例。

模型、通知渠道、兑换、副本、强化、整理和计划编辑页采用可滚动内容加固定操作区。关键保存／测试／预览操作不应埋在长表单末尾；横屏减少高度后仍保留操作入口，字段按合适宽度重排，不能把标签与对应值拆开。

目标尺寸、字体、对比度等最终参数需要在实际 Android 页面与模拟器上验证；本稿不以网页原型的像素值替代平台实现要求。

## 七 需要补齐的视觉稿与交互状态

| 页面组 | 必交付状态 |
| --- | --- |
| 工作台 | 初次空态、就绪、运行、等待、暂停中／已暂停、停止中、异常接管 |
| 任务与计划 | 未配置、可执行、受限、未支持、未保存、待生效、生效失败 |
| 物资与商店 | 可领取／已领取、资格不足、商店未开放、缺货、余额不足、结果未知 |
| 御魂 | 未选对象、筛选命中／无命中、保留排除、阶段完成、素材不足、对象已变更 |
| 活动与模型 | 模型关闭、配置不完整、服务错误、规则理解中、需要确认、无法判断 |
| 消息与通知 | 无待处理、待接管、已读未处理、处理后恢复、投递成功／失败／未知 |
| 悬浮球 | 收起、展开、等待、暂停、异常、停止中、隐藏／唤出、权限不可用、横屏 |

这是一份完整设计范围，不表示所有状态必须在同一期实现。每期交付前应选取对应页面与状态，不得只画正常路径。

## 八 待确认与对齐记录

以下事项不通过视觉稿暗中定案：停止和暂停的执行边界、运行中配置生效、计划冲突与补做、通知渠道及默认订阅、重复提醒及静默规则、截图外发、悬浮球自动展开／吸边／隐藏规则、御魂消耗性操作及新活动自主权限。

系统架构与技术方案对 Android 授权、截图会话和悬浮层限制的核验结果已纳入第三至五节。通知权限关闭不一概阻塞游戏执行；输入未确认结束时不能提前显示完全停止；云端旧响应不能改变已结束会话的 UI 状态。

## 九 原型对照与后续 UI 交接

结构基线：[低保真交互原型](../prototype/index.html)。原型显示的是演示状态，所有任务、时间、商品、数量和渠道占位均不构成产品默认规则。正式视觉稿应保留以下页面关系。

| 原型编号与页面 ID | UI 交付范围 | 结构要求 |
| --- | --- | --- |
| 01 `home` | 工作台 | 当前运行优先于周期统计；保留异常与控制入口 |
| 02 `tasks` | 任务中心 | 六类业务；周期和模型依赖为标签 |
| 03 `daily` | 日常与领取 | 明确领取范围、资格与实际结果；条目选择不能只有文案没有控件 |
| 04 `shops`、05 `shop-detail` | 商店列表与兑换规则 | 商店条件、商品、数量与资源规则层级不变 |
| 06 `dungeons`、07 `dungeon-detail` | 副本与挑战 | 目标、队伍、资源与停止条件；不混入已有御魂整理 |
| 08 `souls`、09 `strengthen`、10 `sort` | 御魂管理与两类操作 | 强化和整理分开；对象、保留与素材影响可检查 |
| 11 `guild` | 结界与阴阳寮 | 卡片与合作规则保持明确，不复制领取任务 |
| 12 `activities`、13 `activity-detail` | 活动列表与理解目标 | 已适配与自主能力区分，目标和不确定项可见 |
| 14 `plans`、15 `plan-edit` | 托管计划 | 引用已有任务规则；不复制一份商品和御魂参数 |
| 16 `messages`、17 `issue` | 待处理问题与接管 | 已读不等于处理；未知不等于失败；停止按钮文案与实际范围一致 |
| 18 `delivery`、19 `history` | 投递和游戏结果 | 两者独立呈现；不能把渠道接收解释成用户已读 |
| 20 `settings`、21 `environment` | 公共设置与环境检查 | 能力逐项呈现，真实系统授权页与 App 页面分开 |
| 22 `model` | 云端视觉模型 | 关闭仍有本地能力；测试连接与视觉能力分别解释 |
| 23 `channels`、24 `channel-edit` | 通知配置 | 渠道、目标、认证与订阅；测试发送由用户主动触发 |
| 25 `float-settings`、26 `compatibility`、27 `data-settings` | 悬浮、兼容与运行数据 | 外观、能力范围与恢复规则分组，不替用户设默认策略 |
| 28 `float-game`、29 `float-expanded`、30 `float-error` | 游戏内悬浮球 | 收起、展开、异常；共享状态与控制，复杂编辑回主 App |

原型的七组总览分别为主导航、资源任务、规则任务、配置、状态、游戏横屏控制、主 App 横屏。正式视觉稿沿用该分组核对覆盖；最终布局可以为实际 Android 屏幕重新分配空间，但不能删掉状态语义。

已向主 agent 反馈的原型收尾检查点：暂停操作需要请求中状态；运行环境需要独立本机通知能力项；问题页停止文案与实际控制范围一致；领取范围需要可见选择表达；权限失效图不应误导为仍能显示悬浮层。这些是状态与表达修正，不是新增业务范围。

后续 UI 绘制按以下顺序交付：主导航与关键正常页 → 任务规则及通知／模型设置 → 异常与结果未知 → 悬浮球各状态与横屏 → 全量文字、尺寸和可达性检查。每组都引用页面 ID 与相应状态，不仅提供漂亮的首页。

## 十 可见视觉草案

[视觉 UI 草案](ui-preview.html)复用主原型的 30 页内容和演示交互，保持页面 ID、五个主入口、六类业务和状态语义。它是独立视觉提案，不覆盖低保真结构基线，不连接服务、保存密钥或操作游戏。

视觉方向为浅色管理界面、墨绿操作强调和少量暖金异常提示，使用本地系统字体及内联线性图标。游戏气质主要来自克制的色彩和小型文字标识，不将游戏插画铺在表单或状态背后。

已针对首页、六类任务、御魂入口、所有表单、通知与模型设置、消息结果和悬浮球统一组件表现。主页的异常信息提前，任务目录以网格呈现；这些是原型信息层级内的布局优化，不改变任务定义或资源规则。

入口用法：

- 竖屏交互：直接打开视觉草案，使用页面目录或手机内入口。
- 主 App 横屏：点击顶部横屏切换，或使用 `?orientation=landscape#home`。导航时保留横屏。
- 页面总览：`?board=overview`、`resources`、`rules`、`configuration`、`states`。
- 游戏横屏悬浮：`?board=landscape`；主 App 横屏总览：`?board=app-landscape`。

30 个页面均从同一内容与交互结构生成；视觉代码通过脚本语法检查。目标设备渲染、平台控件可达性和真实 Android 生命周期仍需实现后验证，网页草案不能替代这些验收。
