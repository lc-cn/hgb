# 步骤内控制流合同提案

2026-11-17，起稿基于 `f5170f9`。**用户已确认按本提案恢复目标并实现。** 下文保留实施策略及起稿时证据；现有实现合同见[步骤程序](../development/step-program.md)。目的在于补齐 M2／M3 对可领、已领和重复处理的表达能力，保留已确认的动作 → 步骤 → 任务 → 计划模型和唯一执行器。字段示例见 [step-control-flow.proposal.json](examples/step-control-flow.proposal.json)，它是步骤片段，不是可安装任务集或已发布游戏任务。

## 核对到的缺口

当前 `StepDefinition.actions` 只有顺序动作列表；`BuiltInStepWorkFactory` 顺序解释，输出仅存于本次步骤尝试。`screen.expectText` 未命中返回 Unknown，既不表示“已领取”，也不能选择另一条业务路径。因此，现有线性任务不足以同时表达“有明确可领证据才输入”及“有明确已领证据时只核对完成”。

起稿时庭院样本只能证明入口外观，真机未在 ADB 设备列表；不能把旧截图当当前资格证据。后续用户已批准只读导航并取得当前[物资页面样本](../development/build-evidence/game-readonly-sampling/README.md)，尚无实际领取结果。此前用户已确认的人工暂停、继续／重新开始、未知核对规则不因控制流扩展而变化。

上游源码的具体依据：固定提交 `7d26c420f10f43ea9eebfc8eeacf73537ea3bbdc` 的 [Func518](https://github.com/zzliux/assttyys_autojs/blob/7d26c420f10f43ea9eebfc8eeacf73537ea3bbdc/src/common/funcList/518_%E9%A2%86%E5%8F%96%E6%97%A5%E5%B8%B8%E5%A5%96%E5%8A%B1.ts#L690-L773) 将状态识别、分支、重复观察组合使用；其中查找达到上限即跳过是上游行为，**不采纳其次数、延迟、坐标、通知或成功判定**。这里只将实际源码作为“代表流程需要控制流”的证据，不复制实现、不声称当前游戏也有相同界面。

## 建议的表达

步骤继续是恢复单位，内部只有三个结构：

| 结构 | 开发者编排 | 运行含义 |
| --- | --- | --- |
| action | 选择 APK 动作并填参数 | 调用现有动作合同、参数绑定及输入记录 |
| branch | 选一个前序输出，列明确值及各自动作块 | 值精确匹配一个分支才进入；未匹配不走默认路径、不当作完成 |
| repeat | 填次数或绑定配置，列重复动作块 | 按明确非负整数次数执行；没有隐式无限循环或失败重试 |

`branch` 的比较仅支持类型相同的字符串／布尔／精确数字值；不执行表达式、模板字符串或脚本。重复计数可为常量或任务已保存的配置，继续沿用精确数值校验，不截断小数／溢出，不由 App 填默认次数。零次执行空块，完成仍须满足整步核对合同。需要“直到某状态结束”时，单独验证后再扩展；本次不把次数耗尽解释为业务成功。

动作 ID 在一个步骤中保持唯一；循环多次调用同一动作定义时，每次真实输入仍生成新的 invocation ID，沿用现有意图／回执记录，不拿动作定义 ID 作去重键。程序节点没有暂停状态、任务优先级或跨步骤游标。

输出按块拥有：子块可读取此前确定可用的外层输出；分支内部输出不自动流入共同后续；每次重复产生新的本地输出表，不复用上次迭代数据。公共后续需要的数据重新观察，不能引用未进入分支的动作。这样制作器可以给出可用输出选项，不让用户填写“可能不存在”的值。

示例中“本次可领取”与“本次已领取”均为**虚构夹具的正向状态文本**：前者才进入点击分支，后者为空分支；之后共同重新观察并核对已领状态。所有文字、置信度、手势时长和资源名均为合同示例，不是游戏默认或已经适配的任务。

## 识别状态的基础动作

建议增加 `screen.classifyText`，从本尝试的有效观察中按任务明确声明的文字证据选择一个状态，输出 `state`。必须只有一个状态有明确命中证据；零命中、多个状态命中、观察过期、识别失败分别保留无法确认，不使用 else 把“没识别到可领”猜成“已领取／无资格”。此输出仅用于选择路径，不能替代最终业务核对。

真实任务的证据还可能需要位置／图形／数值组合；不能为了配合本提案把游戏实际没有的文本写进任务。最终依据仍须由当前游戏采样验证，不能仅凭分类动作存在宣称跨主题支持。

## 同一解释器与验证入口

新增 `StepDefinition.program`，与现有 `actions` 互斥。旧 `actions` 进入同一程序解释器时视为 action 节点列表；没有第二套 Worker 或执行器。旧任务的写出字节和摘要不主动改写；旧 App 遇到新 program 字段按既有严格解析拒绝，不忽略控制流后执行。格式版本和能力兼容性仍在安装／启用入口核对。

装载、配置保存、入队、运行继续共用一份程序遍历及合同校验。必须检查分支条件可用性／类型、重复次数、块作用域、动作支持、截图目标与模型资源；不能只验证实际选中的分支而放过另一条坏分支。路径上的观察与目标只能在最近输入之后使用，分支合流不能让失效观察重新变可用。

核对规则看每一条可能执行路径：只要路径含观察或输入，完成前必须有有效业务核对。输入的独立静默、结果未知与留存证据仍走原 ActionSession／ExecutionRuntime 交接，不因一个分支结束、重复结束、协程取消或平台回调而宣布整步完成。需要演进 ScreenActions 的“末尾动作”判断，使它基于实际程序路径；不能单纯把所有分支平铺后取最后一个 ID。

## 暂停、恢复与故障

- 人工暂停／停止仍暂停整个队列；移除当前项仍须等旧输入静默，按已确认规则推进。
- 继续时跳过完成步骤；本步骤从入口重新观察、重新选分支，重复次数也重新按当前步骤入口开始。不会从上次第几轮／动作中途接着跑。
- 已发送输入而结果未知时，保留原未知，等待核对；不利用重新选分支或循环入口绕过这一保护。
- 明确失败继续后续、未知暂停等既有语义不变。没有增加自动游戏启动、重试、通知规则、发布或资源消费。

## 现有调用点核查

| 当前拥有者 | 必须一起演进的调用 |
| --- | --- |
| `TaskBundle.kt`／`ActionBindings.kt` | 装载校验、配置校验、引用可用性和每条路径末尾证据；不能只新增序列化类型 |
| `BuiltInStepWorkFactory` | 唯一解释器、实际是否可能输入、启动是否依赖观察、静态进程恢复证明和当前会话重入证明 |
| `DeviceExecutionReadiness` | 创建工作器前检查所有可能路径的观察／输入需求，不能只查看旧 actions 导致空程序绕过前置检查 |
| `ScreenActions` | 引用的画面阶段、实际终结核对、取消后的独立业务证据及输入静默 |
| `TaskVersionLibrary` → 配置仓库／候选入队／最终事务 | 继续复用同一合同，不分别实现控制流校验 |
| `ExecutionRuntime` | 继续调用原 factory／readiness；不解读分支语义、不拥有动作游标 |

实现时所有生产 `.actions` 读取都须逐一复核。当前进程恢复只对可证明无输入程序自动重入，不能因分支条件暂未求值而猜测其安全；输入记录或结果未知仍阻止重放。计次重复也须响应协程取消并让出执行机会，不能用巨量零等待循环阻塞主线程；这属于执行实现，不新增用户可见超时阈值。

## 代码实施与验收

实现归于现有任务合同、参数解析、步骤解释器、ScreenActions 及其测试，不更改计划／队列排序模型，不引入脚本运行时、Room 恢复游标或新执行器。必须先完成完整程序路径的静态验证，再开放加载新语法。

| 验证 | 必须看到的结果 |
| --- | --- |
| 手写 JSON 从 BundleCodec → 保存／入队 → 原 Worker | 按数据选择路径，修改配置不改在途快照；两份任务版本保持原锁定 |
| 可领、已领、未知、多状态 | 分别输入、零输入核对、Unknown、Unknown；不是未命中即成功 |
| 分支坏引用、跨块输出、旧观察、坏资源／配置 | 安装／保存／入队按同一合同拒绝；不等运行才碰运气 |
| 明确次数与精确数字 | 次数准确；小数／溢出拒绝；零次不伪造输出／核对证据 |
| 观察／输入路径的最终核对 | 所有路径均要求证据；点击平台完成或重复耗尽不自动完成 |
| 暂停、取消、移除、高优抢占与实际进程终止 | 沿原所有权结算，旧输入静默；未知不重放，已完成步骤保留 |
| 原生实际平台夹具 | 真实截图、识别、手势、数据库结果闭环，不能只测分支函数 |
| 实际游戏与留出主题 | 当前账号资格／状态／领取后结果独立核对；不以夹具或旧截图代替 |

本实现策略已获确认；真实游戏领取、Release 发布及外部消息仍各自核对已有授权。开发者制作器以后按分支／重复块生成 JSON，普通用户任务配置仍只显示 schema 控件。
