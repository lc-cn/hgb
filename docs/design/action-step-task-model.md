# 动作、步骤、任务与计划

日期：2026-11-15。状态：用户已确认App提供动作、开发者用JSON交付步骤与任务、用户拉取后执行或组合计划；具体动作目录、字段名及示例格式仍为提案，尚未实现或冻结协议。

## 1. 内容定义与执行控制

```text
计划 = 有序任务集合 + 执行时间管理
任务 = 有序步骤 + 一组配置 schema
步骤 = 为完成一个阶段而编排的动作
动作 = App提供的可复用基础能力，具有明确输入和输出

唯一 Executor：管理队列，执行任务，处理 pause / resume(mode)
```

任务是交付、配置和使用的基本单位。步骤与动作服务于任务表达，不给普通用户增加动作配置页面，也不增加动作／步骤／任务／计划各自的暂停状态机。

配置schema描述用户能设置什么；用户保存的配置值回答本次具体怎么做。二者分开，步骤和动作读取同一任务的配置值，不另复制预算、目标或数量。

## 2. 动作做什么，步骤做什么

| 层次 | 内容 | 示例 |
| --- | --- | --- |
| 动作 | 完成一种基础能力，输入／输出明确，不拥有任务队列 | 取得画面、定位目标、读取文字／数值、点击、滑动、等待条件、核对状态 |
| 步骤 | 将动作按业务阶段编排，明确何时算这一步完成 | 进入商店、选择商品、完成一次兑换并核对结果 |
| 任务 | 定义完整事项的步骤，以及用户配置schema | 商店兑换：商店、商品、数量、预算等配置与全部步骤 |
| 计划 | 引用任务并管理执行时间，引用用户已保存配置 | 每日指定时间处理所选任务 |

动作不只指手势。观察和核对也是基础能力，否则步骤只能表达“点哪里”，无法表达“为什么点、是否点对”。相反，“永久勾玉卡领取”这类游戏业务应由任务／步骤组织，不变成每次新增玩法都要扩充的原生动作。

动作的实现复用现有截图、识别和输入适配，不自研这些算法。点击的输入应是定位结果，携带对应画面和几何依据；普通任务作者引用语义目标与资源，避免把业务流程绑死到一个主题的坐标。

## 3. 建议的最小步骤表达

步骤至少需要稳定身份、名称及动作编排。第一版可先用有序动作列表；每次动作的输出可供后续动作读取，动作参数可引用任务配置与任务包识别资源。具体引用语法尚待协议设计，不执行字符串代码。

步骤的完成依据由动作编排明确表达，例如末尾核对“目标页面已打开”“余额与限购变化符合结果”。动作执行完毕或点击回调成功，不能自动等同业务步骤完成。

若代表任务需要分支／循环，建议将它们作为步骤的编排语法：根据动作输出选择路径，按配置次数或业务结束条件循环。它们不增加执行器，也不引入任意脚本语言。是否需要、如何表达，由实际任务验证后冻结；不一开始设计通用编程平台。

以下为可读伪定义，不是当前游戏已核实流程，也不是最终JSON协议：

```text
任务：商店兑换
配置schema：商店、商品、兑换数量、消费上限、保留余额

步骤：进入商店
  定位（任务配置中的目标商店） → 入口目标
  点击（入口目标）
  等待并核对（目标商店页面）

步骤：选择商品
  定位（任务配置中的商品） → 商品目标
  点击（商品目标）
  读取并核对（商品身份、价格、可兑换数量）

步骤：兑换并核对
  按任务配置和已观察事实核对数量、预算、保留余额
  定位并点击（本次允许的兑换操作）
  重新观察并核对（实际兑换结果）
```

该示例不假定游戏存在数量输入框、价格固定或点一次只兑换一件。实际动作组合由当前版本采样确定。数量来自schema对应配置，完成与消耗来自游戏结果。

## 4. 暂停与恢复保持简单

暂停仍属于唯一Executor。执行器不再发新动作，并如实等待旧输入静默。

- 继续：跳过已完成步骤，未完成步骤从入口重新执行动作编排；不保存动作调用栈或从第几个动作中途续跑。
- 重新开始：当前任务回到第一个步骤，其他任务进度不变。

未完成步骤重入时先观察当前实际状态。某次兑换可能已生效但尚未确认时，核对原动作结果，不因重入而盲目再点击。必要动作记录用来核对副作用，并非恢复动作中途进度。

动作类型与一次调用记录不同：类型说明“点击”这种能力；原架构的actionId标识某次实际调用，供回执／结果归因，不能拿同一个动作类型名作所有调用的去重键。

## 5. 云任务与壳的分工

已确认的制作与使用链路：

```text
App实现并提供动作能力
  → 开发者经GitHub授权与指定仓库权限核对后，在App编排步骤／任务、编辑配置schema
  → App生成任务JSON，开发者在App内调试
  → 明确上传，成功即发布指定GitHub仓库的新Release及任务附件
  → 用户在App从Release拉取并选择使用版本
  → 填写任务配置后提交任务执行，或将任务组合为定时计划
```

App不按每个游戏任务分别发版。动作能力新增或调整通过App更新；步骤／任务流程、配置schema、识别资源及已有动作的组合通过云端任务版本更新。用户不需要编写JSON或组装底层动作，计划由用户在App中组合。

任务制作应以选动作、填参数和试跑为主，JSON由App生成。上传即发布，不另设云端草稿或发布按钮；制作流程和同执行器调试提案见[App内任务制作](developer-task-authoring.md)。开启开发者模式本身不上传内容。

建议App注册动作标识与输入输出合同，任务JSON声明所需动作能力，装载时核对支持情况。具体字段与版本协议单独设计，不把这条分工扩展成插件市场或任意远程程序运行。

入队后锁定任务版本、配置及所需动作合同。旧任务缺少所需动作或参数不兼容时明确报告，不能把未知动作忽略成成功，也不偷偷下载任意代码补齐。

## 6. 进入实现前要验证

用同一动作集合表达领取、兑换和御魂处理的代表任务；记录哪里需要新动作、哪里只是新步骤／资源。验证输出引用和配置校验、步骤完成判定、条件／循环必要性、两种恢复方式，以及同APK更新步骤和识别资源。现有HTML／JS原型尚未具备这一动作层，不以旧测试代替这些验证。
