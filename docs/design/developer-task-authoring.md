# App 内任务制作、调试与上传发布

日期：2026-11-15。状态：制作、调试、GitHub授权保护及上传即发布仓库Release已由用户确认；下述编辑布局、授权实现及上传内部步骤为设计提案。当前原型尚未实现这些能力，没有真实上传或发布。

## 制作路径

开发者模式只面向项目负责人和其指定开发者。授权依据复用指定任务仓库的GitHub权限，不另维护授权码或自建开发者白名单。GitHub登录成功还须确认当前用户对该指定仓库的有效权限，不能用任意自有仓库或fork的写权限解锁。入口不再是任何人可直接开启的本地开关。

授权后提供“任务制作”和原有“开发诊断”。任务制作主流程保持为：

```text
新建任务／复制现有任务
  → 选择App支持的动作，填写参数并编排步骤
  → 编辑任务的用户配置字段
  → 在App内试跑和调试
  → 填写版本与更新说明，上传即发布到指定任务仓库Release
```

普通用户仍只拉取任务、填写任务配置、执行或组合计划。制作能力不放进普通任务配置页。

## 降低制作成本的编辑方式

建议以表单和有序列表为主，不要求作者手写完整JSON，也不先做复杂节点画布。

| 编辑对象 | 制作器提供什么 |
| --- | --- |
| 任务 | 名称、稳定身份、步骤列表及配置schema；可从已有任务复制修改 |
| 步骤 | 新增、复制、排序；一眼看到该阶段的动作顺序和完成依据 |
| 动作 | 从当前App动作目录选择，按动作输入合同生成参数表单；展示输出含义，选择已有配置或前序输出作为输入 |
| 配置schema | 字段名称、类型、必要约束与控件信息，用表单维护；无需重复手写JSON字段定义 |
| 识别资源 | 绑定任务所用的目标／素材引用，指出缺失资源和不兼容引用 |
| JSON | 从上述编辑内容生成，支持查看与校验；JSON是交付格式，普通制作流程不依赖代码编辑 |

“复制现有任务”“配置字段编辑”“动作输出选择”的具体控件是简洁交互建议，不据此冻结尚未设计的JSON字段名。新建独立任务与修改既有任务须保持稳定身份语义，不因复制覆盖原任务。

校验直接定位到步骤／动作／字段：缺参数、引用不存在、类型不匹配、资源缺失或当前App不支持某动作。静态校验通过只表示定义可解释，不表示真实游戏任务已验证。

## App 内调试

建议提供“试跑当前动作／步骤”和“运行当前任务”，配合暂停及两种恢复方式；调试页查看当前步骤、动作输入输出、识别截图／定位结果与错误位置。只展示排错需要的内容，不要求开发者先建立断点、变量监控窗口和独立调度配置。

调试使用制作中草稿的固定快照与测试配置，不必先上传才能验证。编辑草稿后再次试跑取得新快照，不在动作进行中偷换参数。试跑过程不自动修改用户原有任务配置或当前启用的云版本。

调试仍调用同一个Executor和App动作实现。建议进入调试前暂停托管并等待旧输入静默；明确调试期间只执行作者选择的任务／步骤／动作，托管队列不混跑。结束调试保留此前人工暂停，直到用户继续，不自动接管用户刚操作过的游戏。具体命令由同一执行器接收，不能另开一个不受暂停约束的输入入口。

有输入的试跑可能实际操作游戏，并非自动沙箱或无消耗预览；动作权限、账号、已保存的消费限制和未知结果核对仍有效。定位／观察结果可直接查看，点击／兑换等不能因开发模式绕过执行检查。继续仍从未完成步骤入口，重新开始仍只影响当前任务；不会为调试另建任务／计划暂停状态机。

## 上传即发布

用户已选择：**上传成功即成为云端可拉取的新版本，不设用户可管理的云端草稿或额外发布按钮。** 本地编辑／保存／调试不触发上传；只有作者明确上传才发布。

上传前在当前编辑流程内展示本次JSON、版本和更新说明，并完成定义校验；不额外增加审批流。发布成功返回已发布版本和时间。消费者仍按原规则启动／手动拉取、自行选择启用，作者发布不等于远程替用户切换版本或开始任务。

编辑单位是任务；已有产品的发布／启用单位是完整任务集版本。建议制作工作区保留原任务集的其他任务，上传时形成完整的新版本，不能只提交当前任务就无声丢掉其他任务。App应形成完整可验证的任务集附件上传Release，不能假定GitHub会合并任务JSON。附件组织字段尚待设计，不增加用户混搭任务版本的能力。

## GitHub授权与Release分发

已确认选择GitHub作为身份、权限和版本托管来源，替换此前自建发布接口的提案，不新建另一套云账号／授权平台。

| 所在位置 | 负责的内容 |
| --- | --- |
| App任务制作器 | 本地草稿、动作／步骤及schema编辑、校验、生成JSON、调试展示 |
| 唯一Executor | 解释草稿快照，执行调试命令及现有暂停／恢复，保持唯一游戏输入权 |
| App GitHub适配 | 授权登录、查询身份／指定仓库权限、创建Release与上传附件、拉取版本 |
| GitHub仓库权限 | 项目负责人通过仓库／组织团队权限指定开发者；GitHub执行实际写入鉴权 |
| GitHub Releases | 托管版本、更新说明、任务JSON与资源附件，供App拉取 |

普通任务使用不要求发布权限。公开任务仓库可匿名读取已发布版本；若选择私有仓库，则另需只读访问，不将读取者当成开发者。具体任务仓库尚未指定，本轮不创建仓库或授权应用。

### 推荐的授权实现

推荐先验证GitHub App用户授权＋Device Flow，限制安装仓库及所需权限；这是GitHub OAuth的一种接入，不是自建登录系统。使用用户访问令牌，权限受“该用户和GitHub App两者都具备的权限”约束，不用能代替任意用户发布的内置机器人令牌。Device Flow不需要把client_secret放进APK；若改用网页授权流程，不能仅因支持PKCE就推断其令牌交换不需要secret。具体应用注册、令牌有效期与授权UI尚未实施。[GitHub App用户授权](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)、[OAuth授权流程](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)

进入模式时查询已授权身份和指定任务仓库的权限；发布前检查当前令牌授权，最终以GitHub写入接口结果为准。标准write／maintain／admin可作为入口判断依据，读取／triage不等于发布授权；GitHub App权限、组织审批与仓库规则仍可能使发布受限。403／404／网络错误不能一概解释为该用户没被指定，更不能按成功开放。无有效授权时不开放开发者入口。[仓库权限API](https://docs.github.com/en/rest/collaborators/collaborators#get-repository-permissions-for-a-user)

授权保护覆盖正常App入口与真实Release发布；不承诺修改／Root后的APK无法伪造本地界面。发布仍由GitHub检查权限。离线授权缓存、失效后的本地编辑范围另行决定，不自行设每次联网或永久离线授权；授权失败不删除草稿，也不影响普通已缓存任务。令牌按现有秘密仓储保护，不进入任务JSON、日志或导出。

### Release与本地任务版本的对应

建议tag_name对应任务集版本，body对应changelog，published_at对应发布时间，assets存任务JSON及资源。具体附件文件名、内容摘要和标记格式待定；App只识别符合任务包合同的完整版本，不把源码压缩包或APK Release当任务版本。任务源使用GitHub明确latest及本地缓存信息，不用版本字符串排序猜最新；实际仓库和tag策略待配置。[Releases API](https://docs.github.com/en/rest/releases/releases)、[附件API](https://docs.github.com/en/rest/releases/assets)

一次“上传”由App完成Release创建、附件上传及发布，作者不再另点发布按钮。GitHub创建Release与上传assets是分开的请求，不能把第一步成功当作任务已完整发布。推荐在这一次操作内部临时用draft暂存、附件完整后自动转为published并设为latest；这是待评审的技术暂存方案，不是新增云端草稿工作流。若采用其他内部方案，也须避免把不完整任务集交给用户。

创建／更新Release所需令牌权限与用户仓库权限都须满足，细粒度权限主要为Contents write，特定tag／工作流规则可能还有要求。失败须保留旧可用版本和真实原因；响应丢失时查询该tag／release及附件状态，不盲目重复创建或覆盖既有发布。建议任务版本一经完整发布不再原地改内容，修复以新版本交付；GitHub自身不因此被假定已开启不可变Release功能。

GitHub API／附件请求沿用任务来源的代理范围；系统浏览器授权页受浏览器自身网络设置影响，不能承诺App代理自动控制它。本轮没有进行登录、令牌交换、仓库写入或Release发布；这些是功能设计，不是对当前账户的操作授权。

## 验证制作是否足够简单

用制作器实际完成一个领取任务及一个有配置和结果核对的任务：作者能通过选动作与填表生成任务，完成App内单步观察／试跑，看到错误位置，再上传为新版本；普通用户可拉取配置并执行。记录必须手写JSON或绕到App外的环节，据此修正编辑器，而不是只验证某个JSON文件可以解析。

再核对非指定GitHub用户无法正常进入模式／发布、只读权限／权限撤销／令牌失效／网络未知的区别，以及调试与托管不并发输入、草稿修改不污染在途执行、上传即发布但不替用户启用、原任务集其他内容保留、失败及凭据处理。现有72个内存情境和512项浏览器检查均不覆盖这些新增制作／调试／发布能力。
