# 重出原型的架构契约复核

日期：2026-11-15<br>
最新依据：完整产品蓝图 v1.2、系统架构 v0.4 及任务容器架构 v0.2。以下记录按原型增量复核，范围为设计一致性，不涉及生产开发。

## 必须保持的契约

| 项目 | 契约 |
| --- | --- |
| 常用项 | 由原任务／计划的 common 属性派生；一个开关，没有独立收藏、快捷排序或添加流程；不复制规则、不启用计划 |
| 当前场景 | 可开始、不可开始、未知三态；依据场景、环境及规则版本；正常导航可达属于可开始依据，不做页面等名过滤 |
| 过滤副作用 | 只改变候选显示，不导航、不改 common、不启动；变化后旧判定失效，执行前重新核对 |
| 当前运行 | 由 runId 独立呈现，暂停／继续／停止不因候选过滤消失，也不因普通任务页面不可开始而丢失控制 |
| 忙碌与暂停 | 不隐式排队、替换或并发；暂停仍是原运行，不提示暂停后即可切换 |
| 普通与诊断 | 普通界面没有主题或可执行性矩阵；开发诊断只观察依据，不赋权、不强制执行、不默认新增采集 |
| 配置修正 | 错误定位真实配置；保存后仍待验证，不自动恢复或重做，不抹除未知游戏结果 |
| 模型与通知 | 模型失败不能冒充业务失败；通知投递与游戏结果独立，投递成功不等于问题修复 |
| 演示边界 | 内存场景、模拟调用和模拟运行只证明交互，不证明 Android、真实服务、识别或常驻能力 |

## 原型场景验收

1. 在任务和计划上分别开关常用，悬浮列表同步变化，周期启用状态不变。
2. 同一实体换规则后，立即执行引用新已保存规则；删除或缺失引用不会执行旧副本。
3. 当前页没有目标入口，但示例导航路径明确可达，任务仍可作为候选；确实不能开始时隐藏候选。
4. 切至未知场景后出现识别中或未知说明，不把它显示成已确认无任务。
5. 一个运行正在进行，切到不支持或未知场景，当前运行控制仍在且精确关联原 runId。
6. 暂停后点击其他任务立即执行，不产生第二运行、隐式排队或替换；普通提示不引导“暂停后切换”。
7. 开关开发诊断仅改变信息可见性，不改变上述结果或资源限制。
8. 修改模型密钥、任务目标或通知配置并保存后，关联问题保持待验证，原运行不自动重做；unknown 仍为 unknown。
9. 通知模拟失败时已完成的游戏结果不变；模型配置错误不冒充游戏资源耗尽或任务完成。
10. 原型说明明确使用内存演示数据，不以画面显示“可用”或模拟运行完成宣称真实 Android／24 小时验证通过。

## 验证记录

架构文档已按上述契约修正。新原型 app-v2.html 由 UI agent 独占编辑；本复核不修改 HTML。

已对原型源码只读检查，并在独立 Node VM 中以惰性 DOM 与模拟定时器执行原型内存逻辑，未连接浏览器、Android、游戏、模型或通知服务。检查结果：

| 项目 | 结果 |
| --- | --- |
| common 同源与周期启用独立 | 通过；切换原计划 common 不改变 enabled |
| 场景三态与正常导航示例 | 通过内存示例；未知画面为 unknown，庭院到商店为 ready。此映射不是游戏导航实测 |
| 计划资格 | 源码汇总全部引用任务的示例条件，不以任一匹配放行；真实计划入口与导航仍须按技能实现验证 |
| 暂停与忙碌 | 通过；暂停待确认后仍保留 run，新立即执行返回 busy，不替换或排队 |
| 过滤与当前运行独立 | 通过；切到未知场景后候选为空，当前运行的停止入口仍存在 |
| 未知消费结果 | 通过；相关任务被阻止，配置保存和模拟模型验证未清除待核对问题 |
| 模型与通知分离 | 源码分别维护 issues、history、deliveries；通知测试只新增模拟投递，不改变游戏结果 |
| 诊断与脱敏 | 诊断仅生成已有观察的视图；getState 未导出测试密钥，渠道目标和凭据在状态接口中收敛为配置标记 |
| A 悬浮形态重复控制 | 已修并复核；常用展开面板不再重复当前控制，运行中 A 形态展开后的暂停按钮计数由 2 变为 1 |
| 自定义模型连接与密钥归属 | 已修并复核；保存完整 provider／region／base／model／protocol／presetVersion，密钥绑定连接。自定义地址改变且未重填密钥时，模拟验证与启用保存均被阻止，原已保存连接保持不变 |

UI agent 修复上述两项后，已重新执行内存逻辑检查，并补验诊断视图不会修改运行／任务／计划／能力，通知测试不改变游戏结果，状态快照不导出模拟密钥或自定义服务地址，未知消费结果仍为待核对。复核全程未编辑 HTML。

本记录不代替主 agent 的浏览器全量交互与布局检查；未完成的 Android 和真实服务验证不得记为通过。

## 云端任务容器增量复核

用户明确容器与云任务方向后，系统架构已补充 TaskCatalogEntry、TaskPackageManifest、ActivationSet、RunPackageLock，详细方案见[任务容器架构](task-container-architecture.md)。包格式、自动拉取周期与自动激活并未获实现批准。

对 app-v2.html 的任务包增量再次进行源码只读和独立 Node VM 内存检查，结果如下：

| 场景 | 内存原型结果 |
| --- | --- |
| 云目录失败但已有包 | 保留示例包版本，已缓存本地任务仍为 ready；没有把网络失败当作下架 |
| 断网且从未缓存 | 返回 blocked，并说明网络失败和暂无缓存，不伪造可用任务 |
| 新包不兼容 | 获取新包不可用，旧激活版本仍保留 |
| 当前运行时检查及下载 | 新包为待启用，run.packageVersion 保持开始版本，启用返回 busy |
| 暂停时启用 | 仍返回 busy，不把暂停当作可以替换任务版本 |
| 停止后 | 旧激活版本仍在，新包保持待启用，没有自动激活 |
| 用户再显式启用 | 激活版本改变；tasks、common、plans 和 issues 保持；未知兑换仍待核对 |

这只证明版本显示和交互状态。示例在内存中保存一个简化包版本，任务数据仍是演示夹具；真实 manifest／签名／digest／依赖验证、下载与持久离线存储、参数迁移、解释执行及回滚未实现、未验证。原型的“待启用”和忙碌限制是评审演示，不冻结最终激活策略。
