# 阴阳师助手首期产品需求 草案

版本：0.3<br>
日期：2026-11-15<br>
状态：保留为需求资料，首期范围暂缓冻结。现先确认[完整产品蓝图](PRD.md)，再划分各期；本文已记录需求不被删除，也不自动归入或移出某一期。本文中的“首期建议”及验收细则均为提案，确认前不作为实现授权。

本产品面向希望减少游戏重复操作的阴阳师玩家，支持长期运行、任务按需启用、可选云端视觉模型，并重点解决更换主题后识别失效的问题。长期目标覆盖各类任务和活动，尽量自主理解新活动，减少人工适配。

首期建议交付可实际使用的常驻助手，并验证跨主题识别和新活动自主处理能力。功能按清单验收，不以“支持全部任务”代替可核对的范围。首期结束不代表长期覆盖目标完成。

## 二 问题与产品目标

用户不满意现有方案对特定主题、图像素材和预设流程的依赖。任务数量多不能单独证明长期运行可靠：登录中断、弹窗、界面变化、识别时序和完成判定错误，都可能造成卡住、漏做或重复执行。

已有项目提供了可参考的游戏流程和资源，但历史 issue 不等同于当前版本的缺陷清单。已有成果、报告及证据边界见[开源项目调研](research/onmyoji-automation-survey.md)。

首期需要回答四个产品问题：

1. 不配置云端模型时，用户能否实际完成一组有价值的任务？
2. 更换主题后，相同任务能否继续工作，而不要求用户重新编写流程？
3. 开启云端模型后，能否处理至少一个未预先编写专用流程的新活动场景？
4. 长期运行遇到中断或未知结果时，能否准确呈现状态，避免误判完成与重复消耗？

## 三 首期建议范围

### 3.1 交付平台

优先交付 Android App，目标是在安卓手机或 Windows 安卓模拟器中安装助手与游戏，由助手在同一 Android 环境内执行任务。Windows 使用方式优先复用 Android 应用，不单独建设 Windows 原生应用。

此方向来自用户的平台偏好，仍需后续技术方案验证：能够安装 APK 不代表截图、输入和长期运行能力在真机及模拟器上均已成立。支持的 Android 版本、设备及模拟器清单应依据验证结果确定，不承诺所有环境通用。

技术方案应明确截图与操作所需授权、长期运行条件、被系统中断后的恢复方式，以及是否依赖 Root、调试工具或外部电脑辅助。上述实现条件目前均未确定；如无法实现预期的 Android 独立运行，应说明限制并回到范围评审，不静默改成由电脑端程序控制。

### 3.2 运行与任务管理

首期建议包含以下用户能力：

- 查看当前连接的游戏环境、当前任务、下一项任务和待处理问题。
- 逐项启用或停用任务，查看每项任务的支持条件和所需能力。
- 为任务设置目标和执行条件；涉及次数、时间、资源的具体字段与默认值，在任务清单确认时定义。
- 开始、暂停、继续和停止运行，清楚呈现控制是否已生效。
- 查看任务记录、完成依据及异常发生时的必要截图和说明。
- 在启动和恢复时辨认当前游戏状态，不假定游戏始终停留在庭院。

24 小时常驻期间允许等待任务时间、游戏维护或用户处理。任务调度优先级、抢占、错过时间后的补做和自动启动规则均待确认，不由实现人员自行补充默认行为。

### 3.3 游戏任务覆盖清单

首期按日常、物资领取、商店兑换、御魂管理、副本及活动等类别建立能力清单，而不是只交付演示任务。用户已明确要求纳入物资领取、商店兑换和御魂强化整理；其他项目仍为待确认候选。下表不是当前游戏完整功能目录，详细规则见 3.9 节。

| 任务类别 | 首期候选 | 无模型能力建议 | 必须明确的边界 |
| --- | --- | --- | --- |
| 日常基础任务 | 签到与日常奖励、花合战领取、悬赏封印、宠物相关任务 | 已适配的个人任务可独立执行 | 领取与主动完成分别列项；区分个人任务和需要其他玩家配合的协作任务 |
| 周期物资领取（已要求纳入） | 每日／每周可领取物资、永久勾玉卡产出 | 建议作为本地独立运行能力 | 区分未拥有、未到领取时间、已领取、可领取和识别失败；逐项确定物资清单与周期 |
| 商店兑换（已要求纳入） | 商店物资兑换、用户所指周三／周六商店 | 建议已适配兑换流程可独立运行 | 明确商店与商品、支付资源、数量、限额、开放和刷新条件；不擅自替换商品或追加消费 |
| 御魂管理（已要求纳入） | 御魂强化、御魂整理 | 建议按明确规则在本地独立执行 | 明确目标御魂、强化目标、素材、预算和整理方式；不自行扩展到处置有价值御魂 |
| 重复副本 | 御魂、觉醒、探索、御灵 | 已适配的单人副本可独立执行 | 副本种类、难度、单人或组队、次数及资源限制分别明确 |
| 结界与阴阳寮 | 结界收取与挂卡、个人与寮突破 | 已适配流程可独立执行 | 卡片选择、好友相关操作、失败处理属于独立产品决策 |
| 周期与定时玩法 | 逢魔、狩猎战及其他周期任务 | 已适配流程可独立执行 | 时间窗口、资格条件、错过后的处理和是否支持战斗分别明确 |
| 限时活动 | 当期活动的规则理解、目标选择及执行 | 已适配活动可运行；未适配新活动的自主理解依赖云端模型 | 区分活动内重复战斗、奖励领取和需要新策略的玩法 |

范围确认时，每项被选任务需形成独立记录，至少包含：

| 字段 | 需要说明的内容 |
| --- | --- |
| 任务目标 | 哪个具体结果算完成；只领取还是包含主动获取奖励 |
| 运行前提 | 区服、游戏环境、等级与玩法解锁、队伍准备、资源条件 |
| 执行方式 | 单人、组队；需要云端模型或可在本地独立运行 |
| 用户设置 | 启用条件、目标、停止条件；默认值须经确认 |
| 资源与账号影响 | 可能消耗的体力、门票、货币，以及更换阵容等副作用 |
| 支持状态 | 已验证、部分支持、待适配；分别记录环境与主题条件 |
| 验收依据 | 开始条件、实际游戏结果、异常与恢复场景 |

首期交付清单和关闭模型后可用清单必须在开发前冻结。技术调查发现某项无法满足时，应回到范围评审，不得静默移除或换成同名但更窄的能力。

### 3.4 跨主题识别

用户更换主题后，已支持任务应尽量直接继续工作，无需重新配置一整套任务。识别差异应由产品内部处理，不能要求普通用户编辑坐标、截图模板或脚本。

首期建议覆盖庭院主题，以及所选任务涉及的战斗、结算和功能页面主题差异。不同主题可能同时改变图标、布局、文字外观、背景和动画，验收不能只更换背景图片。

需要分别展示与验证两种能力：

- 已验证主题：列明支持条件，在相同任务上达到一致的完成和停止行为。
- 未预先适配主题：评估是否可以识别并继续；无法确定时正确报告未知状态，不把最相似的页面当作确定结果。

开启和关闭模型的主题支持范围允许不同，但必须可见。不能以开启模型后的成功代替本地模式验收，也不能将“支持多套主题”描述为“任意主题必定可用”。

识别采用何种算法、是否需要主题资源、如何组合文字与图像等，属于后续技术方案。

### 3.5 可选云端视觉模型

设置界面应允许配置服务地址、模型名称及认证信息，并提供连接与视觉能力验证结果。具体协议与首批兼容服务留待技术方案验证。

产品需要向用户区分以下情况：未启用模型、已启用且可用、配置错误、网络不可用、服务限流、响应无法使用。错误信息不得显示完整密钥。

模型未启用时，基础功能应可独立使用；需要模型的功能应明确说明依赖。模型在运行中失效时，不得把无法理解的任务标记为完成。是否等待、切换本地能力或停止该任务，属于待确认的恢复规则。

用户应能了解哪些操作需要向云端发送游戏截图，以及当前模型调用状态。调用费用无法在缺乏服务商价格信息时准确推算；如展示消耗，应区分实际返回用量和估算值。模型调用预算、上限及默认值待确认。

### 3.6 新活动自主处理

首期建议将新活动能力作为必须验证的产品能力，而非仅保留菜单入口：

1. 从游戏中获取规则、入口、奖励和可用资源等信息。
2. 说明对活动目标、完成条件及资源消耗的理解。
3. 在用户启用的任务目标与操作范围内执行。
4. 检查每一步结果，并区分活动完成、阶段完成、等待与无法继续。
5. 展示无法判断的条件，使用户能够接管。

需要先定义自主行动边界：首次执行新活动是否需要确认计划、哪些操作可直接执行、何种情况必须暂停。这些规则不能因启用模型而被自动扩大。

首期以未预先编写该活动专用流程的实测场景验收。使用现成爬塔流程替换图片后运行，只能算活动适配，不能单独证明自主理解新玩法。

新界面理解与策略求解分别验收。能够读懂规则，不代表能够自主找到复杂玩法的最优策略；具体支持活动类型、策略要求和验证样本须在范围评审中确定。

### 3.7 长期运行与异常处理

用户应能区分：等待执行、执行中、暂停、完成、已达到停止条件、执行失败、结果未知、需要人工处理。最终展示用词可由 UI 方案优化，但不同含义不能混为一项。

异常场景至少覆盖：连接中断、游戏退出、掉线回登录界面、弹窗遮挡、资源不足、任务资格不足、云端不可用和页面无法识别。

恢复后需要核对游戏内进度，不能因为本地记录未写入就重新执行可能消耗资源的动作。对于无法确认是否执行成功的操作，应保留未知结果；具体接管和重试规则待确认。

自动重启游戏、重新登录、重连次数、自动重试、跨任务继续和通知均为独立产品决策，本草案未授权启用。

### 3.8 游戏更新适应

区分三类变化，分别呈现支持状况：

- 外观变化：主题、图标、文字外观和局部位置变化。
- 流程变化：入口迁移、额外确认步骤、页面结构或完成条件变化。
- 新玩法：新的活动规则、资源、目标及策略。

首期需要验证前述跨主题能力及新活动能力，并识别无法兼容的变化。任务资源和程序更新的获取、安装、验证及回退方式由后续方案设计；自动下载安装、后台替换程序或自动接受新任务不属于已确认行为。

### 3.9 物资领取 商店兑换与御魂管理

以下功能已由用户明确要求进入首期范围。具体对象、周期和操作规则仍需补齐，不将功能纳入理解为允许任意消费或处置。

**每日与每周物资领取**

- 建立可逐项启用的领取清单，包含永久勾玉卡产出领取；卡片产出的领取与购买卡片分开，当前只明确要求领取。
- 展示每项是否具备领取资格、是否可领取、是否已领取，以及本周期处理结果。未拥有相关权益和页面识别失败不能视为同一状态。
- 按各项实际领取和刷新周期处理，不假定所有物资均在同一时间重置。周期、游戏时区和错过后的处理方式待核对与确认。
- 以领取后的游戏状态确认结果；中断后先核对是否已领取，不能仅根据本地日期推断完成。

**商店物资兑换**

- 支持用户选择商店、商品、数量及兑换条件，区分一般商店和用户指定的周三／周六商店。
- 周三／周六商店先保留用户称呼，正式商店名称、商品和开放时间需核对，不自行映射到某一玩法或固定重置时刻。
- 每项兑换应明确支付资源、单项数量、周期限额，以及必要的余额保留或预算设置。具体字段和默认值待确认。
- 商品缺货、未开放、余额不足、已达限额和无法识别分别呈现。价格、支付资源或商品变化时的处理规则需明确；不能由 AI 自行更换商品、追加预算或刷新商店。
- 兑换结果未知时，先核对库存、限购或余额等游戏证据，再按确认规则决定是否继续，避免重复兑换。

**御魂强化**

- 支持指定御魂或明确的筛选条件、目标等级或阶段，以及使用的强化素材和资源预算。
- 是否根据强化后的属性决定继续或停止，列为独立规则；本稿不预设评分公式、属性偏好或淘汰阈值。
- 强化后核对实际等级、属性和资源变化。中断后先恢复到实际状态，不能重复按旧等级执行。
- 哪些御魂可作为素材、锁定或装备中御魂如何保护，须在执行规则中明确，不因模型判断“价值低”而自行消耗。

**御魂整理**

- 支持基于用户规则筛选并展示处理对象，明确保留与排除条件。
- “整理”需要进一步确定具体操作：筛选查看、锁定／解锁、分组标记，以及弃置、奉纳或作为素材等消耗性处理应分别确认；不能以一个整理开关默认涵盖所有操作。
- 展示命中规则与拟处理对象，并为需要确认的操作提供可检查的依据；是否每次预览确认、哪些规则允许无人值守执行，待用户确认。
- 强化与整理联动时，不得让待判断的御魂被另一个任务提前消耗；中断恢复后重新核对实际对象和状态。

以上功能建议均具备不依赖云端模型的已适配执行路径。云端可辅助理解陌生界面，但不替代用户的兑换、强化或整理规则。

## 四 主要用户流程

### 首次使用

在安卓手机或 Windows 安卓模拟器安装助手 → 完成必要的环境检查与用户授权 → 验证同环境内游戏截图与操作能力 → 可选配置云端视觉模型 → 查看当前可用任务及条件 → 按需启用任务并设置目标 → 开始运行。

### 日常运行

查看当前任务及计划 → 执行已启用任务 → 验证游戏结果 → 记录结果或等待下一项任务。用户可随时发起暂停或停止，并看到实际生效状态。

### 更换主题

用户在游戏内更换主题 → 助手重新确认页面与目标 → 支持时继续执行相同任务 → 无法确认时显示受影响任务与原因。不得无依据宣布主题已兼容。

### 新活动

用户启用活动目标 → 助手理解规则与执行条件 → 按确认后的自主行动边界执行 → 展示进度、结果或需要接管的原因。

### 异常接管

助手显示异常及已知进度 → 用户查看当前游戏和必要记录 → 用户处理后继续或停止 → 助手核对当前状态后决定能否继续，避免重复消耗。

## 五 界面内容要求

以下定义用户需要获得的信息，不规定导航结构、卡片形式、配色或页面排版，交由 UI 子 agent 设计。

| 功能区域 | 必须呈现的信息或操作 |
| --- | --- |
| 运行概览 | 游戏连接、运行状态、当前任务、下一任务、待处理问题、开始与暂停及停止 |
| 任务配置 | 分类、启用状态、目标与条件、模型依赖、支持限制、单项执行结果 |
| 物资与商店 | 领取资格及周期、已领取状态、商店开放状态、商品与支付资源、兑换数量及限额、执行结果 |
| 御魂管理 | 筛选与保留规则、强化目标、素材与预算、整理操作、处理对象及需要确认的影响 |
| 活动处理 | 规则理解、执行目标、资源影响、当前阶段、无法判断的条件 |
| 运行记录 | 时间、任务、实际结果、停止原因、必要证据；可区分失败和结果未知 |
| 设置 | Android 运行环境与授权状态、可选云端视觉模型、连接测试、主题支持情况、经确认的运行规则 |

运行中修改配置何时生效、是否中断当前任务，需要在范围评审中确定。不得出现界面显示已停用、后台仍按旧配置持续刷取却没有提示的状态。

## 六 首期验收建议

以下为可评审的验收提案。具体任务、主题、活动样本及性能数值在范围确认时补齐，未填写前不能宣布首期范围已冻结。

| 编号 | 验收场景 | 通过条件 |
| --- | --- | --- |
| A1 | 不配置云端模型首次使用 | 基础任务清单内的任务可实际执行；模型依赖功能有清晰说明 |
| A2 | 按需启用 | 仅执行用户启用且满足条件的任务；配置生效时间可见 |
| A3 | 任务完成判定 | 以游戏内目标状态验证完成；不能以点击过按钮、流程退出或无报错替代 |
| A4 | 已验证主题切换 | 建议至少两套存在实际界面差异的主题，执行同一组关键任务；本地和模型模式分别记录 |
| A5 | 未适配主题 | 建议至少一套未用于专项适配的主题，记录成功与失败；无法识别时不误判、不误操作 |
| A6 | 新活动自主处理 | 建议至少一个未写专用流程的活动场景，验证规则理解、目标执行和结果判断；记录人工介入与专用修改 |
| A7 | 长期运行 | 在首期支持的安卓真机与 Windows 安卓模拟器代表环境中，分别连续运行至少 24 小时，包含等待、任务切换和重复执行；记录漏做、重复、卡住、人工介入及资源变化 |
| A8 | 中断恢复 | 按确认策略处理连接中断、游戏退出及登录页；恢复后不无依据重复有资源影响的操作 |
| A9 | 云端失效 | 区分鉴权、网络、限流和响应问题；可独立运行的任务按确认策略处理；不泄露密钥 |
| A10 | 暂停与停止 | 用户控制能在约定时限内生效；不能仅改变界面状态，后台继续发出新的游戏操作 |
| A11 | 弹窗与资源不足 | 不无限循环、不错误标记完成，说明停止或等待原因 |
| A12 | 游戏版本变化 | 用外观或流程变化样本验证兼容与不兼容结果；未知状态可见，不能静默继续错误流程 |
| A13 | Android 安装与授权 | 在支持清单内的真机和模拟器完成安装、环境检查与所需授权；授权拒绝或撤销时准确说明受影响能力，不误报可运行 |
| A14 | 周期物资领取 | 覆盖永久勾玉卡产出、每日和每周清单；正确区分资格、可领取及已领取，跨周期和中断后不漏判或重复标记 |
| A15 | 商店兑换 | 覆盖一般商店与用户指定周三／周六商店，按确认商品、数量和支付资源执行；未开放、缺货、余额不足及未知结果均有明确处理，不超限兑换 |
| A16 | 御魂强化 | 命中指定对象，遵守素材、强化目标与预算，正确核对强化结果和中断后的实际状态 |
| A17 | 御魂整理 | 筛选与保留规则生效，处理对象和执行结果可核查；未经授权的处置不能因启用整理而执行，强化与整理联动不误消耗对象 |

验证分为离线截图验证、可控中断测试和目标设备实测。截图识别通过不能代替真实游戏交互；24 小时单次通过也不能推导任意环境下持续可靠。

首期质量报告应给出实测分母：任务尝试与成功次数、漏做与重复次数、人工介入次数、各主题表现、模型调用量及已知限制。成功率、操作延迟、CPU 与内存、调用预算等数值目标待验证设备和方案确定后评审，不在此虚设。

## 七 需要用户确认的范围

| 决策 | 本稿建议或待选内容 | 对范围的影响 |
| --- | --- | --- |
| D1 首发平台 | 已确认 Android App 优先，目标同时适用于安卓手机和 Windows 安卓模拟器；具体兼容环境及必要授权待方案验证 | 优先复用 Android 应用；如存在阻碍，说明证据并重新评审平台方案 |
| D2 首期任务 | 已要求纳入每日／每周物资、永久勾玉卡产出、商店兑换、周三／周六商店、御魂强化与整理；补齐具体清单，并确认其他候选任务 | 决定真实开发量，不能只按大类宣称覆盖 |
| D3 无模型任务 | 为 D2 中每项确定是否必须本地独立运行 | 决定基本可用性与模型依赖 |
| D4 主题标准 | 建议已适配多主题加未适配主题的单独验证，两个模式分别验收 | 决定“换主题可用”的可检验范围 |
| D5 新活动自主程度 | 确定活动类型、目标、首次计划是否确认及可直接执行的操作 | 决定自主行动边界和验收样本 |
| D6 资源及账号操作 | 细化已纳入的商店兑换商品与限额、御魂强化目标与素材及预算、整理保留规则与具体操作；其他体力、门票、货币、式神、阵容及社交操作分别确认 | 防止“启用任务”被解释为允许任意资源操作 |
| D7 常驻和恢复规则 | 确定调度、补做、重连、重启、重试、跨任务继续及配置生效规则 | 决定长时运行的具体行为 |
| D8 模型与数据 | 确定调用预算、截图发送范围、记录留存与清理方式 | 决定费用和设置体验 |

已确认某项后应在后续稿中直接记录结果，避免在设计和实现阶段重复询问。未确认项只暂停依赖它的工作。

## 八 本轮不做的工作

本轮只交付 PRD 草案，不编写程序，不确定技术栈、框架、识别算法、存储或模型协议，不操作真实游戏账号，不发布和部署。

商店物资兑换与御魂强化整理已纳入功能范围，其具体消费和处理规则仍待确认。额外购买（如购买永久勾玉卡）、式神处置、多账号、远程控制、外部消息通知、开机自启、自动安装更新等未由当前需求确认，不能作为附带功能自行加入。是否纳入首期应明确评审；这里不代表永久排除。

## 九 范围确认后的子 agent 分工

用户确认范围后再启动三个独立子 agent，输入相同版本的 PRD，不在本轮提前开展设计。

| 子 agent | 责任 | 交付物 |
| --- | --- | --- |
| 系统架构 | 独立负责首次系统建设的整体结构、模块职责、状态所有权、数据和控制路径、任务生命周期、扩展与恢复边界 | 系统架构方案、关键接口与状态契约、关键权衡和验证风险 |
| 技术方案 | 比较执行环境、图像与文字识别、模型接入、开源成果复用、打包运行及验证方法；用证据验证可行性 | 候选比较、建议技术选型、验证实验、成本与限制、实施拆解 |
| UI 排版 | 根据已确认用户流程设计信息架构、页面排版、任务配置、模型设置和各种运行状态 | 页面结构、主要页面布局、交互与异常状态说明 |

三者分别承担责任，但不能产生互不一致的产品行为。系统架构与技术方案应对齐边界和契约，UI 需反馈用户流程对底层的要求；主 agent 汇总冲突并进行完整审查。超出 PRD 的行为或范围变化回到用户确认，不因某一方案推荐而自动获批。

设计方案完成并评审后再进入开发。首次系统建设必须有独立架构交付物，不能用技术选型列表或 UI 页面清单替代。
