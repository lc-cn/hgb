# 数据结构审视：动作 → 步骤 → 任务 → 计划（2026-11-18）

按用户要求，从效率和体积两方面逐层检查，并测量了能测量的部分。项目尚未公开使用，按约定**不做数据迁移，也不保留旧格式兼容**：Room 结构变化时直接重建数据库。

## 逐层结论

| 层 | 数据 | 测得规模 | 问题与处理 |
| --- | --- | --- | --- |
| 动作（运行时） | 观察结果、目标、区域、像素 | 每帧原始 RGBA 约 10MB | **已处理**：像素不再挂在观察对象上，而是按帧单独保存，最多保留最近 2 帧，输入时清空。更早的帧只保留识别出的文字；需要像素的区域请求会明确报“像素已释放”，不会去用更新的画面。点击前临时截的帧不入表，用完即释放。 |
| 动作（诊断） | `action_traces` | 每条几百字节，只保留最近 5000 条 | 合理。写入走异步通道，失败不影响执行。 |
| 步骤 | 程序结构（动作、分支、计次重复、until 循环） | 草稿任务包 11KB（两个任务、约 40 个动作） | 解析与校验开销可以忽略。JSON 写法偏冗长（绑定为对象形式），但体积不是瓶颈，暂不引入简写，以免带来第二种语法。 |
| 任务（包与资源） | 任务包 JSON 加 Release 附件 | 资源 31MB，几乎全是识别模型 | **已处理**：资源按摘要存储且本来就去重，但每次安装新版本时仍会先把所有附件下载一遍。现在本地已有、且摘要校验通过的资源直接跳过下载，提交新版本前再校验一次。之后发布新版本时，模型不变就不用再下载 31MB。 |
| 计划／执行（持久化） | 执行器状态：整份 JSON 存在一行里，每次状态变化都重写并计算摘要 | 改前每完成 1 次运行约增加 3.2KB，600 次后 1.9MB，且线性增长 | **已处理**：发布状态前统一压缩，运行事实只保留最近 300 条，命令去重表最多 256 条，尝试记录只保留当前、排队、执行中、结果未知的运行和最近 20 次运行。实测 100 次后约 112KB，600 次后约 168KB，不再增长。完整历史在同一事务中按编号增量追加到只追加的 `execution_facts` 表（自增主键）。 |
| 计划（定义） | `ExecutionRequest` 内含各任务快照与配置 JSON | 每次提交一份 | 合理。计划的定时规则尚未实现，届时再按同样原则设计：定义与运行历史分开，状态只保留活动部分。 |

## 涉及的测试

- core：
  - `ExecutorStateGrowthTest`：600 次运行后，状态不超过 100 次时的两倍；
  - 结果未知的运行，在之后又跑了 30 次的情况下仍可核对；
  - 已清掉的旧运行收到迟到结果时，直接忽略；
  - 去重表仍能识别最近的重复命令；
  - 压缩后状态能完整往返（序列化再恢复一致）。
- app：
  - 历史表在同一事务中恰好收到新增事实，没有新事实的状态变化不写入，重开数据库后仍在；
  - 资源去重沿用现有版本库测试；
  - 像素保留由运行时与区域测试覆盖。

## 已删除的兼容负担

- Room 1→6 的全部迁移代码，三个迁移测试，第 1–5 版架构文件。数据库改为结构变化时直接重建，手机装新构建后需要重新拉取任务版本、重新配置；GitHub 登录存放在单独的加密文件里，不受影响。

## 还可以继续做的

- 执行器状态里的每条运行事实都带完整的执行上下文和版本号，存在重复，可以改为按运行引用，状态还能再小约一半。
- 历史页目前读的是状态里最近的 300 条事实，之后应改为从 `execution_facts` 分页读取，这样状态里的事实上限还可以再调低。
- 执行器状态 JSON 里仍保留第 1 种格式的读取分支。按“发布前不兼容”的约定可以删除，但它在核心恢复路径上，删除前要先补足恢复测试，所以单独处理。
