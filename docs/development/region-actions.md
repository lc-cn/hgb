# 区域与图像状态动作

2026-11-18 实施，依据[区域状态动作提案](../design/region-state-actions-proposal.md)及其[离线实验](build-evidence/region-state/README.md)。实施前先做了三处结构调整，下面一并说明。

## 先做的结构调整

**类型化句柄（core）。** `CapabilityContract` 新增 `outputHandles`／`inputHandles`。观察、目标、区域都是句柄：只能通过前序动作输出绑定传入，不能用常量或配置；任何可能的输入之后失效；不能作为普通参数传递或参与分支比较。`HandleRequirement.forbiddenAncestors` 按任意深度检查来源链。原先 `ScreenActions` 里逐个动作手写的“必须引用当前输入阶段的前序观察”规则全部改为声明。规则在 core 统一校验，见 `handleIssues`。

**任务包视觉配置。** `TaskBundle.visionProfiles` 为每个目标声明一次截图包名、识别合同和模型资源。core 校验目标、包名和资源引用；识别合同与模型角色由 APK 校验。没有视觉配置的旧任务包写出时不带该字段，字节不变。

**`screen.readText` 升到 v2。** 输入只有 `profile`。v1（每次重复写包名和三个模型）已移除。尚未发布过任何正式任务，所以没有兼容负担。

**识别子进程改为复用（不常驻）。** 实测冷启动：模拟器每次观察 370–570ms，真机 865–966ms；真机子进程识别时 PSS 约 275–286MB。用户决定不常驻，改为复用：
- 正常完成的请求在子进程写完结果、关闭全部输入、交还所有权后发 `IDLE`，宿主以此（`child-idle`）作为静默证据并释放模型租约，子进程保持加载；
- 子进程按三份模型的长度与摘要缓存已加载会话，摘要不变时跳过复制和加载；
- 拒绝、取消、协议错误、无法读取的结果和崩溃，仍结束子进程并以 Binder 死亡为静默证据，失败后的原生状态不复用；
- 空闲 20 秒后宿主解除绑定，子进程自行退出；必须观察到旧进程死亡后才绑定新进程，避免连到正在退出的进程。宿主进程死亡时子进程也随之结束。

复用后模拟器单次观察约 258ms。

**结构化 trace。** `ActionResult` 的 Produced／Verified／Unavailable 可带一个 `trace` JSON，只记录区域、得分、模板摘要、候选数量等，不含像素、识别文字或账号值。格式由产出它的动作定义；**目前还没有持久化**，任何逻辑都不能依赖它。

## 动作合同

| 动作 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| `screen.readText` v2 | `profile` | `observation`（句柄） | 观察时保留本帧 PNG，供本次尝试中的区域请求复用，不另行截图 |
| `screen.deriveRegion` v1 | `target`（句柄）、`dx`、`dy`、`width`、`height`、`referenceWidth`、`referenceHeight`（整数常量） | `region`（句柄） | 偏移相对锚点水平中心和底边；按当前帧与参考尺寸缩放；宽高比相差超过 1% 或区域超出画面时判为无法确认 |
| `screen.readRegionText` v1 | `region` | `observation`（句柄，来源链含区域） | 只识别区域内文字，现有 `expectText`／`locateText`／`classifyText` 都可以直接引用 |
| `screen.matchImage` v1 | `region`、`template`（已声明资源）、`minimumScore` | `matched`、`score` | Maa 归一化相关系数，取区域内最高分 |
| `screen.classifyRegion` v1 | `region`、`states` | `state` | 每个状态可组合 `text`（需出现的文字）、`present`（需出现的图像）、`absent`（需缺失的图像），至少一个条件；恰好一个状态成立才输出，否则无法确认并给出得分 |

另有两个输入动作，与 `screen.tap` 一样在输入前于新截图中重新唯一定位目标，并写入动作意图与回执：

| 动作 | 输入 | 说明 |
| --- | --- | --- |
| `screen.longPress` v1 | `target`、`durationMs` | 在目标中心按住指定毫秒 |
| `screen.swipe` v1 | `target`、`durationMs`、`dx`、`dy`、`referenceWidth`、`referenceHeight`、`variation` | 从目标起按缩放位移单笔拖动；位移不能为零，路径任一点超出画面或宽高比不符时不输入 |

| `screen.back` v1 | `observation`（句柄） | 系统返回键。先重新截图，确认观察所属应用仍在前台，再在同一输入所有权、画面与前台检查下调用 `GLOBAL_ACTION_BACK`。系统接受返回键只说明按键已送出，业务效果仍须之后重新观察核对。**实测：在阴阳师弹窗上按返回键会弹出游戏的退出确认，不会关闭弹窗**，见 [back-key](build-evidence/back-key/README.md) |

| `screen.tapRegion` v1 | `region`（句柄，来源链不得含区域）、`durationMs`、`requireNoText`（布尔，明确给出） | 点击由锚点推出的区域中心，用于点击弹窗外空白处关闭弹窗。输入前重新截图、重新唯一定位同一锚点并按相同偏移重新推出区域；`requireNoText` 为 true 时先识别区域内文字，只要识别出任何非空文字（不论置信度）就不点击，拒绝原因会写出区域坐标和识别内容。识别器返回的空文字检测框不算文字，只计入 trace |
| `screen.dragRegion` v1 | `region`（句柄，来源链不得含区域）、`durationMs`、`dx`、`dy`、`referenceWidth`、`referenceHeight`（位移和参考尺寸都须由任务版本写死） | 从推出区域的中心沿直线拖到按参考尺寸缩放的位移处，用于拿起列表里没有固定文字或图标的卡片（如寄养时拖式神到好友的空灯笼）。输入前与 `tapRegion` 一样重新截图、重新唯一定位锚点并重新推出区域；画面比例与参考尺寸不同或终点超出画面时不拖 |

| `screen.locateImage` v1 | `observation`（整图观察，来源链不得含区域）、`template`（已声明资源）、`minimumScore` | `target`：整图中恰好一处模板匹配达到得分时成立，零处或多处都判为无法确认。用于没有文字的图标。点击、按住、滑动和 `tapRegion` 的锚点在输入前都会用同一模板重新匹配，而不是复用旧坐标 |

`screen.classifyText` 的状态可以加可选的 `absent`：列出不得出现的文字（各自带置信度），必须非空、字段齐全。用于区分“弹了下载框的商店”和“普通商店”。

`variation` 用于测试程序在不同输入形态下的完整性，所有取值由任务作者明确给出，App 不填默认值：`startJitter`（0–1，起点在目标框内的偏移比例）、`curve`（0–0.5，二次贝塞尔弯曲深度占位移长度的比例）、`durationJitter`（0–0.5，时长变化比例）、`points`（2–32，路径采样点数），`seed` 可选。同一种子生成同一路径；未给种子时由 App 生成，并连同实际时长和点数写入持久化的输入回执，便于复现。全部取 0、`points` 取 2 即为直线。

提案中原写作“`screen.readText` 加可选 `region`”，实施时改为独立的 `screen.readRegionText`。原因：`readText` 会截取新画面，而区域读取必须复用已观察的同一帧，两者语义不同。

**区域内定位到的目标不能点击**（`screen.tap` 声明 `forbiddenAncestors = {screen.region}`，运行时另有保护）。点击前要在新截图里重新定位目标，而区域来源链无法在新画面上重放。需要点击时，应在整图观察中定位按钮文字。

## 识别后端与保护

- `vision` JNI 新增 `overrideTemplate` 与 `inspectRaw`，原生层只接受 `OCR`／`TemplateMatch`。子进程沿用原 OBSERVE 协议：附带 `requests` 和由宿主分配名称（`t0.png`…）的模板描述符，复制模板时校验长度和 SHA-256。
- 结果解码要求每个结果框都落在请求区域内，否则判为无效输出。
- **CPU 保护**：如果 `/proc/cpuinfo` 声明了 `sve2` 却没有 `sve`（Apple Silicon 宿主上的 AVD 就是这样），图像请求在启动子进程前即返回 `UNSUPPORTED_ENVIRONMENT`，避免 OpenCV KleidiCV 的 SIGILL。文字请求不受影响。

## 验证

- core：128 项通过，含新增句柄与视觉配置测试 9 项。
- 专用 API36 模拟器：`TextObservationContractTest` 15 项通过；`VersionedMaaIntegrationTest` 3 项通过、2 项按设计跳过，图像请求走 CPU 保护分支；`TextObservationRuntimeTest` 21 项通过、3 项按设计跳过。完整回归结果见实现进度。
- 真机 SM-G9910／API35：只运行 `VersionedMaaIntegrationTest`，4 项通过、1 项跳过。合成帧上同一模板在付费卡区域得分 0.999999、免费卡区域 0.31，区域内读出“领取”。运行时游戏保持前台，未发送输入，无障碍服务保持启用；测试包已卸载，手机上的助手已更新为本次构建。

## 未覆盖

真实游戏画面上的整条任务（锚点 → 区域 → 状态 → 点击 → 核对）尚未运行；阈值没有基于足够样本确定；跨分辨率缩放只有单元级计算，没有设备证据；Windows 模拟器无证据；trace 未持久化。

## 每日礼包离线回放（草稿任务）

`DailyGiftReplayTest` 用真实 `ScreenActions`、版本资源和原生识别，配合脚本化设备回放私人截图，不连接游戏。草稿步骤：整图观察 → 定位“每日礼包” → 推出按钮区域 → `classifyRegion`（`claimable`：区域内有“领取”且没有魂玉图标；`paid`：有魂玉图标）→ `claimable` 才在整图定位“领取”并点击，点击后重新观察并核对“获得奖励”；`paid` 不输入，核对列表后完成。魂玉模板在测试运行时从私人帧裁出，阈值 0.45 只是暂定值，来源是同一天、同一设备的样本。脚本设备只有在点击点落在免费按钮内时，才切换到奖励帧。

需要 `-PincludePrivateReplayFrames=true -PincludeOcrIntegrationModels=true` 构建，并传 `-e includePrivateReplay true -e allowOcrIntegration true` 运行；默认测试包不含这些帧，运行后应卸载测试包。

专用 API36 模拟器上 5 项通过，全部走 CPU 防护分支：图像证据不可用，程序停在无法确认，没有输入，也没有写入动作意图。完整流程（点击一次并核对奖励、付费状态不输入、点击未产生奖励时保持未知、无关画面不被猜测）需要在真机上运行，尚待手机连接。奖励弹窗的关闭和后续“已领取”核对不在本草稿内：关闭需要点击空白处或返回键，现有动作还不支持。

### 真机结果（2026-11-18，SM-G9910／API35，构建 `830682e`）

`VersionedMaaIntegrationTest` 与 `DailyGiftReplayTest` 一同运行：10 项中 9 项通过，1 项坏 ONNX 用例需显式故障参数，按设计跳过。回放 5 项都走了完整路径：
- 领取前帧只点击一次免费按钮，切到奖励帧后核对“获得奖励”通过；
- 另一会话采集的同状态帧同样判为可领取；
- 付费帧不输入，直接完成；
- 点击后画面没有变成奖励时，结果保持未知；
- 已领详情帧不被误判，也没有任何输入。

复用后真机连续观察 303–347ms（此前冷启动 865–966ms）。合成帧模板得分与上次一致（免费区 0.31、付费区 0.999999）。

测试期间手机停在桌面，没有启动游戏，没有向游戏发送输入。含私人帧的测试包已卸载；手机上的助手更新为本构建，无障碍服务保持启用。这仍是回放证据，不是实际游戏中的自动领取。

### 关闭弹窗与进程内回放（2026-11-18）

core 的来源检查改为只看来源链上游，不含句柄自身的类型：`tapRegion` 要的是区域句柄，但会拒绝由“区域内定位的目标”再推出的区域。

每日礼包草稿的可领取分支在核对“获得奖励”之后继续：
1. 以“获得奖励”为锚点推出弹窗左侧空白区域（dx −842、dy 65、120×120），用 `tapRegion` 点击；
2. 等待 1.5 秒后重新观察，以详情第一列标题“御行达摩的赠礼”为锚点推出左侧空白区域（dx −392、dy 145），再点击；
3. 等待 1.5 秒后重新观察，核对“新手符咒包”可见，即已回到列表。

调试入口新增回放模式（`--ez replay true` 加暂存的 `replay.json`）：在已运行的助手进程内，用脚本化画面代替真实截图和输入，不运行 instrumentation，所以不会断开无障碍服务。真机上两天的截图各回放两种起点：
- 可领取起点：按顺序点击领取按钮、奖励弹窗外、详情外，共 3 次输入，最后核对回到列表，任务完成；
- 付费起点：直接完成，没有输入。

回放中第一次运行被空白检查拦下：识别器在近乎全黑的区域返回了 2 个空文字、置信度 0 的检测框。保护按设计拒绝了点击，没有误点；排查后改为只把非空文字计为文字。

模拟器上契约、运行时（含真实无障碍桥上的空白点击，以及有文字时拒绝）和回放测试共 54 项通过，core 全部通过。**`tapRegion` 尚未在实际游戏中执行**：今日免费礼包已领取，奖励弹窗要到下次领取才会出现。

### 从庭院导航到每日礼包（2026-11-18）

先用 maaprobe 在真机上测了两天共 12 张导航截图（maaprobe 是独立应用，不影响助手进程和无障碍服务）：
- 卷轴图标模板在另一天的庭院得分 1.000，且唯一；其他画面最高 0.468。
- “商店”两天都只读出“店”（商字被图标遮住），改用“阴阳寮”作锚点推出商店图标的区域。
- “取消”“下载”“礼包屋”“每日礼包”两天都能精确读出。
- 未选中的“日常”竖排字读不出，改用灯笼模板：另一天得分 0.999，次高为另一盏灯笼 0.62，进入日常后的选中灯笼为 0.739，因此取 0.85。

草稿任务 `open-daily-gift`（前提：位于庭院）：卷轴 → 等待 → 以“阴阳寮”推出商店图标区域并点击 → 等待 → 按“下载”／“礼包屋且无下载”分为两支，有下载框则点“取消” → 点“礼包屋” → 用灯笼模板点“日常” → 核对“每日礼包”。

真机进程内回放：
- 两天的截图都按 5 次输入完成导航，点击位置都在预期区域；
- 去掉下载框的变体按 4 次输入完成；
- 领取回放 4 种回归通过。

模拟器上契约、运行时与识别集成测试共 56 项通过。导航尚未在实际游戏中运行；不在庭院时启动，结果为无法确认，不会输入。

### 读数、选择、颜色与画面对比（2026-11-18）

| 动作 | 输入 | 输出 | 规则 |
| --- | --- | --- | --- |
| `screen.readNumber` v1 | `observation`、`minimumConfidence`、`minimum`、`maximum` | `value` | 统一全角数字，去掉空格和千分位逗号后，必须是纯数字。观察里只能有一个不同的数值，多个不同数值判为无法确认；超出范围不截断，也判为无法确认。不解析“万”等单位。 |
| `screen.readFraction` v1 | 同上 | `value`、`total` | 同上，格式为 `12/30`，范围同时约束两个数。 |
| `screen.selectText` v1 | `observation`、`text`、`minimumConfidence`、`order`、`index` | `target` | 按 `top`／`bottom`／`left`／`right` 排序后取第 `index` 个（从 0 起，0–49）。数量不够判为无法确认。 |
| `screen.selectImage` v1 | `observation`（整图）、`template`、`minimumScore`、`order`、`index` | `target` | 同上，匹配对象是图像模板。 |
| `screen.matchColor` v1 | `region`、`lower`、`upper`、`minimumRatio` | `matched`、`ratio` | 统计区域内落在 RGB 闭区间内的像素比例（隔行隔列采样），直接用已观察的像素计算，不启动识别进程。 |
| `screen.compareFrames` v1 | `before`（观察）、`region`、`minimumDifference` | `changed`、`difference` | 计算 `before` 与区域所属观察在该区域内的平均绝对差（0–1）。 |

- **选中目标的重新定位：** 输入前在原位置附近的窗口内，取离原位置最近的匹配，且移动距离不得超过目标的宽高中较大者。这样相邻的同名按钮不会被判为“不唯一”，明显移位时也不会点错。
- **前后对比的边界：** core 的 `HandleRequirement.allowStale` 只开放给 `compareFrames` 的 `before` 参数。输入时，最近的观察和最多 2 帧像素转存一次，只供比较读取，不能用于定位或输入；下一次输入时会被覆盖。
- **控制流：** `until` 循环配合 `classifyText`／`classifyRegion` 可以写出条件等待，配合 `swipe` 和 `compareFrames` 可以写出滚动查找，不需要单独的动作。

阈值都由任务作者明确给出，App 不提供默认值。这些动作已在模拟器自有画面上用真实识别和真实无障碍验证；`selectImage` 依赖模板匹配，在模拟器上被 CPU 防护拒绝，只做了契约校验，**尚无运行时证据**。都还没有在实际游戏画面上使用过。

### 启动游戏与本机通知（2026-11-18）

| 动作 | 输入 | 输出 | 规则 |
| --- | --- | --- | --- |
| `app.launch` v1 | `profile` | `delivered` | 请求打开视觉配置里声明的应用入口。目标已在前台时不发送任何请求，避免打断当前页面。按输入动作处理：写入意图与回执，之前的观察全部失效，之后必须重新观察并核对。 |
| `app.awaitForeground` v1 | `profile`、`timeoutMs`（1–120000） | `foreground` | 每 500 毫秒查询一次前台应用，不截图。超时判为无法确认。 |
| `notify.local` v1 | `title`（1–64 字）、`text`（1–240 字） | `delivered` | 发一条只有文字的本机通知，不带截图，也不经过网络。没有通知权限时 `delivered` 为 false，任务继续。 |

边界：
- **请求启动不等于已进入游戏。** Android 可能静默拦截后台启动，所以必须靠 `awaitForeground` 和之后的观察来证明。登录、公告、更新等启动后的画面要由任务自己处理。
- **只有写在步骤开头的 `app.launch`** 才能让步骤在目标不在前台时开始；无障碍未连接或屏幕未亮时仍然等待。
- **不提供强制重启。** 普通应用无权结束其他应用，游戏卡死时只能报告无法确认，由用户处理。
- **开机后不自动拉起游戏**的产品规则不变，这个动作只在用户启动的任务里执行。
- **包可见性**：清单只声明了对桌面入口的查询，没有申请读取全部应用列表的权限。
- **通知权限**：设置 → 运行环境 → 任务通知。Android 13 及以上点“开启通知”弹出系统授权框；系统不再弹框或通知被关闭时，改为跳到本应用的系统通知设置，返回后状态自动刷新。
- `notify.local` 是任务作者写的消息，和事件规则、通知渠道那套设计是两回事，后者尚未实现。

模拟器上已验证：从桌面启动自身应用、等到前台并由观察核对；等待一个不会到前台的应用时超时为无法确认。通知已在模拟器上实际发出，并在系统通知列表中核对到标题和正文；后台启动游戏还没有在真机上验证。
