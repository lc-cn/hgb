# 动作证据持久化

2026-11-18。用于事后诊断：每个执行过的动作留一条记录，写明结果类别和该动作给出的结构化 trace。这些记录**不是执行状态**，恢复、去重、未知判定都不依赖它；崩溃时可能丢失最后几条。

## 结构

- core：`ActionTraceSink`／`ActionTraceRecord`。步骤解释器在每个动作返回后记录：所属尝试、任务、步骤、动作、能力与合同版本、结果（`PRODUCED`／`VERIFIED`／`UNAVAILABLE`／`INTERRUPTED`）、原因或核对证据、trace、耗时。记录器抛异常也不影响步骤结果，有测试覆盖。
- app：Room 版本 5 新增 `action_traces` 表（按 `runId` 建索引），带显式的 4→5 迁移。`ActionTraceLog` 通过一个有界通道和单个消费协程按顺序写入；缓冲区满时丢弃最新一条，写入失败直接忽略。每写入 200 条清理一次，只保留最近 5000 条。
- 正式 App 与 debug 的 `LocalTaskTrigger` 都已接入。触发器把本次运行的 trace 一并写进 `result.json`。

## 各动作的 trace 内容

| 动作 | 字段 |
| --- | --- |
| readText | 候选数量、帧尺寸 |
| locateText | 区域、置信度；失败时为同文字数量和达到阈值的数量 |
| expectText | 最高置信度、阈值 |
| classifyText | 命中的状态 |
| deriveRegion／readRegionText | 区域、候选数量 |
| matchImage／locateImage／classifyRegion | 区域、得分、模板摘要、命中的状态 |
| tap／longPress | 目标区域、按下点、时长、是否图像目标 |
| swipe | 种子、采样点数、实际时长、起止点（种子也写入持久化回执） |
| tapRegion | 区域、空文字检测框数量；拒绝时的原因中写有识别到的文字 |
| back | 类别 |

trace 中不含像素、账号值，也不含屏幕上识别出的任意文字。唯一的例外是 `tapRegion` 拒绝时的原因：会写出空白区域里实际识别到的文字，以便判断是误检还是真有内容。

## 验证

- core 测试：记录顺序与字段正确，记录器抛异常时步骤仍完成。
- 存储测试：按顺序写入、清理只保留最新记录；4→5 迁移保留原有数据。
- 模拟器完整回归：208 项中 198 项通过，10 项为需要私人素材或分阶段运行的用例，按设计跳过。之后补上点击证据，相关的 53 项再次通过。
- 真机：用导航回放验证，一次运行留下 24 条记录，各字段都在。

## 观察到的性能问题

真机上整图识别每次 3.0–4.6 秒。点击类动作要在新截图上重新识别一遍，所以每次点击需要 3.5–5.4 秒，导航一次约 65 秒。这是下一步优化的重点，例如重新定位时只识别原目标附近的区域。

## 另一个发现

`anOffscreenTaskWaits...` 用例在冷启动的模拟器上，带着之前测试留下的应用数据，连续失败了 3 次：任务回到前台后，第一次截图赶上了切换动画，画面里没有文字，程序判为无法确认（没有猜测）。卸载并清除数据后重装同一构建，连续通过，完整回归时也通过。由此看出，“回到前台”就绪后，第一次观察可能落在切换动画中；产品层面是否需要等画面稳定后再观察，留待之后处理。
