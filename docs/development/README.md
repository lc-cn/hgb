## 2. 编码必须守住的已确认约定

| 约定 | 开发约束 |
| --- | --- |
| 动作 → 步骤 → 任务 → 计划 | 动作由 APK 提供；任务＝步骤＋配置 schema；计划＝有序任务集合＋时间＋账号归属 |
| 云任务容器 | 游戏目录、步骤、schema、资源从版本化内容读取；调试样例也用独立数据文件，不变成内置固定游戏任务目录 |
| 唯一执行器 | 队列、当前任务、暂停和恢复统一管理；页面、计划、悬浮、调试不各建一套调度器 |
| 恢复 | 继续：跳过完成步骤，未完成步骤从入口重新观察；重新开始：当前任务第一步，其他任务保留；未知副作用先核对 |
| 优先级 | 独立提交按任务分值；计划整轮按成员分值之和锁定，期间不递减；严格高优可安全抢占，平级 FIFO |
| 控制与输入 | 暂停／停止保持全队暂停，供用户接管；移除当前项在旧输入静默、结果可安全交接后继续，不解除已有人工暂停 |
| 失败与未知 | 确认失败记结果并继续；未知不冒充失败、成功或可重试，不因移除／切号／重做清证据 |
| 入队 | 任务和计划按钮提交一轮；未结束的同类型同 ID 不重复入队；排队标识与禁用、当前暂停由执行器状态投影 |
| 计划 | 每日／指定星期；无总启用开关，保存有效计划登记日程，保存不额外执行一次；时间策略未定部分不自行补做 |
| 常用与悬浮 | 列表行星标；球 → 快捷 → 常用；常用内部按画面过滤，普通 UI 不解释技术矩阵；当前控制不被过滤 |
| 任务更新 | 一次启动自动拉取＋手动拉取；拉取不启用；当前版本号＋已知更新红点；版本行启用／删除、正文展开 changelog |
| 版本锁 | 提交锁定完整任务集、配置、账号与排序分值；在途／恢复／未知依赖版本不被替换或删除 |
| 事件与通知 | 规则生成事件，渠道订阅事件并投递；开始和成功也是事件；通知失败不改变业务结果或调度；首批规则全关 |
| 代理 | 用户选择模型／任务源／外部通知范围；各传输适配遵守保存配置，失败不擅自改路由 |
| 账号 | Root 专用环境先验快照；新身份核对成功且实际换号才清旧队列；原计划保原账号，保持暂停等用户继续 |
| 开发者 | GitHub 登录并核对指定仓库权限；App 内制作与调试；用户明确上传即发布完整任务集，不自动替消费者启用 |
| 原生 UI | 五主入口、横竖自适应、草稿和状态保留；设置顶栏主题三选；多彩半透明图标、清晰正文与玻璃回退 |

界面中的示例商品、时间、次数、优先级、预算和模型名称均不直接成为生产默认。具体控件与布局以当前稿及 PRD 对应条目为准。

## 3. 技术选择的状态

建议沿用现有技术方案的 **Kotlin＋Jetpack Compose＋Material 3，coroutines／Flow，Room／DataStore，kotlinx.serialization，OkHttp**。该原生技术组合已获用户确认，具体兼容版本由工程核验后锁定。正式构建前须从官方合同核验 JDK／Gradle／AGP／Kotlin／Compose／SDK 的兼容组合并锁版本；本机安装了哪个 SDK，不代表自动选择它为 compileSdk 或最低支持版本。

以下按验证结果决定，不能为了开工一并堆进 APK：

| 待定实现 | 决定依据 | 不阻塞的独立工作 |
| --- | --- | --- |
| 截图／输入承载 | 无障碍截图与手势、MediaProjection 对照；在途输入撤销、撤权、旋转和真实画面 | 领域模型、队列测试、无权限下的管理 UI |
| 同进程／独立 DeviceBridge 进程 | 能否在代表卡死场景下独立撤销旧输入并证明静默；多进程不是产品要求 | 桥接口与模拟边界测试 |
| OCR／图形后端 | Paddle／ML Kit／Maa 纯识别等按同样本对照；离线、留出主题、定位、完成判定和资源开销 | 观察／定位接口、样本分类、配置 UI |
| JSON 合同与编排语法 | 领取、兑换、御魂代表定义能否表达；输出引用、分支／循环、恢复、兼容失败 | 外部任务定义的解析与校验边界设计 |
| GitHub 授权类型与任务集附件协议 | 指定仓库、客户端配置、权限和完整发布／拉取闭环；占位仓库不是部署目标 | 本地任务集验证、版本占用与启用流程 |
| SMTP／认证 SOCKS5／Root 快照 | 分别核验实际传输或设备合同 | 普通 HTTP、本地记录、普通已登录任务 |

逻辑职责沿用现有架构：UI 观察状态并发命令；Executor 排序与运行控制；TaskWorker 解释已锁定任务；DeviceBridge 承接设备调用；识别和云视觉返回观察／提案；任务版本与存储管理内容和引用；事件规则与通知独立消费事实。包结构与 Gradle 模块数量是实施设计，不在此新增框架层次。

## 4. 首期建议：先取得一个可实际验证的闭环

**建议的首期成果：可安装的 Android 容器，按 UI v5 管理队列与任务版本，能在所选目标环境中关闭云模型完成一项代表领取任务，保留执行结果；同 APK 可换用两份独立任务集，恢复和移除控制经真实平台验证。** 首期通过不等于所有游戏任务、所有主题或 24 小时可靠性已通过。

该交付切分已由用户于 2026-11-16 确认；完整 PRD 的功能不被删除或默默判为不支持。

| 顺序 | 可评审的交付物 | 完成证据与继续条件 |
| --- | --- | --- |
| M0 工程与可安装壳 | 锁定构建组合、可重复构建 APK；UI v5 原生主题、导航、横竖骨架；无任务时如实展示空目录 | 构建命令和 APK 摘要；目标 Android 安装／启动；主题切换、旋转和返回不丢当前上下文。编译成功不代替后续设备证明 |
| M1 控制基石与平台 PoC | 唯一 Executor、任务数据合同初稿、步骤重入；授权／截图／输入／浮层最小适配 | 单元／集成情境覆盖排队、计划30对独立25、严格高优安全抢占、去重、全队暂停、两种恢复、确认失败与未知；目标设备截图和受控输入、撤权、旋转、暂停中与已静默时间线。不能以协程取消代表旧输入已停止 |
| M2 任务集与配置 | 外部 JSON 定义与 schema 表单、配置保存、任务列表、版本拉取／校验／启用／删除、运行锁定 | 同 APK 处理两套完整版本；损坏／缺动作／未知控件不启用；拉取不换在途版本，删除不损坏引用；表单不产生虚构默认；正式远端联调需明确任务仓库 |
| M3 代表游戏闭环 | 从每日物资或永久勾玉卡产出中选有资格的一项，采集当前玩法证据后制作任务；离线识别后端经对照再选 | 关闭云模型，在已适配和未参与适配的实际主题分别核对入口、目标与领取结果；已领／无资格／定位未知分别处理；执行和恢复不重复领取。真实账号与具体操作授权独立核对 |
| M4 首期联验 | 工作台、任务列表、队列、当前执行、三层悬浮、结果记录贯通；真实平台故障验证 | 工作台与浮层观察同一执行器；移除卡死当前项撤销旧输入后继续，迟到结果不复活；人工暂停保留接管；版本／配置更改不改变本轮；给出支持环境和未通过项 |

定时计划、完整事件通知与代理、开发者 App 内编排及 GitHub 发布、Root 登录态、更多业务任务、陌生活动和 24 小时运行按完整需求继续交付。各自进入开发前确定对应范围和规则；不会在首期用“可点但不执行”的正式功能伪装已交付。

以下验证需提前穿插，以免后期推翻核心方向：JSON 表达要用领取／兑换／御魂样例证明不只适合一条线性流程；新活动与 Root 可做独立可行性实验，但不能把尚未具备的能力计入首期完成。

## 7. 编码目标的验收口径

后续目标模式应以“交付物＋具体行为＋证据＋未覆盖范围”为完成条件。每阶段在实际集成边界验证，发现缺产品规则只暂停依赖路径，其他已授权工作继续。

- 先核对当前目录、并发工作、依赖版本与合同，再改代码；引用既有原型情境不等于保留旧实现。
- 执行器集成测试覆盖用户明确的队列、恢复、移除、未知和账号边界；平台取消／静默必须有设备证据，不能只测内部布尔值。
- 原生 UI 以真实 APK 的明暗与横竖截图核对 UI v5；CSS 模糊效果、固定截图尺寸和浏览器通过不算原生性能证明。
- 每次报告分别写清源码实现、内存／模拟测试、本机构建、目标设备、真实游戏和长期运行做到了哪一层。
- 真实账号输入、消费、消息发送、Release 发布和部署各自核对授权与恢复，不由写代码或构建授权推导。

本次资料整理已处理 PRD 的旧视觉状态、当前设计入口、已定／未定事项混排、架构中的旧恢复交互提示、容器稿中 GitHub 来源仍未确认的旧说法，以及旧环境调查中的路径误判。没有对游戏能力、构建通过或生产就绪作新的成功声明。
